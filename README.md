# ORBITA

[![CI](https://github.com/yuldoshbek/Project_/actions/workflows/ci.yml/badge.svg)](https://github.com/yuldoshbek/Project_/actions/workflows/ci.yml)
![Python](https://img.shields.io/badge/python-3.12-3776AB)
![React](https://img.shields.io/badge/react-18-61DAFB)
![PostgreSQL](https://img.shields.io/badge/postgresql-16-336791)

Инструмент управления проектами для аппарата заместителя директора Агентства
космических исследований и технологий Республики Узбекистан («Ўзбеккосмос»).

**Пользователей двое:** личный помощник вносит данные, заместитель директора смотрит и
принимает решения — с телефона, ежедневно. Встречи, занятость и поручения приходят
обменом с ассистентом SETA — тем же Telegram-ассистентом, которым руководитель уже
пользуется. Сама ORBITA в Google-календарь не ходит
([договор](docs/integration/SETA-ORBITA.md)).

Одна точка управления, одна актуальная картина, полная прозрачность.

---

## О чём проект

Агентство одновременно ведёт десятки проектов, мини-проектов и срочных поручений:
космический мониторинг, дистанционное зондирование Земли, международное сотрудничество,
инфраструктурные и регуляторные инициативы. Сегодня это управляется вручную — через
мессенджеры, отдельные файлы и личный контроль помощника. Единой точки правды по статусам
и срокам нет.

Система замыкает одну цепочку целиком:

```
Письмо → Обращение → Проект → Задача → Встреча → Решение → Результат
```

Каждое звено ставится кнопкой в момент создания, а не связывается руками потом. Открыв
проект, видно всю дорожку: откуда пришло и чем кончилось.

| Проблема | Что делает система |
|---|---|
| Руководитель не видит общей картины без опроса кураторов | Главный экран: тревога → лента времени → портфель → изменения |
| Зелёный проект, который на самом деле стоит | Сигнал «молчит»: нет ни задачи, ни комментария, ни встречи дольше порога |
| Срочные задачи теряются в общем потоке | Приоритет «Срочно» с таймером эскалации |
| Нет единой истории по проекту | Карточка: вехи, задачи, файлы, комментарии, обращения, встречи, журнал |
| Просрочки обнаруживаются постфактум | Напоминания за 1, 3, 7 дней и автоэскалация |
| Непонятно, кто и о чём к нам обращается | Реестр входящих обращений, включая «Ижро» — поручения Президентского аппарата и других вышестоящих органов |
| Встреча прошла — и следов не осталось | Результат в три поля за минуту, задачи из решений, вычисляемое качество |
| Помощник вручную собирает статусы | Экран «Сегодня»: весь периметр руководителя на одном экране |

Таблица — замысел целиком. Что из него уже написано, сказано ниже в «Статусе»: около
четверти.

Ключевое, чего нет в коробочных продуктах: **главный экран, который читается за
30 секунд с телефона**, **числа для утренней сводки в том боте, которым руководитель уже
пользуется**, **обмен с ассистентом SETA без единого конфликтующего поля** и **поиск,
одинаково работающий на русском, узбекской кириллице и узбекской латинице**.

Два свойства определяют весь остальной проект: презентационный слой — это и есть
продукт, а стоимость ручного ввода решает, выживет ли система. Разборы —
[COUNCIL-0002](docs/council/COUNCIL-0002.md) и ADR-0015…0019.

## Кто пользуется

Две роли: **помощник** (вносит всё) и **руководитель** (смотрит, читает сводки, принимает
решения по проектам на контроле). Разграничения доступа между ними нет — делить нечего
([ADR-0011](docs/adr/ADR-0011-two-user-scope.md)).

Кураторы проектов и исполнители задач — **сотрудники агентства, а не пользователи**: они
живут в справочнике, чтобы было понятно, с кого спрашивать, но в систему не входят.

Граница проходит по периметру системы, а не между пользователями: внутри делить нечего,
значение имеет только то, что уходит наружу — в обмен с SETA, в её бот, в экспорт и в
запрос к внешней модели. Решением заказчика от 16.09.2026 гриф секретности снят целиком:
службы безопасности здесь нет, есть два человека и вопрос «что можно показывать наружу».
От прежнего правила остаётся предпочтение выдачи `share_externally` у проекта, и проверка
по-прежнему стоит внутри функции выдачи, а не в вызывающем коде. Прежняя редакция —
[ADR-0007](docs/adr/ADR-0007-restricted-data.md), она переписывается.

## Связка с SETA

SETA — работающий Telegram-ассистент того же руководителя: поручения со сроками,
календарь, встречи, утренняя сводка, четыре языка. Договор двух систем живёт в одном
файле — [docs/integration/SETA-ORBITA.md](docs/integration/SETA-ORBITA.md), и правится он
только по согласованию обеих сторон. Коротко: время руководителя назначает только SETA, в
Google ходит тоже только она, ORBITA забирает встречи и анонимную занятость из её
сервисного API, считает по ним показатели и отдаёт обратно готовые числа для утренней
сводки и уведомления с кнопками решений. Своего Telegram-бота ORBITA не пишет, её
интерфейс открывается как Mini App из бота SETA. Цена названа сразу: собственного пути к
Google у нас больше нет, и когда SETA не отвечает, календарь показывает последние
известные данные с честной пометкой о свежести.

## Статус

**Ранняя стадия. Закрыт 21 тикет из 81 (три сняты при смене объёма) — около четверти
плана по весам.**

Единственный счётчик состояния — [docs/STATE.md](docs/STATE.md): что сделано, чего нет,
чем занята текущая волна. Порядок и зависимости карточек —
[docs/tickets/INDEX.md](docs/tickets/INDEX.md). Здесь — срез на 16.09.2026, чтобы
читающий сразу понимал, на что смотрит.

Backend написан заметно дальше интерфейса: 48 эндпоинтов `/api/v1`, 21 таблица,
13 миграций — вход, справочники, проекты, задачи, вехи, партнёры проекта, журнал
изменений, чек-листы и теги, комментарии с единым потоком событий, вложения с версиями,
фоновый воркер. Целиком отсутствуют встречи, входящие обращения, снимки состояния,
календарь, отчёты и обмен с SETA.

Во frontend работают **два экрана из семи**: «Проекты» (список и доска) и «База задач».
Дашборд, «Сегодня», Календарь, Отчёты и Администрирование — заглушки. Форм создания и
правки нет **ни одной**: из интерфейса записываются только вход, изменение проекта,
загрузка и удаление вложения, а из полусотни эндпоинтов используется 13. Руководитель в
системе пока не может ничего — `POST /projects/{id}/decision` упомянут в докстрингах и не
существует. Дизайн-система нарисована полностью, в код перенесена примерно на пятую
часть.

Тестов: 464 backend против настоящей PostgreSQL и 100 frontend.

Порядок ближайших работ: развязка с SETA и уборка → формы ввода и карточка проекта,
параллельно тёмная тема и космические токены → решение руководителя и главный экран →
«Ижро» → обмен с SETA → визуализации на canvas → ИИ-слой → выкладка.

## Технологии

| Слой | Выбор |
|---|---|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2 (async), Pydantic v2 |
| База данных | PostgreSQL 16, схема `orbita`, `pg_trgm` + `unaccent` для поиска |
| Миграции | Alembic — единственный способ менять схему |
| Фоновые задачи | Redis + ARQ (напоминания, эскалация, отчёты, обмен с SETA) |
| Frontend | React 18 + TypeScript, Vite, TanStack Query/Table, react-i18next |
| Файлы | S3-совместимое хранилище (MinIO в разработке) |
| Качество | ruff, mypy, import-linter, eslint, prettier, pytest, vitest |

Стек совпадает со стеком ассистента SETA — чтобы обе системы поддерживала одна команда.
Обоснование: [ADR-0002](docs/adr/ADR-0002-tech-stack.md).

## Быстрый старт

Нужны: Python 3.12, Node.js 22, Docker, [uv](https://docs.astral.sh/uv/).

```bash
git clone https://github.com/yuldoshbek/Project_.git orbita
cd orbita
cp .env.example .env
```

Дальше — на Linux и macOS через `make`, на Windows через `.\make.ps1` (цели одинаковые):

```bash
make install    # зависимости backend и frontend
make up         # postgres, redis, minio, почта — с ожиданием готовности
make migrate    # применить миграции
make seed       # справочники раздела 7 ТЗ и две учётные записи
make dev        # backend :8000 и frontend :5173
```

Windows (`make` в системе нет, обёртка делает то же самое):

```powershell
.\make.ps1 install
.\make.ps1 up
.\make.ps1 migrate
.\make.ps1 seed
.\make.ps1 dev
```

Проверки перед коммитом:

```bash
make test     # pytest и vitest
make check    # ruff, mypy, границы слоёв, eslint, tsc, prettier
```

**Пароля в сидах нет намеренно.** Репозиторий публичный, и захардкоженный пароль в сидах
останется в рабочей системе. Первичный пароль назначается командой:

```bash
make password EMAIL=assistant@orbita.local
```

Полный список целей — `make help`.

### Что поднимает `make up`

Окружение поднимается и ждёт, пока все сервисы пройдут healthcheck. Номера портов ниже —
значения по умолчанию из `.env.example`.

| Сервис | Адрес | Зачем |
|---|---|---|
| PostgreSQL 16 | `127.0.0.1:55432`, базы `orbita` и `orbita_test` | данные; расширения `pg_trgm`, `unaccent`, `citext`, `pgcrypto` включены при создании |
| Redis 7 | `127.0.0.1:56379` | очередь фоновых задач |
| MinIO | http://localhost:59001 (консоль), логин `orbita` / `orbita-secret` | хранилище вложений, бакет `orbita` |
| Преобразователь (Gotenberg) | `127.0.0.1:53000` | LibreOffice в headless-режиме: производный PDF для предпросмотра DOCX, XLSX, PPTX (ADR-0009) |
| Антивирус (ClamAV) | `127.0.0.1:53310` | проверка вложений до сохранения (Q7). **Первый запуск долгий:** базы сигнатур весят под гигабайт |
| Почта (Mailpit) | http://localhost:58025 | письма разработки не уходят наружу |

**Порты смещены намеренно.** Стандартный 5432 часто занят нативным PostgreSQL: контейнер
тогда садится только на IPv6, а клиент молча уходит в чужую базу. Все порты
переопределяются в `.env`, привязка — только к `127.0.0.1`.

**Одного смещения мало, когда рядом стоит SETA.** Её окружение выбирало номера тем же
способом и пересеклось с нашим; на общем сервере стороны расходятся через `.env`, а в
продуктиве порты базы и очереди на хост не публикуются вовсе — системы говорят по
внутренней сети Docker.

**Адрес — `127.0.0.1`, а не `localhost`.** Windows резолвит `localhost` сначала в `::1`;
контейнеры слушают только IPv4, и подключение занимает 2 секунды вместо 70 миллисекунд.
Разницу платит каждое соединение приложения, а не только тесты.

Остановить: `make down` (данные сохраняются) или `make reset` (данные удаляются, база
создастся заново).

### Где живут данные

**В репозитории данных нет и не будет.** Всё живёт в томах Docker; секреты — в `.env` и
GitHub Secrets.

| Что | Где | `make down` | `make reset` |
|---|---|---|---|
| Проекты, задачи, справочники, аудит | PostgreSQL, том `orbita_postgres-data` | сохраняется | удаляется |
| Тестовые данные | база `orbita_test` | — | пересоздаётся |
| Очередь фоновых задач | Redis, том `orbita_redis-data` | сохраняется | удаляется |
| Вложения | MinIO, том `orbita_minio-data`, бакет `orbita` | сохраняется | удаляется |
| Базы сигнатур антивируса | ClamAV, том `orbita_clamav-data` | сохраняются | удаляются и скачиваются заново |
| Письма разработки | Mailpit, только память | теряются | теряются |

Потеря очереди не теряет данных: фоновые задания идемпотентны
([ADR-0008](docs/adr/ADR-0008-notifications-escalation.md)), повторный прогон не шлёт
второго уведомления. Токенов Google в базе нет и не будет: в Google ходит SETA, а ORBITA
берёт встречи и занятость из её API. Из секретов остаётся сервисный токен обмена — он
живёт в окружении и в GitHub Secrets, в репозитории его нет.

## Решения, определяющие проект

- **Две роли вместо разграничения по проектам**
  ([ADR-0011](docs/adr/ADR-0011-two-user-scope.md)). Механизм, у которого нет двух
  сторон, ничего не разграничивает, но стоит дорого. ADR-0003 отменён.
- **Владение с SETA разделено по полям**
  ([ADR-0015](docs/adr/ADR-0015-seta-data-ownership.md)). Срок поручения меняется только
  здесь, отметка «выполнено» — только там. Пересекающихся полей не существует, поэтому
  арбитраж конфликтов не нужен: его нечем разрешать. Договор с SETA расширяет долю SETA,
  правила не отменяя.
- **Риски — сигналы, а не реестр**
  ([ADR-0016](docs/adr/ADR-0016-risks-signals-not-register.md)). Пять вычисляемых
  признаков и одна строка «что мешает». Реестр с вероятностью и планом реагирования
  требует регулярного пересмотра руками, которого при одном вносящем не будет.
- **Встреча — объект учёта, а не строка календаря**
  ([ADR-0018](docs/adr/ADR-0018-meetings-as-records.md)). Качество вычисляется по следам:
  ручную оценку через две недели начинают ставить не глядя.
- **Руководитель — прямой пользователь, телефон — основной вид**
  ([ADR-0019](docs/adr/ADR-0019-leader-is-direct-user.md)). Что помещается на телефоне,
  разложится на ноутбуке; обратное неверно, и порядок работ это отражает.
- **«Просрочена» — вычисляемый признак, а не статус**
  ([ADR-0004](docs/adr/ADR-0004-overdue-is-computed.md)).
- **Не вариант A и не вариант B, а «A-ready»**
  ([ADR-0001](docs/adr/ADR-0001-architecture-variant.md)): самостоятельный сервис,
  спроектированный под слияние с SETA, но не зависящий от её сроков.

## Как вести работу

```
/council → /grill → /to-spec → /to-tickets → worktrees + параллельные агенты
        → /tdd → /implement → /verify → /code-review → /finish-branch
```

Один тикет — одна ветка — одно рабочее дерево. Готовность подтверждается прогоном
`make check` и `make test`, а не словами. Между тикетами — `/clear`: контекст предыдущего
мешает следующему. Подробно: [docs/PIPELINE.md](docs/PIPELINE.md) и
[CONTRIBUTING.md](CONTRIBUTING.md).
