# ORBITA — система управления проектами и задачами Агентства «Ўзбеккосмос»

Инструмент на двоих: личный помощник заместителя директора вносит данные, заместитель
директора смотрит и анализирует. Портфель проектов, база задач, единый календарь, дашборд
со «светофором», сводки руководителю через бота SETA, отчётность.

Первоисточник требований — [ТЗ v1.0](tz/TZ-ORBITA-v1.0.md). Всё, что ему противоречит, —
баг, **кроме** расхождений, перечисленных в [COUNCIL-0002](docs/council/COUNCIL-0002.md):
объём сужен до двух пользователей, и это осознанное решение, а не отступление. Правки в
ТЗ подготовлены там же, в разделе «Что предлагается изменить в ТЗ».

Два свойства продукта определяют всё остальное:

- **Презентационный слой — это и есть система.** Если руководитель не понял картину за
  полминуты, задача не выполнена, сколько бы функций ни работало.
- **Стоимость ввода определяет, выживет ли продукт.** Данные вносит один человек вручную,
  между делом. Пять минут на проект — и через месяц данные устареют.

## Язык

Документация, тикеты, коммиты, комментарии в коде, сообщения об ошибках для
пользователя — **на русском**. Идентификаторы в коде, имена таблиц и полей,
API-пути — **на английском**. Смешивать внутри одного идентификатора нельзя.

## Стек

| Слой | Технология |
|---|---|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2.x (async), Pydantic v2 |
| БД | PostgreSQL 16, схема `orbita`, расширения `pg_trgm`, `unaccent` |
| Миграции | Alembic (единственный способ менять схему) |
| Фон/очереди | Redis + ARQ |
| Файлы | S3-совместимое хранилище (MinIO в dev) |
| Frontend | React 18 + TypeScript, Vite, TanStack Query, TanStack Table, react-i18next |
| Тесты | pytest + httpx (backend), vitest + Testing Library (frontend), Playwright (e2e) |
| Качество | ruff, mypy (strict на `app/domain`), eslint, prettier |

Стек выбран под совместимость с ассистентом SETA — см. [ADR-0002](docs/adr/ADR-0002-tech-stack.md).

## Архитектура

Модульный монолит, слоями (`backend/app`):

```
api/        FastAPI-роутеры, схемы запросов/ответов. Без бизнес-логики.
services/   Сценарии использования. Транзакции живут здесь.
domain/     Модели, правила, инварианты. Не знает про FastAPI и SQLAlchemy.
repos/      Доступ к данным. Единственное место с SQL/ORM-запросами.
adapters/   Внешний мир: identity, notifications, storage, export.
workers/    ARQ-задачи: напоминания, эскалация, повторяющиеся задачи, отчёты.
```

Правило зависимостей сверху вниз: `api → workers → services → adapters → repos → domain`.
Обратные импорты запрещены — проверяется линтером импортов.

`adapters` стоит **над** `repos`, а не рядом: адаптер внешней системы почти всегда
работает с данными — провайдер входа сверяет пароль с хешем в базе, отправщик
уведомлений отмечает факт отправки. Обратное запрещено и остаётся запрещённым:
репозиторий не имеет права звонить в Telegram.

Своего Telegram-бота у ORBITA нет: [ADR-0013](docs/adr/ADR-0013-telegram-bot.md) отменён
в части бота [договором с SETA](docs/integration/SETA-ORBITA.md). Второй канал
руководителя — бот SETA: ORBITA отдаёт ему числа для утренней сводки и принимает нажатия
кнопок решений, обмен живёт в `adapters`. Числа он получает из тех же сервисов, что и
дашборд: два источника расчёта разойдутся в цифрах, и доверия не будет ни к одному.

**Ключевые порты** (внешние системы подменяются конфигом, не переписыванием кода):
`IdentityProvider`, `NotificationChannel`, `FileStorage`, `ReportRenderer`, `CalendarSync`.
Обоснование — [ADR-0001](docs/adr/ADR-0001-architecture-variant.md).

## Инварианты, которые нельзя нарушать

1. **Граница проходит по периметру системы, а не между пользователями.** Пользователей
   двое, оба видят всё ([ADR-0011](docs/adr/ADR-0011-two-user-scope.md)); грифа
   секретности в системе нет. Единственный вопрос, который остаётся, — что можно
   показывать наружу, и на него отвечает `projects.share_externally`. Точек выхода
   пять: Google-календарь, SETA, Telegram через бота SETA, экспорт, внешняя модель.
   Проект с `share_externally = false` не проходит ни через одну — ни записью, ни
   счётчиком. **Проверка стоит внутри функции выдачи, а не в вызывающем коде**: вызывающих
   у каждой выдачи много, и шестую точку выхода добавят, про правило не вспомнив. См.
   [ADR-0024](docs/adr/ADR-0024-share-externally.md), заменяющий ADR-0007.
2. **«Просрочена» — вычисляемое состояние, не статус.** В БД `status` ∈
   `new|in_progress|in_review|done|cancelled`; просрочка = `due_at < now()` и статус не
   терминальный. Хранить «просрочена» в `status` запрещено — теряется исходное состояние.
3. **Никаких ключей в репозитории.** Он публичный. Токен бота, идентификатор и секрет
   Google OAuth, токены обновления — только окружение и GitHub Secrets. Токены обновления
   в базе хранятся зашифрованными ключом, который не входит в резервную копию базы.
4. **Каждое изменение проекта или задачи пишется в `audit_log`** — через сервисный слой,
   не точечными вызовами из роутеров.
5. **Все временные метки — `timestamptz`, хранение в UTC**, отображение в `Asia/Tashkent`.
6. **Фоновые задачи идемпотентны.** Повторный запуск не должен слать второе уведомление —
   факт отправки фиксируется в `notifications` / `escalations`.
7. **Схема БД меняется только миграцией Alembic.** `create_all` в рантайме — запрещён.

## Команды

```bash
make up            # поднять postgres, redis, minio, mailhog
make migrate       # alembic upgrade head
make seed          # справочники из раздела 7 ТЗ + демо-данные
make dev           # backend :8000 и frontend :5173
make test          # pytest + vitest
make check         # ruff + mypy + eslint + tsc --noEmit
```

## Рабочий процесс

Один тикет — одна ветка — один worktree. Порядок и зависимости тикетов:
[docs/tickets/INDEX.md](docs/tickets/INDEX.md).

```
/council → /grill → /to-spec → /to-tickets → worktrees + параллельные агенты
   → /tdd → /implement → /verify → /code-review → /finish-branch
```

Команды лежат в `.claude/commands`, скиллы — в `.claude/skills`.

- Ветки: `orb-042-recurring-tasks` (номер тикета + короткий слаг).
- Коммиты: `ORB-042: краткое описание в повелительном наклонении`.
- Тикет закрыт только когда выполнены **все** критерии приёмки из его файла и
  пройден `/verify`. «Написал код» — не признак готовности.
- Между тикетами — `/clear`. Контекст предыдущего тикета мешает следующему.

## Чего не делать

- Не добавлять поля в БД «на будущее» — только под конкретный критерий приёмки.
- Не тянуть UI-библиотеку целиком ради одного компонента.
- Не реализовывать то, что ТЗ вынесло за MVP (ЭЦП, бухучёт, учёт трудозатрат) — это
  разделы 2.5 и 11.3 ТЗ. ИИ-слой из этого списка вышел: заказчик включил его решением
  16.09, границы и правило выхода наружу —
  [ADR-0022](docs/adr/ADR-0022-ai-layer-boundaries.md).
- Не писать синхронизацию календарей — ни одну сторону, ни обе. Дело не в границах MVP
  (в разделах 2.5 и 11.3 ТЗ её нет): двусторонней синхронизацией занимается SETA. ORBITA
  берёт встречи и занятость из её API, направление «Google → ORBITA» снято, наружу
  остаётся только выгрузка своих вех и сроков
  ([ADR-0020](docs/adr/ADR-0020-calendar-comes-from-seta.md)).
- Не менять справочники статусов и приоритетов в коде: они редактируемые данные (ТЗ 6.8).
- Не коммитить `.env`, дампы БД и реальные данные агентства.
