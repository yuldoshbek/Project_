# ORBITA — контроль поручений и проектов аппарата заместителя директора «Ўзбеккосмос»

Инструмент на двоих: помощник заместителя директора вносит данные, заместитель директора
смотрит с телефона и принимает решения. **Три блока и ничего сверх них:**

1. **Ижро** — реестр поручений вышестоящих органов. Таблицы приходят из `ijro.gov.uz`
   файлами Word, состояние исполнения ведём мы.
2. **Портфель** — проекты, вехи, задачи агентства.
3. **Связка с SETA** — числа для утренней сводки, приём решений кнопкой, вход Mini App.

Объём сужен 18.09.2026 с девяти разделов ТЗ до этих трёх ([план пересборки](docs/PLAN.md)).
Всё, что в ТЗ v1.0 и в старых документах описано сверх них, — снято, а не отложено.
Первоисточник требований остаётся [ТЗ v1.0](tz/TZ-ORBITA-v1.0.md), но расхождения с ним
теперь существенные и перечислены в [CONTEXT](docs/CONTEXT.md) — они осознанные решения
заказчика, а не баги.

Два свойства продукта определяют всё остальное:

- **Презентационный слой — это и есть система.** Если руководитель не понял картину за
  полминуты, задача не выполнена, сколько бы функций ни работало.
- **Стоимость ввода определяет, выживет ли продукт.** Данные вносит один человек вручную,
  между делом. Пять минут на поручение — и через месяц данные устареют.

## Язык

Документация, тикеты, коммиты, комментарии в коде, сообщения об ошибках для
пользователя — **на русском**. Идентификаторы в коде, имена таблиц и полей,
API-пути — **на английском**. Смешивать внутри одного идентификатора нельзя.
Содержание поручений хранится как есть — на узбекской кириллице, переводу не подлежит.

## Стек

| Слой | Технология |
|---|---|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2.x (async), Pydantic v2 |
| БД | PostgreSQL 16, схема `orbita`, расширения `pg_trgm`, `unaccent`, `citext`, `pgcrypto` |
| Миграции | Alembic (единственный способ менять схему) |
| Фон/очереди | Redis + ARQ |
| Файлы | S3-совместимое хранилище (MinIO в dev) |
| Frontend | React 18 + TypeScript, Vite, TanStack Query, react-i18next, CSS Modules |
| Трёхмерный слой | three.js + @react-three/fiber, отдельным чанком, **вне телефона** |
| Тесты | pytest + httpx (backend), vitest + Testing Library (frontend) |
| Качество | ruff, mypy (strict на `app/domain`), eslint, stylelint, prettier |

Стек выбран под совместимость с ассистентом SETA — см. [ADR-0002](docs/adr/ADR-0002-tech-stack.md).
**Библиотеки графиков в проекте нет и не будет**: цвета обязаны приходить из `tokens.css`,
иначе счётная проверка контраста перестаёт работать на половине экрана
([ADR-0021](docs/adr/ADR-0021-cosmic-visual-layer.md), пункт 6).

## Архитектура

Модульный монолит, слоями (`backend/app`):

```
api/        FastAPI-роутеры, схемы запросов/ответов. Без бизнес-логики.
services/   Сценарии использования. Транзакции живут здесь.
domain/     Модели, правила, инварианты. Не знает про FastAPI и SQLAlchemy.
repos/      Доступ к данным. Модели и запросы.
adapters/   Внешний мир: identity, storage, queue, antivirus, docx, seta, reports.
workers/    ARQ-задачи: напоминания, сборка отчётов.
```

Правило зависимостей сверху вниз: `api → workers → services → adapters → repos → domain`.
Обратные импорты запрещены — проверяется import-linter (`backend/pyproject.toml`).

`adapters` стоит **над** `repos`, а не рядом: адаптер внешней системы почти всегда
работает с данными — провайдер входа сверяет пароль с хешем в базе. Обратное запрещено:
репозиторий не имеет права звонить наружу.

**Ключевые порты** (внешние системы подменяются конфигом, не переписыванием кода):
`IdentityProvider`, `FileStorage`, `ReportRenderer`, `SetaGateway`.
Обоснование — [ADR-0001](docs/adr/ADR-0001-architecture-variant.md).

## Инварианты, которые нельзя нарушать

1. **«Просрочено» — вычисляемое состояние, не статус.** У задачи `status` ∈
   `new|in_progress|in_review|done|cancelled`, у поручения `state` ∈
   `not_started|in_progress|blocked_by_lead|submitted|done|removed_from_control`.
   Просрочка = срок прошёл и состояние не терминальное. Хранить «просрочено» в статусе
   запрещено — теряется исходное состояние ([ADR-0004](docs/adr/ADR-0004-overdue-is-computed.md)).
2. **У поля один хозяин.** Ввоз Ижро меняет только поля источника (`content`, `mechanism`,
   `responsible_raw`, ведомство, `due_on`, `source_state_raw`) и **никогда** — наши
   (`state`, `problem`, `proposal`, ленту, вложения). За SETA — `tasks.status`,
   `completed_at`, `due_at`; за нами — `planned_due_at` и все показатели. Чужое поле
   игнорируется молча ([ADR-0015](docs/adr/ADR-0015-seta-data-ownership.md),
   [ADR-0025](docs/adr/ADR-0025-ijro-standalone-register.md)).
3. **Одни и те же цифры во всех местах.** Экран, отчёт и утренняя сводка SETA считаются
   одними сервисами. Два источника расчёта разойдутся, и доверия не будет ни к одному.
   Сценарии «что если» считает тот же сервис, что и обычные показатели.
4. **Каждое изменение пишется в `audit_log`** — примесью `Auditable` через сервисный слой,
   не точечными вызовами из роутеров ([ADR-0010](docs/adr/ADR-0010-audit-log.md)).
   Сценарий «что если» не пишет **ничего**: он не меняет состояния.
5. **Происхождение данных видно на самих данных.** Что привезли таблицей, что внёс человек
   и что сопоставила система — три разные вещи. `responsible_raw` хранится всегда рядом с
   сопоставленным `responsible_person_id`; `due_year_source` говорит, откуда взялся год.
6. **Свежесть показывается всегда.** У каждого числа — дата последнего привоза и подпись
   «по таблице от 10 сентября». Данные Ижро приезжают партиями, а не текут.
7. **Никаких ключей в репозитории.** Он публичный. Реальные файлы агентства (`*.docx`) в
   git не попадают. Сервисный токен SETA, токены обновления — только окружение и GitHub
   Secrets.
8. **Все временные метки — `timestamptz`, хранение в UTC**, отображение в `Asia/Tashkent`.
   Просрочка считается по календарным дням.
9. **Фоновые задачи идемпотентны.** Повторный запуск не шлёт второго уведомления и не
   собирает второго отчёта — факт фиксируется в базе.
10. **Схема БД меняется только миграцией Alembic.** `create_all` в рантайме запрещён.
11. **Наружу ведут три точки** — SETA, Telegram через бота SETA, экспорт. В каждой
    действует `projects.share_externally`, и **проверка стоит внутри функции выдачи**, а не
    в вызывающем коде ([ADR-0024](docs/adr/ADR-0024-share-externally.md)).

## Команды

```bash
make up            # поднять postgres, redis, minio, mailhog
make migrate       # alembic upgrade head
make seed          # справочники + демо-данные
make dev           # backend :8000 и frontend :5173
make test          # pytest + vitest
make check         # ruff + mypy + eslint + stylelint + tsc --noEmit
```

## Рабочий процесс

Один тикет — одна ветка — один worktree. Порядок и зависимости:
[docs/tickets/INDEX.md](docs/tickets/INDEX.md), план пересборки — [docs/PLAN.md](docs/PLAN.md).

```
/council → /grill → /to-spec → /to-tickets → worktrees + параллельные агенты
   → /tdd → /implement → /verify → /code-review → /finish-branch
```

- Ветки: `orb-101-ijro-model` (номер тикета + короткий слаг).
- Коммиты: `ORB-101: краткое описание в повелительном наклонении`.
- Тикет закрыт только когда выполнены **все** критерии приёмки и пройден `/verify`.
  «Написал код» — не признак готовности.
- Между тикетами — `/clear`.

## Чего не делать

- Не добавлять поля в БД «на будущее» — только под конкретный критерий приёмки.
- Не тянуть UI-библиотеку, библиотеку графиков или набор иконок целиком ради одного
  элемента. Значки рисуются разметкой по `design/Icons.dc.html`.
- **Не ставить трёхмерную сцену под данные и не грузить `three` на телефоне.** Список
  разрешённых поверхностей — [ADR-0021](docs/adr/ADR-0021-cosmic-visual-layer.md), раздел 3а.
  Текст поверх сцены не ставится никогда: контраст на градиенте не проверить счётом.
- **Не заводить связь поручения с задачами и проектами.** Ижро — отдельный реестр
  ([ADR-0025](docs/adr/ADR-0025-ijro-standalone-register.md)). Вопрос «что мы сделали по
  поручению» отвечается внутри его карточки.
- **Не склеивать написания ФИО алгоритмом.** `Ш. Арибжанов` — не `А. Арибжанов`.
  Сопоставление подтверждает человек, результат запоминается псевдонимом.
- Не реализовывать снятое: встречи, входящую корреспонденцию, Google-календарь в любую
  сторону, ИИ-слой и внешнюю модель, конструктор отчётов, почтовый канал, ЭЦП, бухучёт,
  учёт трудозатрат, свой Telegram-бот, реестр рисков, разграничение доступа между
  пользователями.
- Не менять справочники статусов и приоритетов в коде: они редактируемые данные (ТЗ 6.8).
- Не коммитить `.env`, дампы БД и **реальные документы агентства** (`*.docx` в `.gitignore`).
