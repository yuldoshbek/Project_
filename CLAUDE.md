# ORBITA — рабочее пространство заместителя директора «Ўзбеккосмос»

Инструмент на двоих: помощник вносит данные, заместитель директора смотрит с iPhone и
принимает решения. Десять разделов: Пульт, Программы, Проекты, Задачи, Ижро,
Взаимодействие, Доклады и мероприятия, Идеи и карты, Календарь, Управление.

Первоисточник требований — [ТЗ v2.0](tz/TZ-ORBITA-v2.0.md). Всё, что ему противоречит, —
баг. Словарь — [CONTEXT](docs/CONTEXT.md), термины употребляются строго в его значении.
Базовый план — [PLAN](docs/PLAN.md), он меняется только на приёмке блока.

Документы до 20.09.2026 (ТЗ v1.0, план v2, тикеты, прежний глоссарий) лежат в
[архиве](docs/archive) и **не действуют**. Отменённые решения помечены в
[docs/adr](docs/adr) — из истории они не вычёркиваются.

Два свойства продукта определяют всё остальное:

- **Презентационный слой — это и есть система.** Не понял картину за полминуты с
  телефона — задача не выполнена, сколько бы функций ни работало.
- **Стоимость ввода определяет, выживет ли продукт.** Данные вносит один человек между
  делом. Что можно вычислить — вычисляется, а не вводится.

## Язык

Документация, коммиты, комментарии, сообщения об ошибках для пользователя — **на
русском**. Идентификаторы в коде, имена таблиц и полей, пути API — **на английском**.
Смешивать внутри одного идентификатора нельзя. Ни одной строки текста в коде интерфейса —
только ключи перевода. Содержание поручений Ижро хранится как есть, на узбекской
кириллице, и переводу не подлежит.

## Стек

| Слой | Технология |
|---|---|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2.x (async), Pydantic v2 |
| БД | PostgreSQL 16, схема `orbita`; расширения `pg_trgm`, `unaccent`, `citext`, `pgcrypto` |
| Миграции | Alembic — единственный способ менять схему |
| Фон | задачи по расписанию через защищённый эндпоинт; **постоянного воркера и Redis нет** |
| Файлы | порт `FileStorage`: Vercel Blob в облаке, S3‑совместимое хранилище на своём сервере |
| Frontend | React 19, TypeScript, Vite, Tailwind CSS 4, shadcn/ui, Motion, Recharts, Lucide, TanStack Query и Router, react-i18next, PWA |
| Тесты | pytest + httpx, vitest + Testing Library, Playwright (e2e и снимки экранов) |
| Качество | ruff, mypy (strict на `app/domain`), import-linter, eslint, prettier, tsc |

Стек зафиксирован [ADR-0030](docs/adr/ADR-0030-frontend-stack.md). Размещение и
переносимость — [ADR-0028](docs/adr/ADR-0028-hosting.md). Настройка площадок —
[SETUP](docs/SETUP.md), эксплуатация — [RUNBOOK](docs/RUNBOOK.md).

## Архитектура

Backend — модульный монолит слоями (`backend/app`):

```
api/        роутеры, схемы запросов и ответов. Без бизнес-логики
services/   сценарии, единица работы (Unit of Work), транзакции, сервис показателей
domain/     правила и инварианты. Не знает про FastAPI и SQLAlchemy
repos/      модели и запросы. Единственное место с SQL
adapters/   внешний мир: storage, push, разбор docx, экспорт, позже SETA
jobs/       идемпотентные задачи по расписанию
```

Правило зависимостей сверху вниз: `api → jobs → services → adapters → repos → domain`.
Обратные импорты запрещены и проверяются import-linter.

Frontend (`frontend/src`):

```
app/        маршруты, провайдеры, тема, устройство
shared/     клиент API из OpenAPI, набор компонентов, i18n, утилиты времени
sections/   по каталогу на раздел ТЗ
```

**Ключевые порты**, которые подменяются конфигом, а не переписыванием кода:
`FileStorage`, `Scheduler`, `PushSender`, `ReportRenderer`, `SetaGateway`.

## Инварианты

1. **«Просрочено» — вычисляемое состояние, не статус.** Срок прошёл и состояние не
   терминальное. Хранить просрочку в статусе запрещено.
2. **Одни и те же цифры во всех местах.** Все показатели считает один сервис показателей.
   Сценарий «что если» считает тем же кодом и **не пишет в базу ничего**.
3. **Аналитика только от вопроса.** У показателя на экране есть вопрос руководителя,
   ответ числом или фразой, дата данных и действие. Нет действия — нет показателя.
4. **У поля один хозяин.** Привоз Ижро меняет только поля источника и никогда — наши:
   этап, проблему, предложение, ленту, связи. Чужое поле игнорируется молча.
5. **Каждое изменение пишется в журнал** сервисным слоем в одной транзакции с изменением,
   а не точечными вызовами из роутеров.
6. **Происхождение данных видно на данных.** Что привезли таблицей, что внёс человек и что
   предложила система — три разные вещи. Сырое написание ФИО хранится всегда.
7. **Свежесть показывается всегда:** у каждого числа из привоза — «по таблице от 15.09».
8. **Время:** `timestamptz`, хранение в UTC, показ в `Asia/Tashkent`, просрочка по
   календарным дням.
9. **Схема меняется только миграцией Alembic.** `create_all` в рантайме запрещён.
10. **Фоновые задачи идемпотентны.** Повторный запуск не шлёт второго уведомления.
11. **Реальные данные живут только в рабочем контуре.** Превью и демо получают вымышленные
    данные; ветка базы для превью создаётся от демо, а не от рабочей.
12. **Ключей в репозитории нет** — он публичный. Только окружение и GitHub Secrets.
13. **Доступ — по личной ссылке** ([ADR-0029](docs/adr/ADR-0029-access-by-link.md)).
    Проверка стоит в одном месте на входе в API. Пользователей двое, оба видят всё; роль
    подписывает действие, а не ограничивает выдачу.
14. **Никаких полей «на будущее»** — только под конкретный критерий приёмки.

## Команды

```bash
make up            # поднять postgres для разработки
make migrate       # alembic upgrade head
make seed          # справочники и демо-данные
make dev           # backend :8000 и frontend :5173
make test          # pytest + vitest
make e2e           # playwright на локальной сборке
make check         # линтеры, типы и проверка документов
make docs          # только проверка документов
make job n=<имя>   # выполнить задачу по расписанию вручную
make reqs          # пересобрать backend/requirements.txt из uv.lock
```

На Windows те же цели — `./make.ps1 <цель>`.

## Рабочий процесс

Работа идёт **крупными блоками**, а не десятками тикетов. Один блок — одна ветка — один
PR. Состав и критерии приёмки блоков — в [PLAN](docs/PLAN.md).

Цикл блока:

1. **Разработка** — по критериям приёмки блока.
2. **Тест визуала** — снимки телефона, ноутбука и монитора в двух темах; исправление.
3. **Тест кода** — pytest, vitest, Playwright, все проверки в CI зелёные.
4. **Отчёт блока** — `docs/reports/BLOCK-N.md`: что сделано, снимки, тесты, ограничения.

Затем приёмка: заказчик смотрит превью, даёт замечания одним пакетом, после правок
нажимает выкладку в рабочую систему.

- Ветки: `block-1-core`, `block-2-control`, `block-3-ideas`.
- Коммиты: `B1: краткое описание в повелительном наклонении`.
- `main` защищён правилами из [.github/rulesets](.github/rulesets/README.md): только
  через PR с зелёными проверками.
- Конвейер: проверки на каждый push, превью на каждый PR, выкладка в рабочий контур по
  кнопке, ночная копия базы. Ключи вводит заказчик — разработка их не видит.
- **Объём блока не меняется посреди блока.** Новое требование записывается и обсуждается
  на приёмке, с разбором влияния на план.
- Готово — это пройденные критерии приёмки и зелёный CI, а не «написал код».

## Чего не делать

- Не возвращать снятое: Redis и постоянный воркер, ClamAV, Gotenberg, MinIO, вход по
  паролю, гриф и `share_externally`, разграничение доступа между пользователями, встречи,
  Google-календарь, внешние модели ИИ, собственный Telegram-бот, учёт трудозатрат в часах.
- Не рисовать график, у которого нельзя назвать вопрос и решение.
- Не ставить космическую сцену под данные и не грузить её на телефоне.
- Не склеивать написания ФИО алгоритмом: `Ш. Арибжанов` — не `А. Арибжанов`. Совпадение
  подтверждает человек, результат запоминается псевдонимом.
- Не менять справочники типов, статусов и порогов в коде: это редактируемые данные.
- Не тянуть библиотеку целиком ради одного компонента.
- Не коммитить `.env`, ключи и дампы базы. Реальные таблицы агентства по умолчанию в
  `.gitignore`; их место в репозитории — отдельное решение заказчика.
- Не начинать следующий шаг цикла блока, пока не закончен предыдущий.
