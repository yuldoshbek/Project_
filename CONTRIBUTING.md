# Как здесь работают

Правила, которые дороже всего нарушать, собраны в [CLAUDE.md](CLAUDE.md). Здесь — короткий
порядок работы.

## Блок

Работа идёт крупными блоками, а не десятками мелких тикетов. Один блок — одна ветка — один
PR. Состав и критерии приёмки блока — в [PLAN](docs/PLAN.md).

Цикл: **экран на вымышленных данных → API под утверждённый экран → тест визуала → тест
кода → отчёт** (`docs/reports/BLOCK-N.md`), затем приёмка заказчиком на превью и выкладка
по кнопке. Отступления от цикла записываются в [журнал изменений плана](docs/PLAN.md) и в
[HANDOFF](docs/HANDOFF.md).

Объём блока внутри блока не меняется. Новое требование записывается в
[OPEN-QUESTIONS](docs/OPEN-QUESTIONS.md) и обсуждается на приёмке, с разбором влияния на
план.

## Ветки, коммиты, PR

- Ветки блоков: `block-1-core`, `block-2-control`, `block-3-ideas`. Все влиты в `main`
  08.10.2026 слиянием squash (PR #13, #16, #20) и остаются на GitHub как история:
  пошаговые коммиты `B1:`–`B3:` этих PR сохранились только в ветках. Коммиты, на которые
  ссылаются HANDOFF и отчёт блока 0, вошли в `main` раньше, 25.09, слиянием PR #11. Новая
  работа — ветка от `main`.
- Коммит: `B1: краткое описание в повелительном наклонении`, по-русски; цифра — номер блока.
  Обновления зависимостей — своей веткой и PR, коммиты `deps: …`; у dependabot —
  `deps(backend)`, `deps(frontend)`, `deps(ci)`.
- В `main` — только через PR с пятью зелёными проверками (Документы, Backend, Миграции,
  Frontend, Сценарии и снимки) и только слиянием squash: один блок — один коммит. Правила
  лежат в [.github/rulesets/main.json](.github/rulesets/main.json); на GitHub они действуют
  после импорта заказчиком ([SETUP](docs/SETUP.md), шаг 3), до того соблюдаются вручную.
- Описание PR — по [шаблону](.github/PULL_REQUEST_TEMPLATE.md): критерии приёмки с
  доказательствами и фактический вывод проверок.
- PR dependabot по backend меняет `uv.lock`, но не `backend/requirements.txt`: если задеты
  рабочие зависимости, в ветке такого PR нужен `make reqs`, иначе CI покажет расхождение.

## Перед тем как сказать «готово»

```bash
make check
make test
make e2e
```

`make e2e` поднимает свой стенд — свежую базу `orbita_e2e`, API на :8001 и собранный
интерфейс на :5174 — и окно `make dev` не трогает. Прогон чувствителен к нагрузке машины
(наблюдение — в комментарии к `retries` в `frontend/playwright.config.ts`): параллельно с
ним pytest и другие тяжёлые прогоны не запускают.

Вывод прикладывается, а не пересказывается. Критерии приёмки закрываются по одному, у
каждого названо доказательство: имя теста, снимок экрана или вывод команды. Подробнее —
`/verify` и скилл `verification-before-completion`.

## Язык

Документы, коммиты, комментарии и сообщения пользователю — по-русски. Идентификаторы,
таблицы, поля и пути API — по-английски. Внутри одного идентификатора не смешивать. В
интерфейсе ни одной строки текста в коде: только ключи перевода.

## Чего не делать

- Не добавлять поля «на будущее» — только под критерий приёмки.
- Не рисовать график, у которого нельзя назвать вопрос и решение.
- Не коммитить `.env`, ключи, дампы базы и настоящие таблицы агентства — репозиторий
  публичный.
- Не возвращать снятое: список — в [CLAUDE.md](CLAUDE.md), раздел «Чего не делать».
