# Как вести работу над ORBITA

Короткая версия: один тикет — одна ветка — один заход. Готовность подтверждается прогоном,
а не словами. Полные правила работы с кодом — в [CLAUDE.md](CLAUDE.md).

## Прежде чем писать код

1. Прочитайте карточку тикета в [docs/tickets](docs/tickets) — цель, объём, критерии
   приёмки, «не входит».
2. Прочитайте [CLAUDE.md](CLAUDE.md): инварианты и границы слоёв. Их нарушение — дефект,
   а не стилистическое разногласие.
3. Прочитайте ADR, названные в карточке. Решение уже принято и объяснено; если вы с ним не
   согласны — это новый ADR, а не молчаливое отступление в коде.

## Окружение

Нужны Python 3.12, Node.js 22, Docker и [uv](https://docs.astral.sh/uv/).

```bash
cp .env.example .env
make install       # на Windows: .\make.ps1 install
make check
make test
```

Опционально: `pre-commit install` — часть проверок отработает до коммита.

## Ветка и коммиты

```bash
git fetch origin
git worktree add -b orb-NNN-краткий-слаг /d/orbita-wt/orb-NNN origin/main
```

Ветка: `orb-042-recurring-tasks`. Коммит: `ORB-042: краткое описание в повелительном
наклонении`. Рабочие деревья нужны, когда несколько тикетов идут параллельно — подробности
в `.claude/skills/using-git-worktrees`.

## Границы, которые проверяются автоматически

- **Слои.** `api → services → domain`; `services → repos` и `services → adapters` через
  порты. Обратные импорты ловит `import-linter`.
- **Схема БД** меняется только миграцией Alembic. `create_all` в рантайме запрещён тестом.
- **Время** — `timestamptz`, хранение в UTC. Наивные даты ловит ruff (правило `DTZ`) и тест.
- **Документы** — нумерация тикетов и внутренние ссылки проверяются `scripts/check_docs.py`.

## Что проверяется на ревью

- Каждый чекбокс критериев приёмки отмечен и подтверждён тестом или ручной проверкой.
- Новый эндпоинт-список добавлен в `test_rbac_no_leaks` — иначе это утечка между проектами.
- Новая точка выдачи данных наружу обрабатывает проекты `restricted`.
- Изменение сущности пишется в аудит через сервисный слой, а не точечным вызовом из роутера.
- Новое фоновое задание идемпотентно, есть тест на двойной прогон.
- Пользовательских строк в компонентах нет — только ключи локализации, три письменности.
- В диффе нет ничего сверх объёма тикета.

## Чего не делать

- Не добавлять поля и зависимости «на будущее»: без критерия приёмки — не нужно.
- Не реализовывать вынесенное за MVP (ИИ-слой, двусторонняя синхронизация календарей, ЭЦП,
  бухучёт) — разделы 2.5 и 11.3 ТЗ.
- Не менять справочники статусов и приоритетов в коде: это редактируемые данные (ТЗ 6.8).
- Не коммитить `.env`, дампы и реальные данные Агентства.
- Не редактировать `tz/` — замечания к ТЗ оформляются предложением
  ([COUNCIL-0001](docs/council/COUNCIL-0001.md), раздел «Что предлагается изменить в ТЗ»).

допущением, по которому работаете до ответа, и назовите это в описании PR.
