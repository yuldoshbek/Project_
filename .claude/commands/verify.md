# Проверка готовности $ARGUMENTS

«Написал код» — не признак готовности. Готовность — это выполненные критерии приёмки,
подтверждённые запуском. Ниже — обязательный порядок. Не отмечай пункт, не выполнив его.

## 1. Запусти, а не предположи

```bash
make check
make test
```

Приложи фактический вывод. Если что-то падает — так и скажи, с выводом. Красный тест,
объявленный «не связанным с моими изменениями», должен быть подтверждён: покажи, что он
падал и до них.

## 2. Пройди критерии приёмки тикета по одному

Открой карточку тикета. По каждому чекбоксу назови, **чем именно** он подтверждён: имя
теста или описание ручной проверки с результатом. Чекбокс без подтверждения не отмечается.

## 3. Сквозные инварианты (CLAUDE.md)

- [ ] Новые эндпоинты-списки добавлены в `test_rbac_no_leaks` (ADR-0003).
- [ ] Новые точки выдачи данных наружу обрабатывают `restricted` (ADR-0007): списки, поиск,
      экспорт, уведомления, .ics.
- [ ] Изменения сущностей пишутся в аудит через сервисный слой (ADR-0010).
- [ ] Новые фоновые задания идемпотентны, тест на двойной прогон есть (ADR-0008).
- [ ] Пользовательские строки — только ключи локализации, три локали заполнены.
- [ ] Время — `timestamptz`, никаких наивных дат.
- [ ] Схема БД изменена миграцией; `alembic heads` показывает одну голову.

## 4. Посмотри на собственный диск

```bash
git status
git diff --stat
git diff
```

- [ ] Нет отладочного вывода, закомментированного кода и временных файлов.
- [ ] Нет изменений вне объёма тикета.
- [ ] Не закоммичены `.env`, дампы, реальные данные агентства.

## 5. Честный отчёт

Напиши три списка: **сделано и проверено**, **сделано, но не проверено** (и почему),
**не сделано** (и почему). Третий список пустым быть может, но не по умолчанию.

Если что-то из тикета не сделано — это нормально и должно быть названо. Не нормально —
сказать «готово», когда не готово.
