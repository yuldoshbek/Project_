# Раздача тикетов параллельным агентам

Параллелить стоит тогда, когда тикеты независимы **и по зависимостям, и по файлам**.
Иначе выигрыш во времени съедается разбором конфликтов.

## 1. Выбери волну

Открой [INDEX.md](../../../docs/tickets/INDEX.md), раздел «Волны параллелизации». Волна
готова, если:

- все её зависимости закрыты и слиты в `main`;
- ни один тикет волны не ждёт ответа заказчика (таблица заблокированных тикетов);
- в волне **не более одного** тикета, создающего миграцию Alembic;
- общие файлы (`main.py`, корневой роутер, словари локализации, `Makefile`) правит только
  один тикет волны — назначь его владельцем.

Ширина: 3–5 агентов. Больше — и приёмка результатов становится узким местом: один человек
не удержит в голове пять диффов.

## 2. Подготовь деревья

По одному worktree на тикет, скилл `using-git-worktrees`. Общие контейнеры поднимаются один
раз; каждому агенту — своя тестовая база.

## 3. Сформулируй задание

Агент стартует с пустым контекстом. Он не знает ничего из этого разговора. Задание должно
быть самодостаточным:

```
Тикет: ORB-014
Рабочее дерево: /d/orbita-wt/orb-014, ветка orb-014-tasks-crud

Прочитай в таком порядке:
  1. CLAUDE.md — инварианты и границы слоёв
  2. docs/tickets/E1-mvp.md, карточка ORB-014
  3. docs/SPEC.md, раздел 1.4 и строки API по задачам
  4. docs/adr/ADR-0003 (доступ), ADR-0004 (просрочка)

Реализуй ORB-014 по /tdd: критерий приёмки — тест — код.
Границы: только то, что в карточке. Чек-листы, теги, комментарии — другие тикеты, не трогай.
Миграции в этой волне создаёшь только ты; файлы main.py и словари локализации не правь.
Закончив, выполни /verify и приложи фактический вывод make check и make test.
Отчёт: что сделано, что не сделано и почему.
```

Что обязательно в каждом задании:
- **номер тикета и путь к дереву** — иначе агент начнёт работать в основном каталоге;
- **список файлов для чтения** в порядке приоритета — иначе агент прочитает всё ТЗ и
  потратит контекст на неотносящееся;
- **явные границы** — что лежит рядом и трогать нельзя;
- **кто владеет общими файлами и миграциями** в этой волне;
- **требование фактического вывода тестов**, а не утверждения «всё работает».

## 4. Пока агенты работают

Не давай им новых задач в тот же контекст. Если нужно уточнение — уточняй по конкретному
агенту и конкретному тикету.

## 5. Принимай результаты по одному

Не сливай всю волну разом. По каждому тикету:

1. Прочитай отчёт агента, отдельно — раздел «не сделано».
2. Проверь фактический вывод тестов. Отсутствие вывода означает, что работа не проверена.
3. `/code-review` по диффу тикета.
4. `/finish-branch` — слияние и уборка.
5. После каждого слияния следующий агент перебазируется на новый `main` и перепрогоняет
   тесты. Порядок слияния — от тикета с миграцией к остальным.

## Когда параллелить не надо

- **Критические тикеты** (`ORB-008` — разграничение доступа): делаются одним заходом,
  внимательно, без гонки.
- **Тикет, который трогает всё** (локализация, безопасность): он конфликтует со всеми,
  дешевле сделать его отдельной волной.
- **Волна из двух тикетов**: накладные расходы на деревья и приёмку больше выигрыша.
