# Мастер настройки: аккаунты, ключи, первая выкладка

Один раз, 20–30 минут. Делает заказчик — ключи вводит только он: разработка их не видит и
видеть не должна.

Порядок такой: аккаунты → секреты в GitHub → правила ветки → первая выкладка → проверка с
телефона. Каждый шаг заканчивается проверкой, по которой видно, что он сделан.

Пока шаги не пройдены, конвейер не падает: превью и выкладка честно пишут «нет ключа» и
ничего не делают.

---

## Шаг 1. Аккаунты

| Площадка | Что нужно | Стоимость |
|---|---|---|
| [GitHub](https://github.com) | уже есть: `yuldoshbek/Project_` | бесплатно |
| [Neon](https://neon.tech) | проект PostgreSQL 16, регион **Frankfurt** | от бесплатного; рабочий тариф ≈ $19 |
| [Vercel](https://vercel.com) | проект из этого репозитория, корневая папка **`backend`** | Hobby бесплатно, Pro $20 |
| [Netlify](https://netlify.com) | сайт, у заказчика уже есть | бесплатно |

**Регион Франкфурт обязателен** — это страна из перечня, куда закон разрешает выносить
данные граждан ([ADR-0028](adr/ADR-0028-hosting.md)). Регион задаётся при создании проекта
и потом не меняется.

**Про тариф Vercel.** Технически бесплатного хватает: расписание держит GitHub
([ADR-0035](adr/ADR-0035-scheduler-on-github-actions.md)), а не Vercel. Но условия Hobby
описывают личные некоммерческие проекты, а ORBITA — система государственного органа.
Решение о тарифе принимает заказчик; вопрос записан в
[открытых вопросах](OPEN-QUESTIONS.md).

### Ветки базы в Neon

В проекте Neon нужны две ветки:

| Ветка | Что в ней | Кто её видит |
|---|---|---|
| `production` | настоящие проекты, поручения, письма | рабочая система |
| `demo` | вымышленные данные | превью каждого PR |

`demo` создаётся кнопкой **New branch** от `production` **сразу, пока рабочая база пустая** —
тогда в демо гарантированно нет ни одной настоящей записи. Ветки превью создаются от `demo`
автоматически и удаляются при закрытии PR.

Роль и база внутри — `orbita` и `orbita`. Включите **Point-in-time restore** на 7 дней.

## Шаг 2. Секреты и переменные GitHub

Настройки репозитория → **Secrets and variables** → **Actions**.

### Секреты (Repository secrets)

| Имя | Где взять |
|---|---|
| `NEON_API_KEY` | Neon → Account settings → API keys |
| `NEON_PROJECT_ID` | Neon → Project settings → General |
| `VERCEL_TOKEN` | Vercel → Account settings → Tokens |
| `VERCEL_ORG_ID` | Vercel → Team settings → General (или `.vercel/project.json`) |
| `VERCEL_PROJECT_ID` | Vercel → Project settings → General |
| `NETLIFY_AUTH_TOKEN` | Netlify → User settings → Applications → New access token |
| `NETLIFY_SITE_ID` | Netlify → Site configuration → General → Site ID |
| `PREVIEW_SESSION_SECRET` | `python -c "import secrets; print(secrets.token_urlsafe(48))"` |
| `PREVIEW_JOBS_SECRET` | то же, другое значение |

### Секреты окружения production

Настройки репозитория → **Environments** → **New environment** → имя `production`. Внутри —
свои секреты:

| Имя | Что это |
|---|---|
| `PRODUCTION_DATABASE_URL` | строка подключения к ветке `production`, вид `postgresql+asyncpg://…` |
| `PRODUCTION_SESSION_SECRET` | новое случайное значение, не то же, что у превью |
| `PRODUCTION_JOBS_SECRET` | новое случайное значение |
| `PRODUCTION_URL` | адрес интерфейса, например `https://orbita.netlify.app` |
| `PRODUCTION_API_ORIGIN` | адрес API, например `https://orbita-api.vercel.app` |

Здесь же можно включить **Required reviewers** — тогда выкладка будет спрашивать
подтверждение перед запуском.

Отдельное окружение нужно затем, что ключи рабочей базы не должны быть доступны прогонам
на ветках: превью работает своими ключами и своей копией демо-данных.

### Переменные окружения площадок

В проекте Vercel (Settings → Environment Variables, окружение Production) задайте то же,
что лежит в секретах: `ORBITA_ENV=production`, `ORBITA_DATABASE_URL`,
`ORBITA_SESSION_SECRET`, `ORBITA_JOBS_SECRET`, `ORBITA_BASE_URL`, `ORBITA_FILE_STORAGE=blob`,
`ORBITA_BLOB_TOKEN`, `ORBITA_TIMEZONE=Asia/Tashkent`. Полный список с пояснениями —
[.env.example](../.env.example).

**Проверка шага:** вкладка Actions → «Копия базы» → Run workflow. Прогон должен создать
снимок и написать в сводке, сколько таблиц в схеме. Если написал «Копия не делается» —
секреты Neon не дошли.

## Шаг 3. Правила ветки main

Настройки → Rules → Rulesets → New ruleset → **Import a ruleset** →
[`.github/rulesets/main.json`](../.github/rulesets/main.json).

Что это даёт и почему именно так — [README правил](../.github/rulesets/README.md).

**Проверка шага:** попытка отправить коммит прямо в `main` получает отказ.

---

## Шаг 4. Первая выкладка

1. Actions → **«Выкладка»** → Run workflow → «выложить», галочка «Применять миграции».
2. Прогон применяет схему к рабочей базе, выкладывает API и интерфейс и проверяет, что
   ответил именно этот коммит.
3. Если проверка не прошла, площадки возвращаются на прежнюю версию сами, а в сводке
   написано, что делать.

Затем один раз загрузите справочники: Actions → «Задачи по расписанию» здесь не нужны,
справочники ставятся выкладкой (`alembic upgrade head` включает их наполнение).

---

## Шаг 5. Ссылки доступа

После первой выкладки откройте раздел **Управление** → «Ссылки доступа»: там две личные
ссылки — помощнику и руководителю. Ссылка руководителя отправляется ему один раз, он
открывает её на iPhone и добавляет на экран «Домой» — после этого приходят уведомления.

Ссылка равна доступу ко всей системе. Утекла — перевыпустите её в том же разделе, прежняя
перестаёт работать сразу.

**Проверка шага:** руководитель открывает ORBITA с телефона, видит Пульт и получает
утреннюю сводку на следующее утро в 08:30.

## Если что-то не так

| Признак | Что смотреть |
|---|---|
| В PR нет комментария с превью | Actions → «Превью» → сводка: там написано, какого ключа нет |
| Превью открылось, но данных нет | шаг «Схема и вымышленные данные» в том же прогоне |
| Выкладка упала на проверке | сводка прогона: площадки уже откачены, схема — нет |
| Утренняя сводка не пришла | Actions → «Задачи по расписанию»: расписание GitHub может опоздать на несколько минут |
| Ночная копия не сделана | в репозитории появится задача с ссылкой на прогон |

Порядок разбора и восстановления — [RUNBOOK](RUNBOOK.md).
