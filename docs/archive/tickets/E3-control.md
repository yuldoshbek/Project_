Этап 3 ТЗ. Результат — автоматизация рутинного контроля сроков; помощник перестаёт быть
«живым будильником» (ТЗ 2.4).

## ORB-036 — Инфраструктура фоновых задач ✅

- Оценка: M · Зависит от: ORB-002, ORB-003 · Блокирует: ORB-037, ORB-042, ORB-044
- Решения: ADR-0008

**Объём.** ARQ-воркер, расписания (cron-задания), контекст выполнения с системным актором
для аудита, повторные попытки с экспоненциальной задержкой, «мёртвая очередь», метрики.

**Критерии приёмки.**
- [x] Воркер поднимается командой (`make worker`) и **по-настоящему в CI** — в тестах, с настоящими `on_startup` и `on_shutdown`, на живой очереди. Про docker-compose — отступление ниже.
- [x] Падение задания не роняет воркер: проверено тем, что после упавшего задания воркер берёт следующее из той же очереди. Идентификатор прогона — это идентификатор задания ARQ, и он попадает и в лог, и в записи журнала изменений.
- [x] Повторный запуск на тех же данных не даёт побочных эффектов: второй прогон находит ноль работы.

**Отступление: воркера нет в docker-compose.** Образа приложения в проекте не существует —
`docker-compose.yml` поднимает только окружение (база, Redis, хранилище, почта), а backend
и frontend работают с хоста. Завести воркер контейнером означало бы собрать образ
приложения ради одного процесса и получить два разных способа запускать один и тот же код.
Воркер поднимается так же, как приложение: командой. **Контейнеризация приложения не
покрыта ни одним тикетом** — это вопрос выкладки, и его стоит завести отдельно.

**Отступление: своей «мёртвой очереди» таблицей нет.** У неё не было бы читателя.
Провалившееся задание остаётся в результатах ARQ и отдельной строкой `job_exhausted` в
логе. Хранилище заводится тогда, когда появится тот, кто его разбирает, — эскалация
(ORB-039) или центр уведомлений (ORB-037).

**Отступление: одно задание, а не набор заглушек.** Регламентных заданий пока нет:
напоминания приходят с ORB-038, эскалация — с ORB-039, снимки — с ORB-063, отчёты — с
ORB-044. Чтобы критерий про идемпотентность проверялся на настоящем задании, а не на
выдуманном, заведена очистка истёкших и давно отозванных токенов обновления: она реально
нужна (таблица растёт вечно), идемпотентна по устройству и никому не принадлежала.

**Найдено по дороге.** ARQ регистрирует задания по полному имени (`__qualname__`), и
задание, объявленное внутри функции, в очередь по короткому имени не поставить — воркер
молча отвечает «функция не найдена». И `Worker.close()` шлёт себе SIGUSR1, которого в
Windows нет: на машине разработчика воркер останавливают через Ctrl+C. Оба факта записаны
в коде, чтобы следующий не искал их заново.

**Как проверено, что тесты не проходят сами по себе.** Убиралось назначение действующего
лица заданию — краснел тест журнала; очистка начинала удалять всё подряд — краснели три
теста, включая идемпотентность.

## ORB-037 — Уведомления: модель и центр в интерфейсе

- Оценка: L · Зависит от: ORB-036, ORB-007 · Блокирует: ORB-038, ORB-040, ORB-054, ORB-070, ORB-071

**Список блокируемых поправлен 10.09.2026.** ORB-041 снят вместе с Telegram через SETA;
на уведомления теперь опираются собственный бот (ORB-054), напоминание о незаполненном
результате встречи (ORB-070) и подготовка к встрече (ORB-071).
- Требования ТЗ: 6.5 · Решения: ADR-0008

**Объём.** `notifications` с уникальным `dedup_key`, `notification_preferences`, порт
`NotificationChannel`, реализация `in_app`, разделение планирования и отправки, тихие часы.

**Критерии приёмки.**
- [ ] Двойной прогон планировщика не создаёт вторую запись (уникальный индекс по `dedup_key`).
- [ ] Пользователь настраивает каналы по типам событий; настройки соблюдаются.
- [ ] Уведомление вне рабочего окна откладывается, кроме приоритета «Срочно».
- [ ] Непрочитанные видны счётчиком, отмечаются прочитанными, ведут к источнику.

## ORB-039 — Эскалация нарушенных сроков ✂️ сокращён

> **Сокращён 08.09.2026.** Эскалировать некому: цепочки «куратор → помощник →
> руководитель» не существует. Остаётся напоминание помощнику и пометка в утренней
> сводке руководителю (ORB-055). Уровни 1–3 и таблица `escalations` не нужны.

- Оценка: L · Зависит от: ORB-038 · Требования ТЗ: 6.5, сценарий U4 · Решения: ADR-0008
- Открытый вопрос: Q4

**Критерии приёмки.**
- [ ] Уровни 1–3 (куратор, помощник, руководитель) срабатывают по заданным интервалам.
- [ ] Приоритет «Срочно» стартует эскалацию сразу после срока, остальные — с задержкой.
- [ ] Смена статуса или продление срока останавливает эскалацию.
- [ ] Один и тот же уровень по одной задаче и одному сроку не срабатывает дважды.
- [ ] История эскалаций видна в карточке задачи.

## ORB-046 — Провайдер личности SETA ⛔ снят

> **Снят 08.09.2026.** Ждать нечего: API SETA не существует, а пользователей
> двое и заводятся они сидами. Вернуть, когда у SETA появится API.

- Оценка: M · Зависит от: ORB-006 · Требования ТЗ: 3.4, 11.1 · Решения: ADR-0001
- Открытый вопрос: Q2 (тикет не начинается, пока нет ответа)

**Критерии приёмки.**
- [ ] Реализация `IdentityProvider` для SETA: сопоставление по `external_seta_id`, синхронизация профиля.
- [ ] Переключение провайдера — настройкой, без изменения роутеров и экранов.
- [ ] Пользователь, пришедший из SETA, получает роли по правилу сопоставления, а не вручную.
- [ ] Вход через Telegram Mini App работает с тем же набором прав, что и веб-вход.
