# Эксплуатация

Что делать с работающей системой: выложить, откатить, восстановить, перевыпустить ссылку,
переехать на свой сервер. Первичная настройка — [SETUP](SETUP.md).

Правило, которое дороже остальных: **в рабочем контуре живут настоящие поручения.** Любое
действие здесь начинается с вопроса «что произойдёт с данными, если я ошибусь».

## Где что находится

| Часть | Где | Как посмотреть |
|---|---|---|
| Интерфейс | Netlify | панель Netlify → Deploys |
| API | Vercel, регион Франкфурт | панель Vercel → Deployments, Logs |
| База | Neon, ветка `production` | панель Neon → Branches |
| Демо-база | Neon, ветка `demo` | оттуда ветвятся превью |
| Расписание | GitHub Actions → «Задачи по расписанию» | журнал прогонов |
| Копии | Neon, ветки `snapshot-ГГГГ-ММ-ДД` | панель Neon → Branches |

## Выложить

Actions → **«Выкладка»** → Run workflow → действие `deploy`. Галочку «Применять миграции»
снимают только тогда, когда выкладывается код без изменений схемы.

Что делает прогон: записывает текущую версию схемы (точка отката), применяет миграции,
выкладывает API и интерфейс, проверяет `/api/health` и сверяет коммит. Не сошлось —
площадки откатываются сами.

После выкладки откройте систему с телефона. Проверка конвейера говорит, что сервер отвечает;
что руководитель видит нужное — говорит только телефон.

## Откатить

Actions → «Выкладка» → действие `rollback`. Возвращает API и интерфейс на предыдущие рабочие
версии. С ноутбука то же самое: `bash scripts/netlify-restore-previous.sh` и
`npx vercel rollback`.

**База не откатывается вместе с кодом.** Отсюда правило: миграция не ломает прежний код —
поле не удаляется в том же блоке, в котором перестало использоваться. Если схему всё же
надо вернуть: `cd backend && uv run alembic downgrade -1` со строкой подключения рабочей
базы, и только после того, как убедились, что новых данных в новых полях нет.

## Копии и восстановление

Каждую ночь в 01:00 по Ташкенту создаётся снимок рабочей базы — ветка
`snapshot-ГГГГ-ММ-ДД`. Снимки старше недели удаляются. Прогон проверяет, что в снимке
есть схема и таблицы: копия без проверки — это надежда, а не копия.

Упала копия — в репозитории появляется задача со ссылкой на прогон.

**Восстановить на момент времени** (потеря данных, ошибочное удаление):

1. Neon → Branches → `production` → **Restore** → указать время.
2. Neon восстанавливает ветку на состояние того момента; глубина — 7 дней.
3. Проверить данные и сообщить заказчику, что именно потерялось за интервал.

**Посмотреть данные из снимка, ничего не меняя:** `scripts/neon.sh branch-uri snapshot-ГГГГ-ММ-ДД`
и подключиться этим адресом. Снимок только читают — работать в нём нельзя, это копия.

## Задачи по расписанию

| Задача | Когда | Что делает |
|---|---|---|
| `morning-summary` | каждые 10 минут с 06:00 до 11:50 Ташкент | с порога «Утренняя сводка» (Управление → «Пороги») отправляет сводку руководителю — один раз за день, до первой доставки |
| `daily-snapshot` | 23:50 Ташкент | снимок состояния за день для графиков |
| `deadline-check` | 09:00–19:00 пн–сб, раз в час | считает сроки и признак жизни |

Запустить вручную: Actions → «Задачи по расписанию» → Run workflow → выбрать задачу. На
машине разработчика — `make job n=morning-summary`.

Задачи идемпотентны: повторный запуск в тот же день не отправит вторую сводку. Пропущенный
запуск задача догоняет сама.

Итог прогона сводки — в сводке прогона Actions. `done` — ушла хотя бы на одно устройство;
только это занимает день. `not_due` с причиной: `not_yet` — порог ещё не наступил,
`no_device` — у руководителя нет живой подписки, `not_configured` — нет ключа
`ORBITA_VAPID_PRIVATE_KEY`. День при этом свободен: включил руководитель уведомления в 09:00 —
сводка уйдёт в 09:10. Служба доставки не приняла ни одного сообщения — прогон красный (ответ
503), день свободен, следующий прогон через 10 минут попробует снова. Порог принимается с
06:00 до 11:00: после него остаётся шесть вызовов расписания — 50 минут, до последнего
запуска в 11:50.

Расписание GitHub может опоздать на несколько минут — это записано в ТЗ и принято
заказчиком. Опоздало на час и больше — смотрите, не кончились ли минуты Actions.

## Ссылки доступа

Раздел **Управление** → «Ссылки доступа». Перевыпуск нужен, когда ссылка могла утечь:
переслали в чужой чат, потеряли телефон, сменился помощник. Прежняя ссылка перестаёт
работать сразу, новая отправляется человеку одним сообщением.

Журнал входов там же: видно, когда и с какого устройства открывали.

Перевыпуск ссылки руководителя удаляет и подписки его устройств: утерянный телефон перестаёт
получать уведомления вместе с доступом. После входа по новой ссылке руководитель открывает
Пульт → «Сводка»: устройство, сохранившее подписку, восстановит её само («Включены»), иначе
там будет кнопка «Включить уведомления».

## Уведомления

Их два (ТЗ 8): утренняя сводка и «ждёт вашего решения» — сразу, как помощник записал вопрос.
Канал — Web Push ([ADR-0036](adr/ADR-0036-web-push.md)); ключ — `ORBITA_VAPID_PRIVATE_KEY` в
Vercel, его вводит заказчик ([SETUP](SETUP.md)). Каждое уведомление — запись в
`notifications`, `sent_at` — когда служба доставки его приняла. Подписка, от которой служба
отказалась навсегда (404/410), помечается `gone_at` и больше не получает сообщений; тот же
адрес браузер не сможет записать снова — вкладка «Сводка» покажет кнопку «Включить
уведомления», и касание оформит новую подписку. Пуш о вопросе не повторяется: не ушёл —
вопрос придёт в утренней сводке. Ключ добавлен или сменён в Vercel — нужна «Выкладка»:
переменные применяются только к новой выкладке.

## Превью

Превью живёт на своей ветке демо-базы и удаляется вместе с закрытием PR. Осталась лишняя
ветка — `scripts/neon.sh branch-delete preview/pr-N`.

Реальных данных в превью нет и быть не может: ветка создаётся от `demo`. Если в превью
увидели настоящую фамилию или номер поручения — это происшествие: остановите превью,
сообщите заказчику, найдите, откуда данные попали в демо.

## Переезд на сервер агентства

Сборка — `deploy/server/` ([ADR-0028](adr/ADR-0028-hosting.md)): четыре контейнера из того
же кода, что в облаке. **PostgreSQL** наружу не выставлена. **API** при каждом старте
накатывает миграции и справочники. **Caddy** отдаёт интерфейс, проксирует `/api` и
закрывает `/internal`. **cron** вызывает задачи по тому же расписанию, что
`.github/workflows/jobs.yml`. Файлы лежат на диске сервера, в томе `uploads`.

Проверено 05.10.2026 на машине разработки: образы собраны, стек поднят на копии базы,
вход по ссылке, Пульт, Идеи, Календарь, загрузка и просмотр файла, задача по расписанию —
работают (`docs/reports/BLOCK-3.md`).

**Что нужно на сервере:** Docker с Compose v2, доменное имя, указывающее на сервер, открытые
80 и 443. Без HTTPS вход не работает: cookie сессии `__Host-` браузер принимает только по
защищённому соединению.

1. **Код и окружение.**

   ```bash
   git clone https://github.com/yuldoshbek/Project_.git orbita && cd orbita/deploy/server
   cp .env.example .env
   ```

   В `.env` — адрес (`ORBITA_BASE_URL`, `ORBITA_SITE_ADDRESS`) и три случайных значения:
   пароль базы, секрет сессий (не короче 32), секрет задач (не короче 16). Генерировать
   на сервере: `python3 -c "import secrets; print(secrets.token_urlsafe(48))"`. Файл `.env`
   в `.gitignore` — в репозиторий он не попадает.

2. **База и копия данных.** Сначала одна база:

   ```bash
   docker compose up -d postgres
   ```

   Копия из облака — снимок Neon (раздел «Копии и восстановление»): адрес ветки даёт
   `scripts/neon.sh branch-uri snapshot-ГГГГ-ММ-ДД`, дамп —
   `pg_dump --format=custom --no-owner "$URI" > backups/orbita.dump`. Восстановить:

   ```bash
   docker compose exec -T postgres pg_restore -U orbita -d orbita --no-owner --no-privileges /backups/orbita.dump
   ```

3. **Файлы — вместе с базой.** Запись о версии презентации без самого файла откроется
   отказом «файла нет в хранилище» (проверено). Файлы облачного хранилища (V44) кладутся в
   том `uploads` с теми же ключами, что в базе (`stored_files.storage_key`), например
   `rclone copy облако:orbita /var/lib/docker/volumes/orbita-server_uploads/_data`.

4. **Запуск.**

   ```bash
   docker compose up -d --build
   docker compose ps
   ```

   Всё `healthy`, журнал API кончается строкой `Uvicorn running`. Если путь к каталогу
   содержит не латиницу, сборка падает на `x-docker-expose-session-sharedkey` — собирать с
   `COMPOSE_BAKE=false` по одному образу: `docker compose build api`, затем `web` и `cron`.

5. **Ссылки доступа** — тем же средством, что в облаке (раздел «Ссылки доступа»):

   ```bash
   docker compose exec api python -m app.access_cli assistant --base-url https://orbita.agency.uz
   ```

   Ссылка выводится один раз; её не публикуют и не пересылают в общих чатах.

6. **Расписание и копии.** Задачи вызывает контейнер `cron`; ручной запуск —
   `docker compose exec cron run-job deadline-check`. Ночная копия базы на сервере — задача
   cron хоста:

   ```bash
   0 1 * * * cd /srv/orbita/deploy/server && docker compose exec -T postgres pg_dump -U orbita -Fc orbita > backups/orbita-$(date +\%F).dump
   ```

7. **Обновление** — новая версия из `main`:

   ```bash
   git pull && docker compose up -d --build
   ```

   Миграции применятся при старте API. Откат — `git checkout <прежний коммит>` и тот же
   `up -d --build`; миграции вниз — только по решению, после копии базы.

## Что делать нельзя

- Менять схему рабочей базы руками. Только миграцией через выкладку.
- Править данные запросом в базу вместо действия в интерфейсе: изменение не попадёт в
  журнал, и потом никто не поймёт, кто и зачем это сделал.
- Выкладывать в рабочий контур без приёмки заказчиком на превью.
- Выгружать дамп рабочей базы в артефакты прогона, в чат или на почту.
- Ветвить превью от рабочей базы.
