## ORB-010 — Справочники ✅

- Оценка: S · Зависит от: ORB-004 · Блокирует: ORB-011, ORB-014, ORB-035
- Требования ТЗ: 7, 6.8 · **Статус: закрыт.** Ветка `orb-010-dictionaries`

**Объём.** Модели `directions`, `priorities`, `project_statuses`, `settings`,
`organizations`. Сиды строго из раздела 7 ТЗ на трёх локалях. Чтение через API.

**Критерии приёмки.**
- [x] Все значения из ТЗ 7 присутствуют после `make seed`, названия заполнены на ru,
      uz-Cyrl, uz-Latn — проверено тестом по каждому справочнику отдельно и вручную
      на живом сервере.
- [x] Справочные значения не захардкожены, кроме технических кодов. Разделение
      описано в `app/domain/dictionaries.py`: код принадлежит коду, название,
      порядок, цвет и видимость — данным.
- [x] Деактивация значения не ломает существующие записи, но скрывает его из форм:
      параметр `active_only` разделяет эти два случая.

**Разрешённое противоречие ТЗ.** Раздел 6.8 требует менять справочники без
разработчика, разделы 6.4 и 6.5 — чтобы система понимала смысл статусов. Полностью
редактируемый справочник этого не даёт: смысл нового значения системе неоткуда взять.
Переименовать «На контроле руководителя» можно из интерфейса и на всех трёх
письменностях; завести седьмой статус проекта — нельзя. Ограничение названо вслух.

**Что нашлось по дороге.**
1. **Время в схеме было наивным.** `Mapped[datetime]` без явного
   `DateTime(timezone=True)` даёт `timestamp without time zone` — прямое нарушение
   инварианта CLAUDE.md, невидимое ни в модели, ни на ревью. Исправлено в основании
   модели; добавлена проверка всей схемы `test_no_naive_timestamp_columns`.
2. **Подключение по имени `localhost` стоило 2,1 секунды вместо 70 миллисекунд.**
   Windows резолвит `localhost` сначала в `::1`, а контейнеры слушают только IPv4.
   Платило бы каждое соединение приложения, а не только тесты; списали бы на «система
   тормозит». Везде проставлен `127.0.0.1`; набор тестов ускорился с 55 секунд до 4,7.
3. **`alembic.ini` пришлось перевести на латиницу** (обнаружено в ORB-004) — но
   выяснилось, что кириллица ломает и имена файлов миграций: `%(slug)s` убран из
   шаблона, описание живёт в docstring ревизии.

**Решения сверх карточки.**
- Справочник статусов задачи заведён наравне с остальными — интерфейсу нужны их
  локализованные названия. «Просрочена» в него не входит (ADR-0004), и это
  проверяется тестом.
- Порог жёлтой зоны для «Срочно» хранится значением `warn_days_override = 0`, а не
  условием в коде: по ADR-0005 помощник должен уметь его поправить.
- Сиды **не перезаписывают** существующие строки. Иначе обновление системы затирало
  бы правки помощника, и редактируемый справочник стал бы декорацией.
- Заложена тестовая инфраструктура для всех следующих тикетов: схема накатывается и
  наполняется один раз за прогон, каждый тест работает во внешней транзакции, которая
  откатывается.

## ORB-011 — Проекты: модель и CRUD ✅

- Оценка: L · Зависит от: **ORB-009**, ORB-053, ORB-010 · Блокирует: ORB-012, ORB-013, ORB-018, ORB-019, ORB-025, ORB-029
- Требования ТЗ: 6.1 · Решения: ADR-0011, ADR-0007, ADR-0005

**Объём.** Таблица `projects` со всеми полями из SPEC 1.3, генерация `code`, CRUD API,
фильтрация и сортировка, вычисление светофора и `progress_pct` в режиме `auto`,
валидация: `due_on` не раньше `started_on`, причина обязательна для статусов
«Приостановлен» и «Отменён», мини-проект не требует вех.

**Критерии приёмки.**
- [x] Создание, чтение, изменение и удаление проекта доступны помощнику; руководителю
      на запись доступно только решение по проекту (ORB-062, ADR-0011).
- [x] Смена статуса на «Приостановлен» без причины отклоняется с понятной ошибкой —
      и при создании, и при изменении.
- [x] Светофор в ответе совпадает с правилом ADR-0005 (табличный тест на граничных датах).
- [ ] `progress_pct` в режиме `auto` пересчитывается при смене статуса задачи —
      **перенесён в ORB-014**: задач ещё нет, пересчитывать не от чего. Сам расчёт
      (`auto_progress`) написан и покрыт таблицей здесь; в ORB-014 остаётся подключить
      его к смене статуса задачи.
- [x] Каждое изменение попало в `audit_log`; у проекта с грифом — без содержимого.

**Чего нет в таблице намеренно.** CLAUDE.md запрещает поля «на будущее», и пять полей из
SPEC 1.3 заводятся тикетами, которым они нужны: `template_id` — ORB-023, `archived_at` —
ORB-025, `impediment` и `impediment_updated_at` — ORB-073, `search_vector` — ORB-033.
Добавление столбца в заполненную таблицу дешевле, чем пять лет пустых полей, о назначении
которых никто не помнит.

**Проверки стоят дважды: в домене и в базе.** Домен отдаёт понятную пользователю ошибку,
база ловит обход домена — миграцию данных, ручной SQL, будущий импорт. Проверка, живущая
только в приложении, защищает ровно до первого скрипта.

**Что вскрылось по дороге.**

`date.today()` брал часовой пояс машины. Все сроки наступают по `Asia/Tashkent`, и в два
часа ночи по Ташкенту в UTC ещё вчерашний день: проект со вчерашним сроком выглядел бы не
просроченным. Ошибка проявляется ночью, у одного пользователя из двух, и в отчёте её не
видно. «Сегодня» стало входным значением, а не окружающим фактом (`app.domain.clock`).

Оттуда же — зависимость `tzdata`. Системной базы часовых поясов нет ни в Windows, ни в
облегчённых образах Linux: приложение падало бы при первом расчёте светофора, на машине,
где его никто не проверял.

Подробность ошибки вытесняла сообщение: пользователь получал «начало 01.06, срок 01.05»
без объяснения, что не так. Теперь они складываются — правка в `app/api/errors.py`
касается всех ошибок домена, а не только проектов.

**Как проверено, что тесты не проходят сами по себе.** Граница просрочки сдвигалась на
день — краснели два теста светофора; отключалась проверка причины — краснели оба теста
приостановки.

## ORB-012 — Вехи проекта ✅

- Оценка: S · Зависит от: ORB-011 · Блокирует: ORB-026, ORB-031 · Требования ТЗ: 6.1

**Критерии приёмки.**
- [x] Веха создаётся, переупорядочивается, помечается выполненной. Порядок присылается целиком: частичная перестановка оставляет список в неопределённом состоянии, если два запроса пришли подряд.
- [x] Веха с прошедшим сроком и статусом `planned` автоматически считается `missed` в выдаче — и **только в выдаче**: в базе живут два значения из трёх.
- [x] Для мини-проекта вехи необязательны — но не запрещены: запрет заставил бы менять вид проекта ради одной контрольной точки. Скрытие раздела — решение интерфейса, ORB-018.

**Отступление от SPEC 1.5.** Там у вехи перечислены три значения статуса,
`planned | done | missed`. Хранятся два: `missed` вычисляется на выдаче по той же
причине, по которой не хранится просрочка задачи (ADR-0004) — хранимое значение теряет
исходное, а фоновое задание, переписывающее статусы по ночам, отстаёт ровно на сутки.
Ровно те сутки, когда на веху смотрят. Ограничение уровня строки закрепляет это в базе:
без него первый же скрипт импорта запишет туда третье значение.

**Как проверено, что тесты не проходят сами по себе.** Отключалось вычисление
пропущенности — краснели два теста; снималось ограничение в базе — краснел третий.

## ORB-013 — Организации-партнёры ✅

- Оценка: S · Зависит от: ORB-011 · Требования ТЗ: 6.1, сценарий U6

**Критерии приёмки.**
- [x] К проекту привязывается несколько организаций с указанием роли. Одна организация — одна связь: две записи об одном партнёре не «две роли», а ошибка ввода, и её ловит база, а не проверка перед вставкой.
- [x] Справочник организаций поддерживает международных партнёров (страна, краткое имя) — заведено в ORB-010, здесь проверено на зарубежном партнёре.
- [x] Поиск по названию организации находит связанные проекты: фильтры `organization_id` и `partner_search` на `GET /projects`. Ищет и по полному названию, и по краткому имени — вопрос сценария U6 звучит как «что у нас с ЕКА», а не как идентификатор.

**Роль остаётся текстом**, как в SPEC 1.3. Если по ролям понадобится считать, она станет
справочником — свободный ввод к тому времени даст три написания одного слова. Пока по ним
не считают, справочник был бы вводом ради формы.

**Удаление организации из справочника запрещено, пока связь существует** (`RESTRICT`, а не
каскад): организация уходит, а история, с кем шёл проект, остаётся.

**Найденная по дороге ошибка в своём же коде.** Явное имя у `UniqueConstraint` вытесняет
соглашение об именовании целиком — не так, как у `CheckConstraint`, где соглашение имя
оборачивает. Ограничение оказалось единственным в схеме, названным не по правилу, а откат
миграции искал бы его по чужому имени. Имя отдано соглашению.

**Как проверено, что тесты не проходят сами по себе.** Отключался поиск по краткому имени —
краснел тест сценария U6; снималась уникальность связи — краснел тест повторной привязки.

## ORB-014 — Задачи: модель и CRUD ✅

- Оценка: L · Зависит от: ORB-053, ORB-010, ORB-011 · Блокирует: ORB-015..ORB-024, ORB-029, ORB-038
- Требования ТЗ: 6.2, 7 · Решения: ADR-0004

**Объём.** Таблица `tasks` из SPEC 1.4, генерация `code`, CRUD, фильтры (исполнитель,
куратор, проект, направление, приоритет, статус, срок), сортировки, вычисляемые
`is_overdue` и `days_overdue`, задача вне проекта, признак `is_control`.

**Критерии приёмки.**
- [x] Задача создаётся как внутри проекта, так и вне его.
- [x] `is_overdue` считается по ADR-0004; смена статуса на «Выполнена» снимает просрочку.
- [x] Фильтр «просроченные» использует индекс `(status, due_at)` — существование индекса и получение плана проверены тестом; **выбор** плана планировщиком на боевом объёме — ORB-051 (см. отступление ниже).
- [x] Исполнитель задачи — сотрудник агентства из справочника `people`, а не
      пользователь системы (ADR-0011): проверено и тем, что сотрудник принимается, и
      тем, что идентификатор пользователя база отвергает.
- [x] Переходы статусов валидируются: из `done` нельзя вернуться в `new` минуя `in_progress`.
- [x] `progress_pct` проекта в режиме `auto` пересчитывается при смене статуса задачи.
      Перенесено из ORB-011 10.09.2026 и здесь закрыто: пересчитываются оба проекта при
      переносе задачи, ручной режим не затирается, удаление последней задачи возвращает
      проект к нулю.

**Чего нет в таблице намеренно.** Шесть полей из SPEC 1.4 заводят тикеты, которым они
нужны: `milestone_id` — ORB-012, `recurrence_rule` и `recurrence_parent_id` — ORB-042,
`kanban_order` — ORB-021, `source_meeting_id` — ORB-069, `search_vector` — ORB-033
(CLAUDE.md: никаких полей «на будущее»).

**Отступление: запрета на закрытие поручения нет.** По ADR-0015 ход исполнения задачи с
`is_control` принадлежит SETA, и попытка изменить статус должна давать `409`. Признак
заведён, запрет — нет, и это осознанно: обмена ещё не существует, а с запретом поручения
станут незакрываемыми — закрывать их станет некому. Запрет вводит **ORB-076**, вместе с
обменом.

**Отступление: что именно проверено про индекс.** Критерий говорил «подтверждено
`EXPLAIN`». План снимается на почти пустой таблице, и планировщик там честно предпочтёт
последовательный просмотр — требовать от него выбора индекса значило бы проверять не
систему, а размер тестовых данных. Проверено то, что проверяемо сейчас: индекс существует,
покрывает `(status, due_at)` в этом порядке, и план запроса строится. Замер выбора плана
на боевом объёме — ORB-051.

**Правило просрочки живёт на двух языках** — в домене и в SQL, — и это неизбежно: фильтр
«просроченные» самый частый на дашборде, а считать его в памяти значит обходить все задачи
при каждом взгляде на экран. Записано по одному разу на язык, и совпадение проверяется
сверкой: отфильтрованный базой список сравнивается с признаком, посчитанным в Python.

**Как проверено, что тесты не проходят сами по себе.** Разрешался переход `done → new` —
краснели два теста; отключался пересчёт процента — краснели ещё два.

## ORB-015 — Чек-листы и теги задач 🔨 почти

- Оценка: S · Зависит от: ORB-014 · Требования ТЗ: 6.2

**Критерии приёмки.**
- [x] Пункты чек-листа добавляются, отмечаются, переупорядочиваются. Порядок приходит
      списком целиком, а не сдвигом по одной позиции, и присланный состав обязан совпасть
      с имеющимся — иначе перетаскивание, начатое до удаления пункта, тихо оставило бы
      часть списка с прежним порядком. То же решение и по той же причине, что у вех
      (ORB-012).
- [x] Прогресс чек-листа виден **в списке задач** — числом «3/5» и полосой, и приходит
      вместе с задачей одним запросом на всю выборку, а не запросом на строку.
      **В карточке задачи — только в ответе API, экрана пока нет:** карточка задачи это
      ORB-022, который на ORB-015 и так объявлен зависимым. Строить её здесь значило бы
      делать чужой тикет; поле `checklist_done/total/percent` её дожидается готовым.
- [x] Теги переиспользуются: ввод существующего тега не создаёт дубликат. «ДЗЗ», «дзз»,
      «ДЗЗ » и «ДЗЗ  Ташкент» с двойным пробелом — один тег. Уникальность держит тип
      столбца (`citext`), а не проверка в коде: проверку обходит первый же импорт.
      Найденный тег возвращается **со своим написанием** — переписать его значило бы
      поменять надпись у всех уже помеченных задач из-за одного ввода в одной карточке.

**Прогресс не хранится.** Считается из самих пунктов, как просрочка задачи (ADR-0004) и
пропущенность вехи. Хранимое число расходится с пунктами молча, и спорить с ним нечем: оно
и есть источник. Отдельно: **пустой чек-лист не имеет прогресса** — не ноль процентов.
Ноль означает «взялись и не сделали», на экране это тревожный знак, а задача без чек-листа
не сообщает ни о чём.

**Здесь же исправлена причина, а не очередное следствие.** Живая проверка показала два
отказа: отметка пункта отвечала «Пункт чек-листа не найден» для пункта, созданного
мгновение назад (три раза из четырёх), а повторный ввод тега другим регистром давал 500.
Обе — от того же, что при ORB-020 съедало каждую вторую задачу: **ответ уходил клиенту
раньше, чем закрывалась транзакция**, и следующий запрос не видел предыдущей записи.

Первое и третье лечатся повтором. Второе не лечится ничем: нельзя «повторить» ответ «не
найдено» о том, что человек видит на экране. Поэтому граница транзакции перенесена туда,
где ей место, — `app/api/transaction.py`: класс маршрута фиксирует транзакцию после того,
как обработчик закончил, но **до** того, как ответ ушёл. CLAUDE.md и так помещает
транзакции в слой сценариев; теперь это правда, а не намерение.

Закреплено тремя способами: тестом на порядок вызовов (фиксация после обработчика, и её
нет на пути с отказом), соглашением «каждый роутер заведён через `transactional_router`»
с обходом пакета, и живой проверкой — все три болезни перестали воспроизводиться.

**Измерено, а не предположено.** На стенде: 3/5, 3/3, 1/2 и прочерк там, где чек-листа
нет; доли полосы 60 %, 100 %, 50 % при ширине 48 px. Словарь тегов после ввода «ДЗЗ» и
«дзз» с разных задач содержит одну запись. Выгрузка несёт колонку «Чек-лист» со значением
«3 из 5» и пустой ячейкой у задач без чек-листа; задача закрытого проекта не уходит в файл
вместе со своим чек-листом.

## ORB-016 — Комментарии 🔨 почти

- Оценка: M · Зависит от: ORB-011, ORB-014 · Блокирует: ORB-033 · Требования ТЗ: 6.1, 6.2

**Критерии приёмки.**
- [x] Комментарий добавляется к проекту и к задаче, редактируется автором, мягко удаляется.
      Одна таблица на оба вида записей: реплика устроена одинаково, различается только то,
      к чему она относится. **Удалённая реплика остаётся в ленте следом — без текста, с
      автором и временем.** Исчезни она совсем, мягкое удаление не отличалось бы от
      обычного, а пропуск в переписке делает соседние реплики непонятными: читатель не
      может отличить «здесь ничего не было» от «здесь было и убрали».
- [x] Упоминание сотрудника порождает уведомление. **Извещается второй пользователь, а не
      упомянутый** — и это допущение, а не решение: сотрудники в систему не входят (Q5
      закрыт), показать им внутри неё нечего. Записан вопрос **Q24**; кого упомянули,
      сохраняется в уведомлении, чтобы доставку можно было изменить, не потеряв данные.
      Повтор закрыт ключом `dedup_key`: правка запятой в реплике второго уведомления не
      порождает (инвариант 6).
- [x] Лента комментариев и история изменений — **один поток** (`GET /timeline`). В ответе
      API; **на экране пока нигде**: лента живёт на карточке проекта (ORB-018) и карточке
      задачи (ORB-022), а их нет. Строить карточку здесь значило бы делать чужой тикет.

**Однофамильцы.** «@Каримов» при двух Каримовых не разбирается ни в кого: предупредить не
того человека о не его проекте хуже, чем не предупредить никого — первое выглядит как
утечка, второе как забывчивость автора, который видит свой текст и может дописать имя.
При этом «Каримов» и «Каримова» — разные слова и разные люди; иначе правило «молчать,
когда неясно» выродилось бы в «молчать почти всегда».

**Текст реплики в журнал изменений не пишется.** Журналу нужен ответ «кто и когда», а «что
написано» лежит в самой реплике и никуда не девается — удаление мягкое. Второе место
хранения того же текста означало бы, что комментарий к проекту с грифом расползается по
таблицам, из которых его уже не вычистить (ADR-0007).

**Что нашлось только вживую.** Проверки проходили, а лента читалась вдвое хуже: **каждая
реплика стояла в потоке дважды** — своим текстом и строкой журнала «[created] body,
author_id, entity_id, entity_type». Появление реплики из журнала убрано; правка и удаление
остались — «написал» и «поправил написанное» разные события. Заодно вскрылось, что по
событию изменения нельзя было понять, к чему оно относится: «[updated] body» одинаково
выглядело у задачи и у реплики. Добавлено поле `subject`.

**Удаление обсуждения.** Комментарии уходят вместе с записью вручную: `entity_id`
указывает то на проекты, то на задачи, и внешним ключом такое не выразить. Отдельно
закрыт случай, где реплики осели бы навсегда: удаление проекта уносит его задачи каскадом,
а их обсуждения — нет, поэтому они убираются до удаления проекта.

## ORB-020 — Экран «База задач»: таблица ✅

- Оценка: L · Зависит от: ORB-005, ORB-014 · Блокирует: ORB-021, ORB-024 · Требования ТЗ: 6.2, 9

**Критерии приёмки.**
- [x] Таблица заменяет Excel: сортировка по любой колонке, выбор видимых колонок, экспорт
      выборки. Сортировка и набор колонок живут в адресе — ссылкой делятся вместе с видом,
      а не только с фильтром. **Выгрузку собирает сервер, а не браузер** (`GET
      /tasks/export.csv`): файл — точка выхода наружу, и проверка грифа стоит внутри
      функции выдачи (`list_for_export`, ADR-0007). Собери файл из строк на странице — и
      проверка оказалась бы на клиенте, то есть нигде.
- [x] Все фильтры из ТЗ 6.2 доступны и комбинируются: название, статус, приоритет,
      исполнитель, куратор проекта, направление, только просроченные, только поручения.
      **Фильтры по исполнителю и куратору потребовали нового эндпоинта** `GET /people`:
      справочник сотрудников лежал в базе с ORB-007, но наружу его не отдавал никто, и
      наполнить оба выпадающих списка было нечем. Ведение сотрудников — по-прежнему
      ORB-045; здесь только чтение.
- [x] Просроченные задачи визуально выделены (ADR-0004), а не вынесены в отдельный статус:
      строка получает цвет и пометку «просрочена на N дней», а колонка статуса остаётся
      своей — задача бывает «в работе» и просроченной одновременно.

**Что нашлось только вживую.** Ни одно из пяти не было видно ни в коде, ни в тестах.

1. **Каждая вторая задача, заведённая подряд, пропадала.** Ответ «создано» доходит до
   клиента раньше, чем закрывается транзакция, и следующий запрос читает максимум номера,
   не видя предыдущей записи. Уникальность номера превращала это в `IntegrityError` →
   «Внутренняя ошибка» и потерю задачи. `codes.py` обещал «честную ошибку вместо двух
   записей с одним номером», но честной ошибки никто не делал. Заведён
   `codes.add_with_code`: пересчёт номера и повтор внутри точки сохранения, исчерпание
   попыток — отказ 409 словами. Относится к ORB-014, исправлено здесь: это потеря данных
   на главном пути ввода.
2. **Ссылка `<a download>` уходила без токена.** Браузер не прикладывает `Authorization` к
   переходу по ссылке, а класть токен в адрес нельзя — адрес попадает в журналы и в
   пересланную ссылку. Выгрузка стала действием: запрос тем же клиентом, файл из ответа.
3. **Срок на экране показывался по UTC.** `due_at.slice(0, 10)` — срок в 02:00 по Ташкенту
   хранится как 21:00 UTC предыдущего дня, и на экране стояло вчерашнее число (инвариант
   5). Заведён `shared/time.ts`, показ через `Intl` в `Asia/Tashkent`.
4. **Выгрузка отдавала идентификаторы.** В колонках «Исполнитель» и «Проект» стояли UUID,
   в статусе — код `in_progress`, в сроке — UTC. Файл открывают в Excel, где подставить
   имя уже некому. Теперь имена, названия и «30.08.2026 17:00».
5. **Класс ячейки `title` совпал с классом заголовка страницы** — в таблицу протекал его
   кегль, названия набирались в полтора раза крупнее, каждая строка переносилась на две, и
   на экран влезало вдвое меньше задач. Классы ячеек разведены (`cellTitle` и прочие).
   Заодно на телефоне заливка просроченной карточки не показывалась вовсе: правило
   `.overdue` слабее, чем `.table tr`, и специфичность решала молча.

**Что ещё оказалось непроверенным.** Ни один тест не заметил бы пропажи заголовка
`Authorization`: обвязка тестов не вызывала `configureApi`, и все запросы и так уходили
без токена. Исправлено в `testing/WithSession.tsx`. И ни один маршрут не был проверен на
то, что он вообще требует сессию, — новый роутер мог открыть данные всем незаметно.
Заведена сквозная проверка обходом схемы API (`test_roles.py`), она растёт вместе с
системой сама.

**Измерено, а не предположено.** 8 задач на стенде, из них одна в проекте с грифом
`restricted` и одна вне проектов. На экране 8, в файле 7: закрытая не ушла, беспроектная
ушла. Проверено и вживую, и тестом.
