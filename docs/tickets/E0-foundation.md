## ORB-002 — Локальное окружение: PostgreSQL, Redis, MinIO, почта ✅

- Эпик: E0 · Оценка: S · Зависит от: ORB-001 · Блокирует: ORB-003, ORB-036, ORB-047
- **Статус: закрыт.** Ветка `orb-002-local-environment`

**Цель.** `make up` — и есть всё, что нужно для разработки и тестов.

**Объём.** `docker-compose.yml`: postgres:16 (с `pg_trgm`, `unaccent`, `citext`),
redis:7, minio, почтовая заглушка. Тома, healthcheck, порты из `.env`. Отдельная тестовая БД.

**Критерии приёмки.**
- [x] `make up` поднимает всё и проходит healthcheck — `docker compose up -d --wait`
      возвращает 0, все четыре сервиса в состоянии `healthy`, бакет вложений создан.
- [x] Тесты используют отдельную БД и не затирают данные разработки — база `orbita_test`
      создаётся init-скриптом; приспособление `guard_separate_database` останавливает
      прогон, если имена баз совпали, и срабатывает до любого подключения.
- [x] В README описано, как поднять окружение с нуля на Windows и Linux — с таблицей
      адресов сервисов и объяснением, почему порты смещены.

**Отступления от карточки и почему.**
- **Mailpit вместо MailHog.** MailHog не поддерживается с 2020 года; Mailpit — прямой
  преемник с теми же портами (SMTP 1025, интерфейс 8025).
- **Порты хоста смещены** на 55432, 56379, 59000/59001, 51025/58025 и привязаны к
  `127.0.0.1`. Обнаружено при проверке: на машине разработчика уже работал нативный
  PostgreSQL, он занял IPv4:5432, контейнер сел только на IPv6, и клиент молча уходил в
  чужую базу — соединение рвалось без единой записи в логах контейнера. Со стандартным
  портом первый критерий приёмки невыполним на такой машине.
- **`minio-init` вынесен в профиль compose.** `up --wait` считает любой завершившийся
  контейнер отказом, даже с нулевым кодом; разовая задача запускается отдельной командой,
  которая заодно отдаёт честный код возврата.
- **В CI добавлены сервис-контейнеры** PostgreSQL и Redis: тесты с маркером `infra` идут
  против настоящих сервисов, подменять их заглушками — значит проверять заглушки.

## ORB-003 — Каркас FastAPI ✅

- Эпик: E0 · Оценка: M · Зависит от: ORB-001, ORB-002 · Блокирует: ORB-004, ORB-006
- **Статус: закрыт.** Ветка `orb-003-fastapi-skeleton`

**Цель.** Скелет приложения со сквозными механизмами, чтобы фича-тикеты не изобретали их заново.

**Объём.**
- Слои `api / services / domain / repos / adapters / workers`, DI через зависимости FastAPI.
- Настройки на pydantic-settings, чтение из окружения, падение при отсутствии обязательных.
- Единый формат ошибок RFC 9457, обработчики исключений домена.
- Структурные логи (structlog) с `request_id`, middleware его проставляет и возвращает в заголовке.
- `GET /health` (живость) и `GET /ready` (БД и Redis доступны).
- Асинхронная сессия SQLAlchemy, транзакция на запрос, `search_path` в схему `orbita`.

**Критерии приёмки.**
- [x] `GET /health` отвечает 200, `GET /ready` — 503 при выключенной БД. Проверено
      тестами и вручную на запущенном сервере; `/ready` называет, что именно не
      отвечает, и не зависает: у каждой проверки свой предел ожидания.
- [x] Необработанное исключение возвращает RFC 9457 без стектрейса наружу и с ним в
      логе. Тест проверяет отсутствие в ответе текста исключения, имени класса и слова
      Traceback — не только код 500.
- [x] `request_id` из заголовка запроса протаскивается в лог и в ответ. Проверено на
      живом сервере: заголовок клиента `check-log` виден и в ответе, и в записи
      access-лога uvicorn.

**Что нашли тесты (дефекты в коде, не в тестах).**
1. **Логгер падал на каждом вызове.** `PrintLoggerFactory` не даёт логгеру имени, а
   `add_logger_name` его требует. Последствие было куда серьёзнее кривого лога: обработчик
   ошибки не мог записать событие, исключение уходило наверх, и **любая** обработанная
   ошибка превращалась в пустой ответ 500. Регрессия закрыта `test_logging_does_not_raise`.
2. **`create_app(settings)` настраивал приложение наполовину.** Роутеры читали
   глобальные настройки из окружения, а подключение к базе бралось из переданных.
   Приложение могло работать с двумя конфигурациями сразу — в тесте это выглядело как
   «Redis почему-то доступен на порту 1». Настройки привязаны к экземпляру приложения.
3. **Заголовок `X-Request-ID` не доходил до ответа 500.** Такой ответ собирается уровнем
   выше middleware, и до неё управление не возвращается — то есть заголовка не было
   ровно там, где он нужен. Проставляется в самом ответе об ошибке.
4. **Логи uvicorn шли мимо общего формата.** Комментарий в коде обещал единый конвейер,
   а код его не делал. Исправлен код: записи библиотек направляются в общий обработчик
   повторно при старте, когда uvicorn уже применил свою конфигурацию.

**Заметки по реализации.**
- `HTTP_422_UNPROCESSABLE_ENTITY` в Starlette 1.6 объявлена устаревшей — используется
  `HTTP_422_UNPROCESSABLE_CONTENT`.
- Нетипизированная граница redis-py собрана в одном файле `adapters/redis_client.py`:
  одно подавление проверки с объяснением вместо подавления в каждом вызове.
- В CI добавлена обязательная переменная `ORBITA_SECRET_KEY`: без неё приложение не
  стартует, и это правильно.

## ORB-004 — Alembic и базовая схема ✅

- Эпик: E0 · Оценка: S · Зависит от: ORB-003 · Блокирует: ORB-007, ORB-009, ORB-010
- **Статус: закрыт.** Ветка `orb-004-alembic-schema`

**Цель.** Единственный способ менять схему БД — миграция.

**Объём.** Настройка Alembic под async-движок, создание схемы `orbita`, включение
расширений `pg_trgm`, `unaccent`, `citext`, `pgcrypto`. Соглашение об именовании
ограничений. Тест «миграции применяются и откатываются на чистой БД».

**Критерии приёмки.**
- [x] `alembic upgrade head` и `downgrade base` проходят без ошибок — полный цикл
      накат → откат → накат прогоняется на **отдельной** базе, которая создаётся и
      удаляется тестом: `downgrade base` не должен сносить ничего нужного другим.
- [x] `create_all` нигде не вызывается — тест `test_no_create_all` из ORB-001.
- [x] Автогенерация на неизменённых моделях даёт пустой diff — `alembic check` на
      свежей базе, накатанной до головы.

**Сверх карточки — то, что дешевле заложить сейчас.**
- **Соглашение об именовании ограничений.** Без него имена индексам придумывает
  PostgreSQL, на каждой установке по-своему, и откат миграции падает там, где его
  никто не проверял.
- **Таблица версий в схеме `orbita`, а не в `public`.** `public` делится с SETA
  (ADR-0001): в общей схеме две системы переписывали бы номер версии друг другу.
- **Автогенерация ограничена схемой `orbita`.** Иначе Alembic предложит удалить всё,
  что найдёт в чужих схемах, — и однажды такую миграцию применят.
- **Тест на одну голову.** Правило про параллельные миграции записано в INDEX.md;
  теперь оно проверяется, а не только упоминается.
- **Первая миграция проверяет расширения** и, если их нет и создать нельзя, падает с
  инструкцией для администратора базы. Без этого отсутствие `pg_trgm` обнаружилось бы
  через несколько тикетов, при создании GIN-индекса, и сообщение было бы о чём угодно,
  только не о причине.
- Цели `make revision` и `make heads`.

**Что пошло не так.**
`configparser` читает `alembic.ini` в системной кодировке — на Windows это cp1251, и
кириллица в комментариях ломала запуск alembic полностью. Файл переведён на латиницу
с пояснением: это единственное место в проекте, где комментарии не по-русски, потому
что его разбирает чужой парсер, на который мы не влияем. Объяснения перенесены в
`alembic/env.py`, который читается как UTF-8.

**Решения, не входившие в объём.**
Расширения при откате **не удаляются**: база делится с SETA, и `DROP EXTENSION` снёс бы
вместе с расширением всё, что от него зависит у соседа. Откат возвращает базу к
состоянию «есть пустая схема orbita».

**Заметки по реализации.**
- Собственный определитель языка вместо `i18next-browser-languagedetector`: стандартный
  сводит обе узбекские письменности к `uz`, а нам нужно различать их.
- Тесты словарей сравнивают наборы ключей, пустые значения и подстановки `{{...}}` во всех
  трёх локалях — расхождение перевода видно поимённо, а не «где-то что-то не переведено».
- Помощник `cx` появился из-за `noUncheckedIndexedAccess`: класс CSS-модуля имеет тип
  `string | undefined`, и без обёртки в разметку попадает строка «undefined».

## ORB-007 — Пользователи и справочник сотрудников ✅ ✂️ сокращён

> **Сокращён 08.09.2026.** Роли — две вместо шести (ADR-0011).
>
> **Закрыт 09.09.2026**, ветка `orb-007-users-and-people`.

- Эпик: E0 · Оценка: M · Зависит от: ORB-004 · Блокирует: ORB-006, ORB-053, ORB-037
- Открытый вопрос: Q14

**Объём.** Таблицы `users` (двое, кто входит в систему) и `people` (сотрудники
агентства, которые в систему не входят). `external_seta_id` и `telegram_id` заведены
с первой миграции — ADR-0001, ADR-0013.

**Критерии приёмки.**
- [x] `make seed` создаёт согласованный набор пользователей: помощник и руководитель,
      по одному на роль. Проверено тестом и на живой базе.
- [x] ~~У пользователя может быть несколько глобальных ролей.~~ **Критерий изменён**
      вместе с объёмом: роль ровно одна из двух (ADR-0011). Несколько ролей были нужны
      при шести ролях и разграничении по проектам; сейчас это лишняя степень свободы,
      которую пришлось бы проверять в каждом запросе.
- [x] Деактивация пользователя сохраняет его в истории: отключение — не удаление,
      иначе пропадёт авторство прошлых записей. Вход закрывается в ORB-006.

**Ключевое решение.** Пользователь и сотрудник — **разные сущности**. Куратор проекта
и исполнитель задачи — реальные люди агентства, которые в ORBITA не входят. Смешать их
с пользователями значило бы завести сорок учётных записей, которыми никто не
воспользуется: система выглядела бы многопользовательской, не будучи такой.

**Что нашлось по дороге.**
1. **Ошибка порядка в собственном плане.** ORB-006 (вход) стоял перед ORB-007, но
   аутентифицировать не с чем, пока нет таблицы пользователей с хешем пароля. Порядок
   исправлен в INDEX.md.
2. **`alembic check` бесконечно предлагал пересоздать внешний ключ.** Отражение базы
   описывало его как `people.id`, модели — как `orbita.people.id`. Имя схемы убрано из
   `MetaData` и задаётся `search_path` подключения: схема — свойство развёртывания, а
   не модели. Первый же внешний ключ в проекте вскрыл это; со следующими тикетами
   разбираться было бы дороже.
3. **`public` обязан оставаться в `search_path`**: расширения (`citext`, `pg_trgm`)
   установлены там, и без него типы из них не находятся.
4. **Фикстура `session` перестала означать «пустая схема»** после переноса сидов на
   уровень прогона, а её описание это утверждало. Ложное различие с `seeded_session`
   убрано — тест поймал именно эту неточность.

**Решения сверх карточки.**
- **Пароль в сидах не задаётся.** Репозиторий публичный: захардкоженный пароль в сидах
  — это пароль, который останется в рабочей системе. Первичный пароль назначает
  администратор отдельной командой (ORB-006).
- **Сотрудники сидами не заполняются.** Это реальные люди; выдуманные записи пришлось
  бы вычищать перед эксплуатацией, и часть наверняка осталась бы.
- **Счётчик неудачных попыток входа — в записи пользователя, а не в памяти процесса.**
  В памяти он обнулялся бы при перезапуске и не учитывался бы воркером и ботом: то
  есть ограничение частоты существовало бы только на бумаге.
- **Адрес — `citext`.** Человек, набравший заглавную первую букву, должен войти, а не
  завести вторую учётную запись.

## ORB-008 — Ядро разграничения доступа ⛔ снят

> **Снят 08.09.2026.** Пользователей двое, оба видят всё — разграничивать
> нечего ([ADR-0011](../adr/ADR-0011-two-user-scope.md)). Заменён тикетом **ORB-053**,
> который стоит S вместо L. Описание ниже сохранено: если появится третий пользователь
> с ограниченным доступом, возвращаться нужно сюда — и до его подключения, а не после.

- Эпик: E0 · Оценка: L · Зависит от: ORB-007 · Блокирует: ORB-011, ORB-014, ORB-035, ORB-050
- Решения: ADR-0003, ADR-0007 · Сценарий ТЗ: U7

**Цель.** Единственное место, где решается, что человек видит. Самый важный тикет E0.

**Объём.**
- `project_members`, роли в проекте, API управления участниками.
- Выражение `visible_projects(actor)` в репозитории, применяемое ко всем выборкам.
- Зависимость `require(permission, project)` для действий.
- Матрица прав «роль × действие» как данные, а не как условия в коде.
- Учёт `classification = restricted` (ADR-0007) уже здесь.

**Критерии приёмки.**
- [ ] Тест `test_rbac_no_leaks` перебирает все эндпоинты-списки и проверяет отсутствие
      чужих данных для пользователя вне проекта.
- [ ] Роль `admin` не видит содержимое проектов, где не является участником.
- [ ] Обращение к чужому проекту по прямой ссылке даёт 404, а не 403 (не раскрываем существование).
- [ ] Матрица прав задокументирована в `docs/permissions.md`.

## ORB-009 — Журнал аудита

- Эпик: E0 · Оценка: M · Зависит от: ORB-004, ORB-007 · Блокирует: ORB-045
- Решения: ADR-0010 · Требование ТЗ: 6.8

**Объём.** Таблица `audit_log`, вычисление diff по изменённым полям в базовом сервисе,
маскирование содержимого `restricted`-проектов, `actor_kind` для человека, фонового
задания и интеграции, связка с `request_id`.

**Критерии приёмки.**
- [ ] Изменение названия проекта порождает одну запись с `from` и `to` только по этому полю.
- [ ] Запись создаётся в той же транзакции: откат изменения откатывает и запись аудита.
- [ ] Для `restricted`-проекта значения полей в `changes` заменены маркером.
- [ ] UPDATE и DELETE по `audit_log` отклоняются на уровне прав БД.
