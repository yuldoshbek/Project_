## ORB-001 — Репозиторий, инструменты, CI ✅

- Эпик: E0 · Оценка: S · Зависит от: — · Блокирует: ORB-002, ORB-003, ORB-005
- **Статус: закрыт.** Ветка `orb-001-tooling`

**Цель.** Один способ собрать, проверить и запустить проект, одинаковый у человека и у агента.

**Объём.**
- `backend/pyproject.toml`: зависимости, ruff, mypy (strict на `app/domain`), pytest с
  `--cov`, `import-linter` с правилом слоёв из CLAUDE.md.
- `frontend/package.json`: vite, typescript, eslint, prettier, vitest.
- `Makefile`: `up`, `down`, `migrate`, `seed`, `dev`, `test`, `check`, `fmt`.
- `.gitignore`, `.editorconfig`, `.env.example`, `.pre-commit-config.yaml`.
- GitHub Actions: линт, типы, тесты backend и frontend на каждый push.

**Критерии приёмки.**
- [x] `make check` и `make test` проходят на чистом клоне — проверено через `make.ps1`:
      ruff, ruff format, mypy (10 файлов), import-linter (2 контракта), eslint, tsc,
      prettier — все зелёные; pytest 10 passed, vitest 3 passed.
- [x] `import-linter` падает при импорте `app.api` из `app.domain` — тест
      `test_violation_is_detected` намеренно создаёт нарушение и проверяет ненулевой код возврата.
- [ ] CI зелёный, время прогона менее 5 минут — **проверяется после первого push**,
      локально запустить GitHub Actions невозможно.

**Что добавлено сверх исходного объёма и почему.**
- `make.ps1` — в Windows нет `make`, а команда работает на обеих системах.
- `.gitattributes` — без него каждый диск шумит переносами строк.
- `scripts/check_docs.py` и задача `docs` в CI — нумерация тикетов и внутренние ссылки
  ломаются молча; проверка стоит десять строк.
- `backend/.python-version` — без него uv поставил 3.14, а CI работает на 3.12.

**Не входит.** Сборка production-образов и деплой — это ORB-047.

## ORB-003 — Каркас FastAPI

- Эпик: E0 · Оценка: M · Зависит от: ORB-001, ORB-002 · Блокирует: ORB-004, ORB-006

**Цель.** Скелет приложения со сквозными механизмами, чтобы фича-тикеты не изобретали их заново.

**Объём.**
- Слои `api / services / domain / repos / adapters / workers`, DI через зависимости FastAPI.
- Настройки на pydantic-settings, чтение из окружения, падение при отсутствии обязательных.
- Единый формат ошибок RFC 9457, обработчики исключений домена.
- Структурные логи (structlog) с `request_id`, middleware его проставляет и возвращает в заголовке.
- `GET /health` (живость) и `GET /ready` (БД и Redis доступны).
- Асинхронная сессия SQLAlchemy, транзакция на запрос, `search_path` в схему `orbita`.

**Критерии приёмки.**
- [ ] `GET /health` отвечает 200, `GET /ready` — 503 при выключенной БД.
- [ ] Необработанное исключение возвращает RFC 9457 без стектрейса наружу и с ним в логе.
- [ ] `request_id` из заголовка запроса протаскивается в лог и в ответ.

## ORB-004 — Alembic и базовая схема

- Эпик: E0 · Оценка: S · Зависит от: ORB-003 · Блокирует: ORB-007, ORB-009, ORB-010

**Цель.** Единственный способ менять схему БД — миграция.

**Объём.** Настройка Alembic под async-движок, создание схемы `orbita`, включение
расширений `pg_trgm`, `unaccent`, `citext`, `pgcrypto`. Соглашение об именовании
ограничений. Тест «миграции применяются и откатываются на чистой БД».

**Критерии приёмки.**
- [ ] `alembic upgrade head` и `downgrade base` проходят без ошибок.
- [ ] `create_all` нигде не вызывается (проверяется grep-тестом).
- [ ] Автогенерация миграции на неизменённых моделях даёт пустой diff.

## ORB-005 — Каркас frontend

- Эпик: E0 · Оценка: M · Зависит от: ORB-001 · Блокирует: ORB-018, ORB-019, ORB-020, ORB-027, ORB-030

**Цель.** Оболочка приложения, дизайн-токены и локализация до того, как появятся экраны.

**Объём.**

- Дизайн-токены: цвета статусов и светофора, типографика, отступы. Тёмная тема не требуется.

- i18next с тремя локалями и переключателем; правило eslint, запрещающее литералы в JSX.
- Скелетоны загрузки, единый компонент ошибки, страница 403 «нет доступа к проекту».

**Критерии приёмки.**
- [ ] Переключение локали меняет весь интерфейс без перезагрузки.
- [ ] Правило eslint падает на добавленной строке-литерале в компоненте.
- [ ] `tsc --noEmit` и `vitest` зелёные.

## ORB-006 — Аутентификация и порт IdentityProvider

- Эпик: E0 · Оценка: M · Зависит от: ORB-003, ORB-004 · Блокирует: ORB-007, ORB-046
- Решения: ADR-0001 · Открытый вопрос: Q5

**Цель.** Вход в систему сегодня — локальный, завтра — через SETA, без переписывания кода.

**Объём.** Протокол `IdentityProvider` (`authenticate`, `get_or_create_user`,
`sync_profile`), реализация `local` (argon2, JWT access и refresh, ротация refresh),
выбор реализации настройкой. Ограничение частоты попыток входа. Смена пароля,
принудительная смена при первом входе. `GET /me`.

**Критерии приёмки.**
- [ ] Вход, обновление и выход работают; протухший токен даёт 401 с понятным телом.
- [ ] Пять неудачных попыток подряд блокируют вход на 15 минут.
- [ ] Подмена реализации провайдера в тесте не требует правок в роутерах.

## ORB-008 — Ядро разграничения доступа

- Эпик: E0 · Оценка: L · Зависит от: ORB-007 · Блокирует: ORB-011, ORB-014, ORB-035, ORB-050
- Решения: ADR-0003, ADR-0007 · Сценарий ТЗ: U7

**Цель.** Единственное место, где решается, что человек видит. Самый важный тикет E0.

**Объём.**
- `project_members`, роли в проекте, API управления участниками.
- Выражение `visible_projects(actor)` в репозитории, применяемое ко всем выборкам.
- Зависимость `require(permission, project)` для действий.
- Матрица прав «роль × действие» как данные, а не как условия в коде.
- Учёт `classification = restricted` (ADR-0007) уже здесь.

**Критерии приёмки.**
- [ ] Тест `test_rbac_no_leaks` перебирает все эндпоинты-списки и проверяет отсутствие
      чужих данных для пользователя вне проекта.
- [ ] Роль `admin` не видит содержимое проектов, где не является участником.
- [ ] Обращение к чужому проекту по прямой ссылке даёт 404, а не 403 (не раскрываем существование).
- [ ] Матрица прав задокументирована в `docs/permissions.md`.

## ORB-009 — Журнал аудита

- Эпик: E0 · Оценка: M · Зависит от: ORB-004, ORB-007 · Блокирует: ORB-045
- Решения: ADR-0010 · Требование ТЗ: 6.8

**Объём.** Таблица `audit_log`, вычисление diff по изменённым полям в базовом сервисе,
маскирование содержимого `restricted`-проектов, `actor_kind` для человека, фонового
задания и интеграции, связка с `request_id`.

**Критерии приёмки.**
- [ ] Изменение названия проекта порождает одну запись с `from` и `to` только по этому полю.
- [ ] Запись создаётся в той же транзакции: откат изменения откатывает и запись аудита.
- [ ] Для `restricted`-проекта значения полей в `changes` заменены маркером.
- [ ] UPDATE и DELETE по `audit_log` отклоняются на уровне прав БД.
