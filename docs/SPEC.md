## 1. Модель данных (схема `orbita`)

Общие поля всех таблиц: `id uuid pk default gen_random_uuid()`,
`created_at timestamptz not null default now()`, `updated_at timestamptz`.

### 1.1 Люди и доступ

**`users`** — `external_seta_id text unique null` (кто этот человек в SETA; он же белый
список Mini App), `email citext unique`, `full_name`, `position`,
`telegram_id bigint unique null`, `locale` (`ru | uz-Cyrl | uz-Latn`), `timezone` (по
умолчанию Asia/Tashkent), `is_active bool`, `password_hash null`,
`must_change_password bool`, `last_login_at`.

`telegram_id` — **именно `bigint`, не `integer`**, и это не формальность. Миграция
создала поле как `sa.Integer()`
(`backend/alembic/versions/20260909_0902_0003_users_people.py:60`), модель объявлена
`Mapped[int | None]` без явного типа (`backend/app/repos/models/people.py:96`), а в SETA
это `BigInteger`. На настоящем 64-битном идентификаторе вставка сломается. Чинится
отдельной миграцией до включения обмена; расхождение живёт ровно в двух файлах.

`locale` — три значения и **CHECK по списку**. Сегодня это `String(10)` без ограничения,
и чужой код (`uz`, `uz_cyrl`, `en` у SETA) запишется молча. Перевод делает таблица
соответствия в шлюзе обмена, а база обязана отказать чужому значению, а не принять его.
Четвёртый словарь не заводится: английский интерфейс обслуживал бы пользователя, которого
у нас нет.

**`user_roles`** — `user_id fk`, `role` (`assistant | leader`), первичный ключ по паре.
Две роли, разграничения по проектам нет ([ADR-0011](adr/ADR-0011-two-user-scope.md)):
`assistant` — полный доступ, `leader` — чтение плюс решение по проекту в статусе
«На контроле руководителя».

Таблицы `project_members` нет и не будет: делить нечего. Если появится третий
пользователь с ограниченным доступом, возвращаться нужно к ADR-0003 — и до его
подключения, а не после.

**`people`** — сотрудники агентства: `full_name`, `position`, `department`,
`email null`, `phone null`, `is_active`. **Это не пользователи системы.** Куратор
проекта и исполнитель задачи — реальные люди, которые в ORBITA не входят: их
назначает помощник, чтобы знать, с кого спрашивать. Смешать их с `users` — значит
завести сорок учётных записей, которыми никто никогда не воспользуется, и получить
ложную картину: система будет выглядеть многопользовательской, не будучи такой.
Когда сотрудник получит доступ, у него появится запись в `users` со ссылкой на
`person_id` — справочник при этом не переделывается.

### 1.2 Справочники (ТЗ 7, редактируются администратором)

**`directions`** — `code`, `name_ru`, `name_uz_cyrl`, `name_uz_latn`, `sort_order`,
`is_active`. Стартовый набор из ТЗ 7: космический мониторинг, ДЗЗ, международное
сотрудничество, инфраструктура и техническое развитие, нормативно-регуляторная работа,
внутренние организационные инициативы.

**`priorities`** — `code` (`urgent | high | normal | low`), названия на трёх локалях,
`color`, `sort_order`, `escalation_enabled bool` (для `urgent` — да, ТЗ 7).

**`project_statuses`** — `code`
(`initiation | in_progress | on_hold | awaiting_decision | done | cancelled`),
названия, `is_terminal bool`, `requires_reason bool` (для `on_hold` и `cancelled` ТЗ
требует указания причины), `sort_order`.

**`settings`** — key-value с типизацией: `warn_days`, `warn_ratio`,
`escalation_delay_hours`, `escalation_step_hours`, `quiet_hours_start`, `quiet_hours_end`,
`max_upload_mb`, `allowed_mime`. Меняются в интерфейсе администратора без разработчика.

**`organizations`** — `name`, `short_name`, `country_code`, `kind`
(`ministry | agency | university | company | international`), `notes`.

### 1.3 Проекты

**`projects`** — `code` (человекочитаемый, вида PRJ-2026-001), `title`, `description`,
`kind` (`project | mini`), `share_externally bool not null default true` — предпочтение
выдачи, а не гриф секретности (ADR-0024 взамен
[ADR-0007](adr/ADR-0007-restricted-data.md)): запись со значением `false` не уходит ни в
одну из пяти точек выхода наружу — Google-календарь, SETA, Telegram через SETA, экспорт,
внешняя модель,
`direction_id fk`, `curator_person_id fk people` (сотрудник агентства, не пользователь
системы), `status_code fk project_statuses`,
`status_reason text null`, `priority_code fk priorities`, `started_on date`,
`due_on date`, `finished_on date null`, `progress_pct smallint 0..100`,
`progress_mode` (`manual | auto`), `budget_note text null` (справочно, ТЗ 2.5 — без
интеграции с финансовыми системами), `template_id fk null`,
`archived_at timestamptz null`, `created_by fk`, `search_vector tsvector generated`.

`progress_pct` — ручной ввод куратора либо авторасчёт по доле выполненных задач; режим
выбирается полем `progress_mode`, по умолчанию `auto`.

**`impediment text null`** и **`impediment_updated_at timestamptz null`** — единственное
поле ручного ввода по рискам ([ADR-0016](adr/ADR-0016-risks-signals-not-register.md)).
Одна фраза «что мешает» и дата. Реестра рисков с вероятностью, влиянием и планом
реагирования нет и не будет: он требует регулярного пересмотра руками, которого при одном
вносящем человеке не случится.

Строка старше `impediment_stale_days` (справочник `settings`, по умолчанию 14 — **Q23**)
помечается в интерфейсе как устаревшая и **не считается за действующую проблему** в
агрегатах главного экрана. Дата обновления показывается рядом с текстом всегда.

**Сигналы движения вычисляются, не хранятся** (ADR-0016). Пять правил, все пороги в
справочнике `settings` и меняются без разработчика (ТЗ 6.8):

| Сигнал | Правило | Откуда считается |
|---|---|---|
| `is_stalled` | `progress_pct` не менялся дольше `silence_days` при незакрытом сроке | `project_health_snapshots` |
| `is_silent` | нет ни новой задачи, ни комментария, ни встречи дольше `silence_days` | `tasks`, `comments`, `meetings` |
| `has_overdue_tasks` | есть задача с `due_at < now()` в нетерминальном статусе (ADR-0004) | `tasks` |
| `is_squeezed` | до `due_on` меньше `warn_days`, а `progress_pct` ниже доли пройденного времени | `projects` |
| `is_worsened` | `health` хуже, чем в снимке 7 дней назад | `project_health_snapshots` |

`is_silent` — главный из пяти: такой проект зелёный на светофоре и потому невидим до дня,
когда становится красным. Он выносится на первый уровень главного экрана отдельной
строкой, а не прячется в карточку.

**`project_partners`** — `project_id`, `organization_id`, `role text`.

**`milestones`** — `project_id fk`, `title`, `due_on date`, `status`
(`planned | done | missed`), `sort_order`, `description`.

**`project_templates`** — `name`, `kind`, `payload jsonb` (преднастроенные направление,
приоритет, набор вех, чек-листы). Стартовые шаблоны из ТЗ 6.1: международное
сотрудничество, программа мониторинга, внутренняя инициатива.

### 1.4 Задачи

**`tasks`** — `code` (вида TSK-2026-00123), `project_id fk null` (задача может
существовать вне проекта, ТЗ 1), `milestone_id fk null`, `title`, `description`,
`assignee_person_id fk people null` (кому поручено — сотрудник агентства),
`author_id fk users`, `status`
(`new | in_progress | in_review | done | cancelled`, ADR-0004), `priority_code fk`,
`due_at timestamptz null`, `started_at`, `completed_at`, `is_control bool` (поручение
руководителя, требующее контроля), `recurrence_rule text null` (RRULE),
`recurrence_parent_id fk self null`, `kanban_order numeric` (позиция в колонке),
`source_meeting_id fk meetings null` (задача родилась из решения на встрече, ADR-0018),
`search_vector tsvector generated`.

Индексы: `(status, due_at)` — для просрочки, `(assignee_person_id, status)`,
`(project_id, status)`, `(project_id, status, due_at)` — для сигнала
`has_overdue_tasks` по проекту без обхода всех задач, `(source_meeting_id)` — для
вычисления качества встречи, GIN по `search_vector`.

**Ход исполнения поручения принадлежит SETA.** У задачи с `is_control = true` поля
`status` и `completed_at` изменяются только приёмом из SETA
([ADR-0015](adr/ADR-0015-seta-data-ownership.md)); попытка изменить их через наш API
даёт `409` с указанием, где действие живёт. Прочие поля такой задачи ведутся у нас
обычным порядком.

**`task_checklist_items`** — `task_id`, `text`, `is_done`, `sort_order`.

**`tags`** и **`task_tags`** — `name` unique, связь многие-ко-многим.

Таблицы наблюдателей нет: пользователей двое, и оба видят всё.

### 1.5 Общение, файлы, календарь

**`comments`** — `entity_type` (`project | task`), `entity_id`, `author_id`, `body`,
`edited_at`, `deleted_at`. Упоминания вида «собака-имя» разбираются при сохранении и
порождают уведомление.

**`documents`** и **`document_versions`** — см. ADR-0009.

**`meetings`** — встреча как объект учёта, а не строка в календаре
([ADR-0018](adr/ADR-0018-meetings-as-records.md)): `title`, `starts_at`, `ends_at`,
`is_all_day`, `location`, `project_id fk null`, `direction_id fk null`,
`subject text` (по какому вопросу), `created_by`, `ics_uid`,
`seta_meeting_id text null`, `seta_request_id text null` (заявка, если встреча пришла из
неё — встреча может прийти и без заявки).

**Время встречи у нас — копия, а не значение.** `starts_at`, `ends_at`, статус, перенос и
отмена принадлежат SETA ([ADR-0020](adr/ADR-0020-calendar-comes-from-seta.md), договор
§3): правила окна и два запрета на двойную бронь живут в её схеме, и создать встречу мимо
них нельзя ни из Google, ни от нас. `PATCH` этих полей отвечает `409
field-owned-by-seta`. Запись с пустым `seta_meeting_id` заведена руками аварийным путём, и
в интерфейсе у неё стоит подпись «эта встреча календарь руководителя не занимает»:
скрывать разницу нельзя, на ней держится доверие ко всему разделу.

**Заявки на встречу в ORBITA не заводятся.** Заявка, согласование и выбор времени живут
в SETA и уже работают там; дублировать их означало бы завести двух хозяев у одной записи
(ADR-0015). Мы принимаем согласованную встречу и ведём её дальше.

**`meeting_participants`** — `meeting_id`, `person_id fk people null`,
`organization_id fk organizations null`, `full_name text null`, `is_external bool`,
`response` (`none | yes | no | maybe`). Внешний участник обязан нести
`organization_id`: без него вопрос ТЗ 6.4 «сколько организаций запросили встречу» не
имеет ответа, а свободный ввод названия через месяц даст три написания одного министерства.

**Послабление от 16.09** (договор §9): гость, пришедший из SETA, приносит организацию
**текстом**, которой в справочнике может не быть. Такой участник хранится блоком гостя
(ФИО, организация строкой, телефон, нормализованный `phone_norm`), справочник им не
засоряется, а сопоставление со справочником — отдельное действие человека (ORB-082).
Требование выбирать организацию из справочника остаётся в силе для участника, которого
заводят руками у нас.

**`meeting_outcomes`** — результат: `meeting_id unique fk`, `summary text` (о чём
договорились), `decisions text` (что решили), `recorded_at`, `recorded_by fk users`.
Форма разбора — три поля и одна минута: что решили, что делаем, кто и к какому сроку.
Из последнего сразу создаются задачи со ссылкой `source_meeting_id`.

**Качество встречи вычисляется, не оценивается** (ADR-0018, тикет ORB-070). Ручную оценку через две
недели начинают ставить не глядя. Новых цветов не заводится — значения ложатся на
светофор (ADR-0005):

| Значение | Правило | Цвет |
|---|---|---|
| `productive` | результат заполнен, все порождённые задачи закрыты в срок | зелёный |
| `stalled` | результат заполнен, но есть просроченные либо не начатые задачи | жёлтый |
| `formal` | результат не заполнен спустя 48 часов после `ends_at` | серый |

Напоминание о незаполненном результате отправляется **ровно один раз**, через сутки
после `ends_at` (ORB-070). Второе напоминание превращается в фон, который перестают замечать, и
вместе с ним перестают замечать первое (ADR-0008).

Единая лента календаря (ТЗ 6.3) — это **представление** поверх трёх источников: вехи
проектов, сроки задач, события-встречи. Отдельной таблицы «все события календаря» нет.

### 1.6 Уведомления, эскалация, аудит

**`notifications`** — ADR-0008. **`audit_log`** — ADR-0010 (нужен для отчётности и
восстановления хода событий, а не для контроля доступа).

Таблицы `escalations` нет: эскалировать некому (COUNCIL-0002). Нарушенный срок даёт
напоминание помощнику и строку в утренней сводке руководителю.

**`notification_preferences`** — `user_id`, `event_kind`, `channels text[]`.

**`project_health_snapshots`** — ежедневный снимок состояния проекта: `project_id`,
`taken_on date`, `health`, `status_code`, `progress_pct`, `overdue_tasks_count`,
`open_tasks_count`, `days_to_due`; уникальность по `(project_id, taken_on)`.
Отвечает на вопрос «где мы проседаем», на который светофор ответить не может: цвет
меняется от хода времени, и журнал изменений об этом не знает
([ADR-0014](adr/ADR-0014-progress-history.md)). Ретроспектива не восстанавливается —
задание должно работать до первого показа дашборда.

### 1.7 Интеграции

**Направление «Google → ORBITA» удалено целиком**
([ADR-0020](adr/ADR-0020-calendar-comes-from-seta.md), договор §4). Встречи и занятость
руководителя приходят из API SETA; в Google уходят только вехи и сроки задач. Отсюда
исчезли две таблицы — `external_events` и `calendar_sync_state`: читать нечего, `syncToken`
держать не для чего, ответ `410 Gone` обрабатывать негде. В миграциях 0001–0013 их нет,
удаляется спецификация, а не код.

**`google_accounts`** — `user_id fk`, `google_sub`, `email`, `refresh_token_encrypted`,
`access_token_expires_at`, `orbita_calendar_id` (наш отдельный календарь),
`sync_enabled bool default false`, `last_sync_at`, `last_sync_error`. Токен обновления
шифруется ключом из окружения; ключ не входит в резервную копию базы
([ADR-0012](adr/ADR-0012-google-calendar-sync.md) в редакции 16.09). Поля
`watched_calendar_ids` больше нет: чужих календарей мы не читаем.

**`calendar_links`** — связь нашей записи с событием Google: `entity_type`
(`milestone | task`), `entity_id`, `google_event_id`, `calendar_id`, `synced_at`.
Само событие в Google несёт `extendedProperties.private.orbita_entity` — метка остаётся:
к тому же календарю подключён второй клиент, и своя запись должна быть узнаваема.

**`seta_links`** — соответствие наших записей записям SETA: `entity_type`
(`task | meeting`), `entity_id`, `seta_id text`, `last_pulled_at`, `last_pushed_at`.
Уникальность по `(entity_type, seta_id)` и по `(entity_type, entity_id)`: одна запись
там — одна запись здесь, иначе обмен начнёт плодить дубли.

**`seta_sync_state`** — `entity_type` pk, `cursor` (пара `(updated_at, id)`: `updated_at`
не уникален и одного поля мало), `server_time` из последнего ответа SETA, `last_run_at`,
`last_error text null`, `enabled bool default false`. Векторов версий и счётчиков
владельцев не заводится (договор §5).

**Владение разделено по полям** ([ADR-0015](adr/ADR-0015-seta-data-ownership.md), договор
§3). Пересекающихся полей не существует, поэтому арбитраж конфликтов не нужен:

| Сущность | Владеет SETA | Владеет ORBITA |
|---|---|---|
| Поручение (`tasks`, `is_control`) | `status`, `completed_at`, **`due_at`** — действующий срок с учётом продлений | `title`, `description`, **`planned_due_at`** — плановый срок по проекту, `priority_code`, `project_id`, `direction`, `assignee_person_id`, `impediment` проекта, комментарии, вложения |
| Встреча (`meetings`) | время целиком (`starts_at`, `ends_at`), статус, перенос, отмена, заявка и согласование, формат, переговорная, ссылка на онлайн-встречу, блок гостя, решения встречи, ручная оценка руководителя | `project_id`, `direction_id`, `subject`, результат (`meeting_outcomes`), вычисленное качество, привязки, **все показатели и аналитика** |
| Занятость (`busy`) | анонимные интервалы своих встреч | — |
| Занятость вне SETA | приходит от Google к SETA, к нам — анонимной | — |

**Единственный хозяин времени встречи — SETA.** Правило звучит одной строкой: владеет
тот, кто отвечает на вопрос «свободно ли». Отвечать умеет только она — правила окна
(рабочие часы, обед, буфер, праздники, отпуска) живут в её коде, а два запрета на двойную
бронь в ограничениях её схемы.

**Вычисленное качество встречи в SETA не отдаётся вовсе** (договор §9). У неё это ручная
оценка руководителя (−1/0/1), у нас — признак, вычисленный из результата и порождённых
задач. Сложить две разные величины в одно поле — ровно та болезнь, от которой защищает
ADR-0015. Каждая система считает своё, сходятся они на нашем экране.

Правила обмена, проверяемые тестом:

1. Сторона принимает только те поля, которыми не владеет. Прилетевшее чужое поле
   игнорируется молча — это норма протокола, а не ошибка, и в журнал не пишется.
2. Задание идемпотентно: два прогона подряд не создают дублей и не шлют вторых
   уведомлений. Опрос раз в 5 минут по внутренней сети Docker; вебхуков нет ни в одну
   сторону.
3. Недоступность SETA не ломает ORBITA: показываются последние полученные данные с
   пометкой о свежести — не пустой экран и не сообщение об ошибке вместо календаря.
   Пустой календарь неотличим от «встреч нет», а «встреч нет» читается как «день
   свободен». Основание для пометки берётся из `GET /integration/state`, а при
   недоступности самой SETA — из времени нашего последнего успешного опроса.
4. Записи с `share_externally = false` в SETA не уходят ни названием, ни счётчиком
   (ADR-0024). Проверка стоит внутри функции выгрузки, а не у вызывающего кода. Точка
   выхода здесь не одна: поля ORBITA, сохранённые в SETA, попадают ещё и в её ИИ-контур —
   договор §6 обязуется их к модели не передавать проверкой в коде.

**Соответствие статусов встречи** задано договором и не додумывается: `PLANNED` и
`CONFIRMED` → запланирована, `IN_PROGRESS` → идёт, `FINISHED` → состоялась, `CANCELLED` →
отменена. Отменённые приходят тоже — иначе отменённая встреча остаётся в нашем календаре
навсегда. `OVERDUE` к встречам не относится: у SETA это про поручения, а у нас просрочка
статусом не хранится никогда — она вычисляется ([ADR-0004](adr/ADR-0004-overdue-is-computed.md)).
**Соответствие статусов поручений договором не задано** — это дыра, которую закрывать
через владельца вместе с двумя правками ниже.

**Чем SETA входит к нам, договор не сказал.** Он описал наш вход к ней
(`X-Seta-Service-Token`) и молчит о своих вызовах раздела 7. В таком виде
`POST /integrations/seta/decision` и `GET /integrations/seta/digest` — два входа в систему
без объявленной проверки подлинности. Там же: тело `decision` несёт только `idem_key`, а
решение руководителя обязано лечь в `audit_log` от его имени — значит нужен `seta_user_id`.
Обе правки идут через владельца: молча менять формат обмена нельзя.

**Q20 закрыт договором.** API SETA отдаёт `updated_at`, курсор `(updated_at, id)` и
`server_time` в каждом ответе списка и принимает `Idempotency-Key`. Предпосылка обмена
выполнена; `enabled = false` остаётся до этапа 5 её собственного плана, и это не
деградация, а очередь.

**Telegram отдельной таблицы не требует и своего бота у нас нет**
([ADR-0013](adr/ADR-0013-telegram-bot.md), отменён в части бота 16.09). Уведомления
руководителю уходят через `POST /integration/notify` бота SETA с кнопками решений,
нажатие возвращается к нам. Факт отправки фиксируется записью в `notifications`, получатель
определяется по `users.external_seta_id`. Модуль `app/bot` не пишется: две утренние сводки
и два места с кнопками означают, что перестанут читать оба.

### 1.8 Отчёты

**`report_definitions`** — `name`, `owner_id`, `filters jsonb`, `columns text[]`,
`format` (`docx | xlsx`), `schedule_rule null` (RRULE для автогенерации).

**`report_runs`** — `definition_id`, `generated_at`, `document_id fk`, `status`, `error`.

### 1.9 Входящие обращения ([ADR-0017](adr/ADR-0017-incoming-correspondence.md))

**`inbound_requests`** — обращение по существу, а не письмо как документ:
`code` (человекочитаемый, вида IN-2026-0411), `channel`
(`email | letter | telegram | call | in_person`), `organization_id fk organizations`,
`person_name text null` (кто именно обратился), `subject text` (тема одной строкой),
`received_on date`, `respond_by date`, `status`
(`new | in_progress | answered | closed`), `project_id fk null`,
`registration_no text null`, `type_code fk inbound_request_types`,
`kind` (`correspondence | assignment`), `created_by fk users`,
`search_vector tsvector generated`.

**«Ижро» — это `kind = assignment`, а не вторая таблица**
([ADR-0023](adr/ADR-0023-ijro-register.md)). Поручение вышестоящего органа —
Президентского аппарата или другой организации — отличается от письма источником,
сроком, заданным снаружи, и тем, что исполнение контролируется не нами. Различий на одно
поле, а второй реестр стоил бы ORB-065…067 целиком второй раз. К модели добавляются:
`responsible_text text null` (ответственный так, как написано в источнике; ввозом задним
числом не правится), `responsible_person_id fk people null` (необязательная связь, ставится
рукой и отвечает ровно на вопрос «что из этого на нашем сотруднике»),
`source_row_key text null` (распознавание повторов: номер поручения плюс дата документа,
а без номера — «организация + тема + исходный срок»; уникален в пределах `kind`),
`import_batch_id fk null` (из какого привоза строка) и `missing_since date null` (строка
пропала из выгрузки — не удаляется, а помечается: исчезнуть она могла и потому, что
поручение закрыли, и потому, что у выгрузки поменялся фильтр).

`organization_aliases` — `alias text`, `organization_id fk organizations`, уникальность по
нормализованному алиасу. «Президент Администрацияси», «Аппарат Президента» и «АП РУз» —
одна организация. Правило «организация только из справочника» не ослабляется: незнакомое
написание не роняет строку, а попадает в очередь сопоставления, и один жест человека
создаёт псевдоним и достаёт из очереди все строки с ним.

`import_batches` — привоз: файл, кто и когда привёз, период выгрузки, счётчики
(новых, обновлено, сдвинуто сроков, не легло). Предпросмотр до записи обязателен, в базу
не пишется ничего до подтверждения. Статус из чужой таблицы укладывается в наш словарь, а
значение вида «просрочено» в `status` не пишется **никогда**: просрочка вычисляется от
`respond_by` (ADR-0004, инвариант 2 `CLAUDE.md`).

**Обязательных полей ровно четыре:** организация, тема, тип, срок ответа. Всё
остальное необязательно. Семь обязательных полей означают, что через месяц заполняются
три, и неизвестно какие. Норматив ввода — 20 секунд на карточку, проверяется на UAT
наравне с мастером создания проекта (ТЗ 10.5).

`registration_no` — номер канцелярии, ключ сцепки с бумажным контуром: по нему находится
бумага, по бумаге находится карточка. Одно письмо, породившее несколько обращений,
заводится несколькими карточками с одним номером — случай редкий, а разделение на две
сущности удорожает ввод каждый день.

**Разделения «письмо» и «запрос» нет.** Канал — поле, а не сущность.

**`inbound_request_types`** — справочник (ТЗ 6.8, редактируется без разработчика):
`code`, `name_ru`, `name_uz_cyrl`, `name_uz_latn`, `respond_within_days smallint`,
`sort_order`, `is_active`. Стартовый набор: обычное 30 дней, срочное 3 дня, по
поручению руководителя 1 день (**Q24**). `respond_by` вычисляется от `received_on` по
этому справочнику и правится вручную — регламентные сроки не держат в голове.

Индексы — **с ведущим `kind`**, иначе поручения смешаются с письмами в первом же
счётчике: `(kind, status, respond_by)` — для просрочки ответа;
`(kind, organization_id, received_on)` — для аналитики по организациям; `(kind, project_id)`;
`(kind, source_row_key)` unique — для распознавания повторов при привозе; GIN по
`search_vector`.

Вложения — те же `documents` с `entity_type = inbound_request`
([ADR-0009](adr/ADR-0009-attachments-versioning.md)). Первое действие при заведении —
снимок письма или его регистрационного штампа: это меняет ввод с «перепечатать» на
«сфотографировать и дописать три поля». Распознавание текста в первой версии не
делается — снимок официальной переписки уходил бы внешнему сервису (**Q21**).

**Счётчики подписываются «внесено за период», а не «поступило».** Это требование к тексту
интерфейса и к телу ответа `GET /inbound-requests/stats`, а не пожелание: в систему
попадает то, что помощник решил занести, и «поступило» будет прочитано как полная
статистика агентства. Ответ обязан нести поле `completeness: "entered"` и период, за
который считали.

**Периметр.** Обращения, связанные с проектом со `share_externally = false`, не уходят ни
в Google, ни в SETA, ни в экспорт, ни в контекст внешней модели, ни счётчиком в аналитике
и поиске (ADR-0024). Проверка стоит в функции выдачи. Реквизиты источника поручения —
единственное, что из обращений разрешено в поисковый запрос к открытой сети, и то по
белому списку полей ([ADR-0022](adr/ADR-0022-ai-layer-boundaries.md)).

**Не входит:** интеграция с почтовым ящиком, выгрузка из СЭД или канцелярии,
маршруты согласования, ЭЦП (ТЗ 2.5), автоматическая классификация обращения по
направлению (ТЗ 11.3, за пределами MVP).

| Случай | Ответ |
|---|---|
| Сессия истекла, отозвана или токен недействителен | `401` с заголовком `WWW-Authenticate: Bearer`. | SETA недоступна при `POST /integrations/seta/sync` | `503`, `type: seta-unavailable`, состояние обмена не меняется, `last_error` записывается |
| Запрос из внешнего контура к записи со `share_externally = false` | `404`, а не `403`: наружу не подтверждается даже существование записи (ADR-0024) |

| Привоз Ижро: файл без строк | `422`, `type: empty-import`. Не «успешный ввоз нуля строк»: иначе пустой файл пометит весь прежний реестр исчезнувшим |
| Привоз Ижро: заголовки не совпали с запомненной раскладкой | `409`, `type: import-layout-mismatch`, требуется подтвердить сопоставление колонок заново. Сверка по заголовкам, а не по номерам колонок |

## 3. Экраны (ТЗ 9)

## 5. Критерии приёмки системы (ТЗ 14)

1. Все требования раздела 6 ТЗ реализованы и проверены на данных агентства: не менее
   10 проектов и 50 задач (ORB-052).
2. Сценарии U1–U8 из ТЗ 8 проходятся вручную на UAT, каждый — с зафиксированным временем.
3. Разграничение записи (U7) подтверждено автотестом и ручной проверкой: руководителю
   доступно ровно одно записывающее действие — решение по проекту.
4. Резервное копирование и восстановление проверены на тестовом сценарии.
5. Внутренний регламент обязательного ведения проектов в системе утверждён (ТЗ 15).
6. Цифры совпадают во всех местах выдачи на одном наборе данных: главный экран, режим
   «Доклад», числа для утренней сводки SETA и Mini App. Проверяется тестом, а не глазами —
   два источника расчёта разойдутся, и доверия не будет ни к одному. Модель числа не
   считает: она их только называет (ADR-0022).
7. Руководитель проходит сценарий доклада **со своего телефона**, без помощника у
   экрана, и за 30 секунд называет, что в красной зоне и что ждёт его решения
   (ADR-0019). Проверяется на руководителе, а не на разработчике.
8. Обмен с SETA прогнан на боевых данных: поручение, изменённое с обеих сторон между
   синхронизациями, сохраняет обе правки — каждая в своём поле. Отдельно проверяется, что
   нажатие кнопки решения в боте SETA ложится в `audit_log` от имени руководителя.
9. Привоз таблицы Ижро прогнан на настоящей недельной выгрузке: предпросмотр совпал с
   записанным, повтор того же файла не создал вторых строк, сдвинутый срок виден
   в карточке как «было → стало».
10. Каждый экран проверен в обеих темах по правилу контраста ADR-0021.

**Критерий «проверка службой безопасности пройдена без критических замечаний» снят**
решением заказчика 16.09.2026: «здесь нет службы безопасности или утечки, это сугубо
между мной и руководителем». Снят он у нас — в утверждённом ТЗ (раздел 14, критерий 4)
он остался, как осталось и требование 10.1 о размещении данных внутри республики. Это в
точности повторяет историю **Q15** по Google-календарю: разрешение дал заказчик, а не
СБ. Кто и когда снимает критерий формально — **Q27**.

## 6. Что не входит в этот объём

Границы, без которых спецификация описывает всё на свете. Каждая строка — с источником.

| Не делаем | Почему |
|---|---|
| Реестр рисков с вероятностью, влиянием и планом реагирования | ADR-0016: требует регулярного пересмотра руками, которого при одном вносящем не будет |
| Заявки на встречу и их согласование | ADR-0018: живут в SETA и уже работают там |
| Интеграция с почтовым ящиком, выгрузка из СЭД | ADR-0017: ORBITA остаётся единственным источником правды |
| Распознавание текста со снимков писем | Q21: в первой версии его нет, снимок хранится вложением. Адресат вопроса исчез вместе со службой безопасности — решает заказчик |
| **Чтение встреч из Google** | ADR-0020: к тому же календарю подключена SETA, два клиента дают два курсора, и своё эхо неотличимо от чужой правки |
| **Собственный Telegram-бот** | ADR-0013 отменён в части бота 16.09: у руководителя один бот — SETA. Две утренние сводки означают, что не читают обе |
| **Заявки на встречу, согласование, выбор времени** | Договор §3: время руководителя назначает только SETA, там это уже работает |
| Живое обновление постоянным соединением | ADR-0019: отдельная инфраструктура ради эффекта, незаметного при двух пользователях |
| Разграничение доступа между пользователями | ADR-0011: делить нечего, их двое |
| Учёт трудозатрат, бухгалтерия, ЭЦП, публичный портал, мобильное приложение | ТЗ 2.5 и 11.3 |
| Двусторонняя правка встреч в Google | ADR-0012 в редакции 16.09: наружу уходят только вехи и сроки, обратного направления нет вовсе |
| **Трёхмерная графика, звёздное поле, параллакс, анимированный фон под данными** | ADR-0021: всё перечисленное отнимает место или кадры у первого экрана телефона |
| **Локальная модель в контуре** | ADR-0022: сервер с видеокартой и человек при нём дороже всей системы, построенной для двоих. Пересматривается, если разрешение заказчика отзовут |
| **Своя матрица прав из ответа SETA** | ADR-0013: у неё шесть ролей и 34 права, у нас двое; принять чужую матрицу — завести второго хозяина у доступа |

**Тёмная тема делается и становится основной.** Прежняя запись «не делается» снята
[ADR-0021](adr/ADR-0021-cosmic-visual-layer.md) — тем самым отдельным решением, которого
она и требовала. Момент выбран не случайно: во всём `frontend/src` за пределами
`tokens.css` цветов нет, кроме шести зашитых чернильных значений в двух модулях, поэтому
сегодня перекраска стоит один файл и шесть правок, а после волны A — проход по всем
написанным к тому времени экранам.
