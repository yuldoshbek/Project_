# ADR-0002. Технологический стек

- Статус: принято · Дата: 08.09.2026 · Контекст: ТЗ 11.1, 10.2, 10.4

## Решение

Backend: Python 3.12, FastAPI, SQLAlchemy 2.x (async), Pydantic v2, PostgreSQL 16,
Redis + ARQ, Alembic. Frontend: React 18 + TypeScript, Vite, TanStack Query и Table,
react-i18next, dnd-kit (канбан), ECharts (дашборд и диаграмма Ганта).
Хранение файлов: S3-совместимое (MinIO в dev и в контуре агентства).

## Обоснование

Стек прямо назван в ТЗ 11.1 как используемый для SETA. Главный критерий здесь не
техническое превосходство, а то, что обе системы поддерживает одна команда, и что при
слиянии (ADR-0001) не потребуется переписывание.

PostgreSQL 16 выбран в том числе из-за требования 6.9: `pg_trgm`, `unaccent` и tsvector
закрывают полнотекстовый поиск на трёх раскладках без внешнего поискового движка
(см. [ADR-0006](ADR-0006-multiscript-search.md)). Отдельный Elasticsearch на объёме
«десятки проектов, тысячи задач» — необоснованная эксплуатационная нагрузка.

ARQ вместо Celery — как в SETA; для нашего профиля (напоминания, эскалация, генерация
отчётов) возможностей достаточно, а зависимостей меньше.

## Последствия

Нагрузка из ТЗ 10.2 закрывается одним экземпляром приложения; горизонтальное
масштабирование возможно, но в MVP не требуется и не строится. Ограничение: агрегаты для
диаграммы Ганта упираются в SQL, а не в ORM — это учтено в тикете ORB-029.
