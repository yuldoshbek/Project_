# ADR-0035. Расписание держит GitHub Actions, а не площадка размещения

- Статус: принято · Дата: 20.09.2026
- **Уточняет** [ADR-0032](ADR-0032-scheduled-jobs.md): порт `Scheduler` и защищённый
  эндпоинт остаются, меняется только то, кто нажимает будильник
- Связано: [ADR-0028](ADR-0028-hosting.md)

## Контекст

ADR-0032 оставил фон без воркера: задача — именованный обработчик за эндпоинтом
`/internal/jobs/{name}`, а расписание вызывает его извне. Кто именно вызывает, там было
записано как «расписание платформы», то есть Vercel Cron.

При настройке выяснились два обстоятельства.

Первое: на бесплатном тарифе Vercel расписание ограничено — одна задача в сутки и не
больше двух заданий. Наших задач три, и одна из них ежечасная. То есть расписание Vercel
требует платного тарифа само по себе, независимо от нагрузки.

Второе: заказчик прямо просил, чтобы **GitHub был центром**. Журнал прогонов в Actions
видно там же, где код, PR и выкладку, и в него можно заглянуть с телефона.

## Решение

Расписание держит **GitHub Actions** (`.github/workflows/jobs.yml`). Оно вызывает тот же
эндпоинт `/internal/jobs/{name}` с секретом в заголовке. Работу выполняет приложение,
GitHub только звонит.

Точность — минуты, а не секунды: GitHub может задержать запуск при общей загрузке. Для
утренней сводки в 08:30 это приемлемо и записано в ТЗ. Остальные задачи ко времени
безразличны.

Последствия для переносимости нулевые: на сервере агентства тот же обработчик вызывает
cron в контейнере, и меняется одна строка расписания, а не код.

## Отвергнутые варианты

**Vercel Cron.** Требует платного тарифа ради самого расписания, а журнал запусков лежит
отдельно от репозитория. Остаётся запасным путём: если Actions станет неудобен, включается
без изменений в коде.

**Ежеминутный опрос вместо расписания.** Сорок тысяч запусков в месяц ради трёх задач в
сутки.

## Последствия

- Отказ GitHub Actions означает, что задачи не выполнились. Это видно: пропуск заметен по
  отсутствию утренней сводки, а догоняющий режим обработчика делает работу при следующем
  запуске.
- Секрет `PRODUCTION_JOBS_SECRET` живёт в окружении `production` и нигде больше.
- Эндпоинт задач не проходит через прокси интерфейса: расписание обращается к API напрямую,
  а публичный адрес сайта его не отдаёт вовсе.
