# ADR-0004. «Просрочена» — вычисляемое состояние, а не статус

- Статус: принято · Дата: 08.09.2026 · Контекст: ТЗ 7 (справочник статусов задачи), 6.4, 6.5

## Контекст

ТЗ перечисляет статусы задачи так: Новая, В работе, На проверке, Выполнена, Просрочена.
Первые четыре описывают, что делает исполнитель. Пятый описывает, что наступил срок.
Это разные измерения: задача «на проверке» может быть просроченной одновременно.

Если хранить «просрочена» в поле `status`, при наступлении срока теряется исходное
состояние: непонятно, куда возвращать задачу после обновления, ломается статистика по
этапам работы и появляется колонка канбана, в которую задачи попадают сами собой.

## Решение

- `tasks.status` принимает значения `new`, `in_progress`, `in_review`, `done`, `cancelled`.
- Просрочка вычисляется: `due_at IS NOT NULL AND due_at < now() AND status NOT IN (done, cancelled)`.
- API отдаёт производные поля `is_overdue` и `days_overdue`.
- В интерфейсе, фильтрах и отчётах «Просрочена» присутствует как значение фильтра и как
  визуальный маркер — пользователь видит ровно то, что описано в ТЗ.
- В канбане просрочка — красная рамка карточки, а не отдельная колонка.

## Последствия

Раздел 7 ТЗ в этой части реализуется по смыслу, а не буквально. Пункт вынесен в
[OPEN-QUESTIONS](../OPEN-QUESTIONS.md) (Q6) для подтверждения заказчиком и в предложения
по изменению ТЗ (COUNCIL-0001, замечание 1). Фильтр по просрочке требует индекса
`(status, due_at)` — учтено в тикете ORB-014.
