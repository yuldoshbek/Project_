# ADR-0003. Права доступа считаются на уровне проекта

- Статус: принято · Дата: 08.09.2026 · Контекст: ТЗ 5 (последний абзац), 10.1, сценарий U7

## Контекст

ТЗ требует разграничения «на уровне проекта, а не только на уровне всей системы»:
куратор и исполнители видят полные данные своего проекта, посторонние — только то, куда
приглашены. Сценарий U7: новый сотрудник с первого входа видит только свои задачи.
Это требование невозможно добавить позже — оно определяет форму каждого запроса к данным.

## Решение

Две независимые оси прав:

1. **Глобальная роль** (`leader`, `assistant`, `admin`, `employee`) — что человек может
   делать в системе вообще.
2. **Участие в проекте** (`project_members` с ролью `curator`, `executor`, `watcher`) —
   к каким данным он допущен.

Видимость вычисляется одним выражением `visible_projects(actor)`:
- `leader` и `assistant` — все проекты, кроме `restricted`, куда не включены явно;
- `admin` — управление пользователями и справочниками, **без** доступа к содержимому
  проектов, куда не включён (иначе IT-роль становится обходом разграничения);
- остальные — проекты, где есть запись в `project_members`.

Единственная точка реализации — слой репозиториев. Каждый метод выборки принимает `actor`
и обязан применить фильтр. Роутеры запросы не строят.

Контроль: тест `test_rbac_no_leaks` перебирает все эндпоинты-списки и проверяет, что
пользователь без участия не видит чужой проект и его задачи. Новый эндпоинт списка, не
добавленный в этот тест, не проходит ревью.

## Последствия

Плата — обязательный параметр `actor` во всех выборках и невозможность «просто выбрать все
задачи» в отчётах и фоновых задачах (для них заводится явный системный актор). Взамен
сценарий U7 выполним и проверяем, а проверка службой безопасности (ТЗ 10.1) получает одно
место для аудита вместо россыпи условий по роутерам.

## Отвергнуто

Row Level Security средствами PostgreSQL: даёт более жёсткую гарантию, но требует
пробрасывать личность пользователя в соединение при пуле соединений async-приложения и
усложняет фоновые задачи. Возврат к этому варианту возможен, если потребует СБ.
