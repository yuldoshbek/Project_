# ADR-0026. Входа в приложении нет: доступ решает периметр, роль выбирается переключателем

- Статус: принято · Дата: 18.09.2026 · Контекст: решение заказчика 18.09.2026 — «убери вход,
  авторизация не нужна, свободный доступ»; бэкенд на сервере агентства, фронтенд может
  стоять на Netlify
- **Отменяет** ORB-006 (аутентификация и порт `IdentityProvider`), ORB-081 (вход в
  интерфейсе), ORB-122 (экран смены временного пароля) и инвариант про 401/403
- Связано: [ADR-0011](ADR-0011-two-user-scope.md), [ADR-0010](ADR-0010-audit-log.md),
  [ADR-0019](ADR-0019-leader-is-direct-user.md), [ADR-0024](ADR-0024-share-externally.md)

## Контекст

Заказчик потребовал убрать вход: «авторизация не нужна, свободный доступ». Отдельно он
сказал, где всё будет жить: **бэкенд и все процессы — на сервере агентства**, фронтенд
можно положить на Netlify.

Вход здесь и правда почти ничего не охраняет, и это было известно раньше. Пользователей
двое, [ADR-0011](ADR-0011-two-user-scope.md) уже постановил, что **границы между ними
нет**: оба видят всё, разграничение по проектам отменено, матрица прав не заводится.
Экран входа разделял не двух пользователей друг от друга, а систему от всех остальных —
то есть делал работу периметра, стоя внутри приложения.

При этом плата за него была настоящая: пароли, их хеши, ротация токенов обновления,
блокировка после пяти попыток, временный пароль, которого негде сменить (известный пробел
ORB-122), 590 строк тестов и порт `IdentityProvider` под провайдера, которого не будет.
Полторы тысячи строк ради ворот, за которыми стоят двое, знающих друг друга.

**Опасность, которую нельзя замолчать.** Снятие входа само по себе безобидно; опасна пара
«нет входа» плюс «API виден из интернета». Фронтенд на Netlify ходит в API из браузера
пользователя — значит при работе вне сети агентства API обязан быть доступен снаружи. А
API без входа, доступный снаружи, означает, что контрольные таблицы с поручениями
Администрации Президента и фамилиями ответственных читает любой, кто узнал адрес, и
индексирует любой поисковик, который до него добрался.

## Решение

**Аутентификация уходит из приложения на периметр. Роль остаётся и выбирается
переключателем без пароля.**

### 1. В приложении входа нет

Удаляются: экран входа, ворота маршрутов, JWT, токены обновления и их ротация, пароли и их
хеши, блокировка после неудачных попыток, признак «сменить временный пароль», порт
`IdentityProvider` и его локальная реализация, команда назначения пароля.

`401 Unauthorized` из системы исчезает: ответить «войдите» некуда. `403` остаётся ровно для
одного случая — действие, доступное только одной роли.

### 2. Кто действует — говорит переключатель, а не пароль

Таблица `users` **остаётся** с двумя строками из сидов. Она нужна не для входа, а для двух
вещей: у записи в `audit_log` обязан быть автор (инвариант 4,
[ADR-0010](ADR-0010-audit-log.md)), и решение руководителя обязано быть отличимо от заметки
помощника.

Действующее лицо приезжает заголовком `X-Orbita-Actor` со значением `assistant` или
`leader`; в интерфейсе это переключатель «Я помощник / Я руководитель», выбор хранится на
устройстве. Нет заголовка — действует помощник: он вносит данные, и ошибка в его пользу
безопаснее.

**Сервер верит заголовку на слово, и это не недосмотр.** Между двумя пользователями
границы нет (ADR-0011) — проверять нечего. Заголовок не охраняет данные, он **подписывает
действие**: чтобы через месяц было видно, кто перевёл поручение в «сделано». Подпись,
которую можно подделать, бесполезна против злоумышленника и совершенно достаточна против
забывчивости, а именно забывчивость здесь и стоит денег.

### 3. Защита переезжает на периметр, и там её надо поставить

Это не «защиты больше нет». Это «защита в другом месте», и место обязано быть названо,
иначе решение превращается в публикацию поручений АП.

**База:** API **не публикуется в открытый интернет**. Он слушает внутри сети Docker на
сервере агентства, наружу его выставляет обратный прокси, и у прокси стоит хотя бы одно из
трёх: доступ только из сети агентства, VPN, или общий пароль на уровне прокси (браузер
запоминает его один раз — экрана входа в приложении это не добавляет).

**Фронтенд на Netlify при этом остаётся возможным**, но честно: он работает там, откуда
браузер дотягивается до API. Снаружи сети — только если периметр открыт. Поэтому запасной
и более простой путь — положить собранный фронтенд рядом с API на том же сервере, и тогда
Netlify не нужен вовсе.

**Что настраивается в коде:** список источников CORS (домен Netlify и домен агентства) —
параметр окружения, не константа. Без него фронтенд с чужого домена не сможет вызвать API
вовсе, и это первое, что сломается при выкладке.

### 4. Чего это решение не отменяет

`share_externally` остаётся ([ADR-0024](ADR-0024-share-externally.md)) и становится
**важнее**. Раньше внутри системы было видно всё, потому что внутри были двое. Теперь
«внутри» определяется периметром, а не входом, и предпочтение выдачи — единственное, что
по-прежнему проверяется в коде на точках выхода наружу.

Журнал изменений не ослабляется ни на строку: у каждой записи по-прежнему есть автор,
время и дифф по полям.

## Последствия

**Хорошо.** Уходит полторы тысячи строк, которые охраняли двоих друг от друга. Исчезает
известный пробел ORB-122: временный пароль, который негде сменить, больше не существует.
Руководитель открывает ссылку и сразу видит данные — ровно то, ради чего ADR-0019 требовал
тридцать секунд. Порт `IdentityProvider` снимается вместе с провайдером, которого не будет.

**Плохо и существенно.** Приложение больше не защищает себя само. Пока периметр не
настроен, **любой, кто дотянулся до API, читает и меняет всё** — включая поручения
Администрации Президента. Раньше забытая настройка прокси означала неудобство; теперь она
означает утечку. Это обязано попасть в контрольный список выкладки первой строкой, а не в
примечание.

Вторая цена: заголовок роли подделывается тривиально. Если когда-нибудь появится третий
пользователь, которому нельзя видеть всё, это решение придётся пересматривать целиком —
не дописывать, а пересматривать.

**Риск, который надо назвать.** Соблазн выложить API наружу «на время, чтобы посмотреть с
телефона» возникнет на первой же неделе. Сделанное «на время» останется, потому что
работает. Поэтому правильный порядок — сначала прокси с ограничением, потом первый показ,
а не наоборот.

## Отвергнутые варианты

- **Оставить вход как есть.** Отвергнут заказчиком дважды и прямо. Довод против него
  честный и без заказчика: вход разделял не пользователей, а систему от внешнего мира, то
  есть делал работу периметра не на своём месте.
- **Убрать вход и вместе с ним роли.** Отвергнут: тогда `audit_log` теряет автора
  (инвариант 4), а решение руководителя становится неотличимо от заметки помощника — то
  есть пропадает единственное действие, которое в системе есть у руководителя.
- **Один общий пользователь без переключателя.** То же самое, мягче на словах: через месяц
  на вопрос «кто это отметил» журнал ответит «система».
- **Секретная ссылка вместо входа** (длинный токен в адресе). Отвергнут: токен, зашитый в
  сборку фронтенда на Netlify, читает любой, кто открыл сайт. Это не защита, а её
  имитация, и имитация опаснее отсутствия — на неё полагаются.
- **Фронтенд на Netlify с открытым API.** Отвергнут как основной путь: публикация
  поручений АП в открытый интернет — не то решение, которое принимают между делом. Если
  заказчик выберет его осознанно, это отдельная запись с его подписью, а не следствие
  этой.
