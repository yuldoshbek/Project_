# ADR-0005. Правило «светофора» актуальности

- Статус: принято как допущение, ожидает подтверждения (OPEN-QUESTIONS Q1)
- Дата: 08.09.2026 · Контекст: ТЗ 6.4, 2.4

## Контекст

ТЗ требует цветовую индикацию: зелёный — по плану, жёлтый — риск срыва срока, красный —
просрочено. Красный определён однозначно. Зелёный и жёлтый — нет: непонятно, когда именно
проект переходит в зону риска. Без числа это невозможно ни реализовать, ни принять.

## Решение

Цвет вычисляется на сервере по единому правилу и для проекта, и для задачи:

| Цвет | Условие |
|---|---|
| Красный | просрочено (см. [ADR-0004](ADR-0004-overdue-is-computed.md)), либо есть хотя бы одна просроченная задача проекта |
| Жёлтый | до планового срока осталось не более `warn_days` (по умолчанию 3 календарных дня), либо прошло более `warn_ratio` (по умолчанию 80%) отведённого на работу времени, а статус не терминальный |
| Зелёный | остальные случаи |
| Серый | статус `done` или `cancelled` — из светофора исключены |

`warn_days` и `warn_ratio` — записи справочника настроек, редактируемые администратором
без разработчика (ТЗ 6.8). Для приоритета «Срочно» `warn_days` равен 0: такая задача
жёлтая с момента постановки и красная сразу после срока.

Цвет **не хранится** в таблицах: он вычисляется в том же SQL-запросе, что и агрегаты
дашборда, иначе понадобится пересчёт по расписанию и цвет будет отставать от реальности.

## Последствия

Дашборд и списки считают цвет одним выражением — это обязывает держать правило в одном
месте (`domain/health.py` + SQL-функция), иначе UI и API разойдутся. Тест сравнивает
результат Python-реализации и SQL-реализации на одном наборе данных.

Если заказчик задаст другие пороги — меняются только значения справочника, не код.
