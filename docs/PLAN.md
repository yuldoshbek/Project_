# Базовый план ORBITA v3

Версия 3.0 · 20.09.2026 · Заменяет [план v2](archive/PLAN-v2.md) и все тикеты прежних
объёмов ([архив](archive/tickets-v2)).

Требования — [ТЗ v2.0](../tz/TZ-ORBITA-v2.0.md). Правила работы — [CLAUDE.md](../CLAUDE.md).

**Как меняется план.** Только на приёмке блока: заказчик даёт замечания пакетом, влияние
на план разбирается вслух, изменение записывается сюда с датой. Посреди блока объём не
меняется — именно это правило лечит главную болезнь прежней разработки, где объём
пересобирался пять раз за одиннадцать дней.

## Как нарезаны блоки

Блок — это вертикальный срез: данные, API и экран, который можно открыть и которым можно
пользоваться. Не «слой целиком» и не «модель без экрана». Каждый блок заканчивается тем,
что заказчик работает в системе на настоящих данных.

Цикл внутри блока один и тот же: **разработка → тест визуала → тест кода → отчёт**, затем
приёмка и выкладка по кнопке.

| Блок | Название | Результат для заказчика |
|---|---|---|
| 0 | Подготовка | система открывается по личной ссылке, пустая, но настоящая |
| 1 | Ядро управления | ведём проекты, программы, задачи; руководитель решает с телефона |
| 2 | Контроль и взаимодействие | Ижро, организации и письма, подготовка докладов |
| 3 | Идеи, монитор, завершение | идеи и карты, режим совещания, отчёты, узбекские языки |

## Блок 0. Подготовка

**Документы.** ТЗ v2.0, CLAUDE.md, этот план, глоссарий, архитектура, решения ADR‑0027…0035,
мастер настройки [SETUP](SETUP.md), инструкция эксплуатации [RUNBOOK](RUNBOOK.md),
обнулённый список открытых вопросов, новый README.

**Инфраструктура.**
- Защита `main`: слияние только через PR, обязательные проверки, запрет force-push.
- CI: ruff, mypy, import-linter, pytest на настоящей PostgreSQL, eslint, prettier, tsc,
  vitest, сборка, проверка миграций (одна голова, `alembic check`).
- Превью на каждый PR: ветка демо‑базы, развёртывание backend и frontend, e2e‑проверка,
  комментарий со ссылкой в PR.
- Рабочий контур: выкладка после слияния по кнопке, проверка после выкладки, откат.
- Ночная резервная копия и восстановление на момент времени.

**Код.**
- Backend: новая базовая миграция вместо восемнадцати прежних; перенос доменных правил,
  журнала изменений и разбора Ижро; единица работы и сервис показателей; порты
  `FileStorage`, `Scheduler`, `PushSender`; вход по личной ссылке; задачи по расписанию.
- Frontend: новый проект на React 19, Tailwind и shadcn/ui; токены двух тем; оболочка трёх
  устройств; PWA с установкой на экран «Домой»; клиент API из OpenAPI; i18n на ключах.
- Справочники из указов: организации, типы проектов с шаблонами вех, типы задач, регионы,
  пороги сигналов.

**Критерии приёмки.**
1. Заказчик открывает ORBITA по своей ссылке на iPhone и на ноутбуке; руководитель — по
   своей; обе темы работают, экран не ломается на 390, 1440 и 2560 px.
2. PR с любым изменением даёт ссылку на превью, и там видно изменение.
3. Все проверки в CI зелёные; выкладка в рабочий контур проходит по кнопке и откатывается.
4. В рабочей базе заведены справочники; в демо — вымышленные данные.
5. Реальных данных в облачном превью нет и попасть туда они не могут.

**Что делает заказчик:** запускает мастер настройки аккаунтов и ключей (20–30 минут),
разрешает защиту `main`, проверяет вход по ссылке с телефона.

## Блок 1. Ядро управления

**Состав.**
- **Шаг 0 — основание под ТЗ v2.0** (добавлен 20.09.2026, см. журнал): новая базовая
  миграция по разделу 3 ТЗ, сервис показателей с лестницей внимания, поле версии у
  редактируемых записей, справочники из указов, удаление снятого объёма. Выполняется до
  первой строки Пульта: пока рабочей базы нет, замена схемы стоит один файл.
- **Пульт**: лестница внимания по всем готовым разделам; решения руководителя в одно
  касание и журнал решений; «С прошлого визита»; «Кто держит»; отчёт недели и месяца с
  печатью; предпросмотр утренней сводки.
- **Программы**: горизонт 2026–2030, вехи по годам, отсчёт, «что должно случиться до конца
  года», подпроекты.
- **Проекты**: десять типов с шаблонами вех, подпроекты, роли организаций, Центр и срез
  «что держит Центр», исходный срок и переносы, «что мешает», виды доска / таблица /
  таймлайн, сценарий «что если».
- **Задачи**: одиннадцать типов, задачи без проекта, чек‑листы, создание строкой с разбором.
- **Календарь**: вехи, сроки, годовые циклы, «горячие дни».
- **Захват** на всех экранах; **Управление**: справочники, пороги, ссылки доступа, обход.
- **Уведомления**: утренняя сводка в 08:30 и пуш на два события.

**Критерии приёмки.**
1. Помощник заводит настоящий проект со всеми полями меньше чем за минуту.
2. Руководитель на iPhone видит лестницу внимания и принимает решение в одно касание;
   решение видно помощнику и попадает в журнал.
3. Изменение срока вехи в сценарии «что если» показывает влияние и **не меняет базу**,
   пока не нажато «применить».
4. Все цифры Пульта совпадают с разделами: проверяется тестом, а не на глаз.
5. Утренняя сводка приходит на iPhone в 08:30 по Ташкенту.
6. Печать отчёта недели даёт читаемый PDF.

**Что делает заказчик:** вносит настоящие проекты и программы, проверяет их на телефоне,
даёт замечания пакетом.

## Блок 2. Контроль и взаимодействие

**Состав.**
- **Ижро**: загрузка таблиц Word с предпросмотром классов изменений и идемпотентностью;
  карточка поручения (сроки, промежуточный срок, этап, головной исполнитель, признак
  жизни, контрольные отметки, история продлений); двенадцать вопросов‑виджетов; стена
  документов; связь с задачами и «разложить на задачу»; решения по поручениям и их
  исполнение; справка по проблемным поручениям.
- **Взаимодействие**: карточка организации, Центр как учреждённая организация, архив
  писем и его аналитика, оценка ответа, соглашения и «спящие».
- **Доклады и мероприятия**: подготовка к дате, запросы сведений и блок «кто не дал» с
  напоминанием, этапы, версии презентаций с замечаниями на слайд, чек‑лист мероприятия.
- **Файлы**: загрузка и хранение через порт, предпросмотр PDF.

**Критерии приёмки.**
1. Настоящая таблица Word загружается, предпросмотр показывает изменения, повторная
   загрузка того же файла ничего не меняет.
2. Перенос срока в источнике превращается в запись истории продлений после подтверждения
   человеком.
3. Руководитель на телефоне видит «что горит», «из‑за кого сорвётся» и «работает ли
   ответственный», и ставит контрольную отметку в одно касание.
4. По письмам видно, кто не отвечает и как быстро отвечают, с честной пометкой при малом
   числе писем.
5. У доклада видно, каких сведений не хватает и кто задерживает; напоминание готовится
   кнопкой.

**Что делает заказчик:** приносит настоящие таблицы Ижро и письма, проводит через систему
подготовку одного реального доклада.

## Блок 3. Идеи, монитор, завершение

**Состав.**
- **Идеи и карты**: путь идеи, решение руководителя, mind map в двух режимах, полотно на
  ноутбуке и контур на телефоне, узел → проект или задача одним действием, живое появление
  правок у второго пользователя.
- **Монитор**: многопанельный обзор и режим «Совещание» — один вопрос на экран.
- **Отчёты**: неделя и месяц в PDF, справка по Ижро.
- **Узбекские языки**: латиница и кириллица.
- **Полировка**: движение «космос», бюджеты производительности, доступность, снимки
  экранов как тесты.
- **Переносимость**: сборка Docker и инструкция переезда на сервер агентства; порт для
  событий SETA (без подключения).

**Критерии приёмки.**
1. Идея превращается в проект одним действием, карта работает на ноутбуке и на телефоне.
2. Режим «Совещание» проходит повестку на большом мониторе без служебных элементов.
3. Интерфейс полностью переключается на узбекскую латиницу и кириллицу.
4. Первый экран на телефоне открывается меньше чем за 2,5 секунды по 4G.
5. Сборка Docker поднимается на чистой машине по инструкции и работает с копией базы.

## Порядок и зависимости

Блоки идут строго по очереди: каждый следующий опирается на данные и экраны предыдущего.
Внутри блока backend и frontend могут идти параллельно, но не больше двух потоков.

Вне плана до отдельного решения заказчика: подключение SETA, собственный бот, внешние
модели ИИ, учёт трудозатрат в часах, разграничение доступа, электронный документооборот.
