# План 10x: что переписать, что починить, что не трогать

Предложение к приёмке блока 0. Основание — [аудит 20.09.2026](AUDIT-2026-09-20.md).
План работ [PLAN.md](../PLAN.md) этим документом **не заменяется**: он меняется только на
приёмке, решением заказчика, и запись в его журнал делается после разговора.

---

## Откуда берётся десятикратность

Не из того, что код станет чище. Из четырёх рычагов, каждый из которых меняет не качество,
а **стоимость следующего шага**.

### Рычаг 1. Переписать схему сейчас, а не потом

Сегодня схема ТЗ v2.0 — это один файл миграции. Рабочей базы с реальными данными нет
([PLAN](../PLAN.md), блок 0 ещё не выложен), поэтому «переписать» значит буквально
заменить `20260920_1200_0001_foundation.py` на другой такой же файл.

После первой выкладки то же самое — это миграция «расширить → переключить → сжать» по
десятку таблиц, перенос данных, откат, проверка отката, и всё это на данных агентства.
Разница в стоимости — примерно тридцатикратная, и окно закрывается в день, когда заказчик
нажмёт «выложить».

**Это самый дорогой пункт плана, и он же самый срочный.**

### Рычаг 2. Лестница внимания как единственный расчёт

ТЗ 4 задаёт шесть состояний в строгом порядке: ждёт решения → просрочено → горит →
зависит от чужих → молчит → по плану. Из них собирается Пульт, из них же — сигналы в
каждом разделе, отчёт недели, утренняя сводка и сценарий «что если».

Сейчас это считают три места разными способами (аудит, К6). Если Пульт станет четвёртым,
критерий приёмки блока 1 № 4 — «все цифры Пульта совпадают с разделами, проверяется
тестом» — выполнить будет нечем: тест сверял бы два независимых расчёта и падал бы на
третьей неделе.

Один модуль `services/metrics.py` с одной точкой входа `attention_ladder(scope)` — и тест
превращается в «Пульт без фильтра равен сумме разделов», три строки.

### Рычаг 3. Экран первым, API под экран

Сейчас порядок обратный: 45 эндпоинтов, из них интерфейс вызывает 5. Сорок написаны,
покрыты тестами, задокументированы — и ни разу не открыты человеком. Это не потерянная
работа, это **работа, о полезности которой никто не может судить**.

ТЗ §1 говорит: «Презентационный слой — это и есть система». Из этого следует порядок
работы внутри блока: сначала экран на вымышленных данных, заказчик смотрит его на
телефоне, потом под утверждённый экран пишется API. Эндпоинт, у которого нет экрана, не
пишется вовсе.

### Рычаг 4. Снять то, чего ТЗ не требует

Удаление снятого объёма даёт больше, чем кажется: 2 000 строк кода и 208 тестов перестают
требовать внимания на каждом изменении, `make test` ускоряется, и — главное — перестаёт
работать механизм «раз тесты есть, значит это нужно».

| Что убрать | Строк кода | Тестов | Почему |
|---|---|---|---|
| Теги (`tags`, `task_tags`, `services/tags.py`) | ~150 | ~10 | ТЗ v2.0 и CONTEXT слова «тег» не знают |
| Приоритеты как поле проекта и задачи | ~80 | ~12 | в ТЗ 3.1/3.2 приоритета нет; важность выражает лестница внимания |
| Мини-проект (`ProjectKind.MINI`) | ~40 | ~8 | ТЗ знает проект, программу и подпроект |
| `progress_mode`, `budget_note` | ~60 | ~10 | готовность в ТЗ 3.1 считается по вехам и задачам, всегда |
| Комментарии к проектам и задачам | ~430 | 33 | ТЗ 3.x ленты у проекта и задачи не предусматривает. **Лента «Ижро» остаётся** — она нужна по ТЗ 3.3 и уже реализована той же таблицей |
| `is_control`, `author_id` у задачи | ~30 | ~6 | контроль — это «Ижро», а не признак задачи |

Итого ≈ 790 строк кода и 79 тестов прямого удаления, плюс ≈ 1 200 строк и 130 тестов
переписываются вместе со схемой.

Обоснование каждого — в аудите, раздел «Что оправдано и трогать не надо».

## Этапы

Четыре этапа. Границы блоков [PLAN.md](../PLAN.md) сохраняются; меняется наполнение
блока 1 — в него добавляется нулевой шаг «основание под ТЗ v2.0».

### Этап 0. Закрыть блок 0 — 1 день

Цель: превью, в которое заказчик реально может войти с телефона.

1. К1: решить судьбу `--demo` (рекомендация: убрать флаг, демо-данных пока нет — нечем
   наполнять).
2. К2: `ORBITA_BASE_URL` в превью, порядок шагов «интерфейс → API».
3. К3: SETUP приведён в соответствие настройкам.
4. Отчёт `docs/reports/BLOCK-0.md` с честным списком того, чего нет.

**Готово, когда:** заказчик открыл превью PR по ссылке из «Управления» на iPhone.

### Этап 1. Основание под ТЗ v2.0 — 3–4 дня, до первой строки Пульта

1. Новая базовая миграция: программы, проекты с типом и шаблоном вех, подпроекты, задачи с
   типом и четырьмя видами привязки, вехи с исходным сроком и датой прохождения, регионы,
   учреждённая организация, поле версии везде.
2. `services/metrics.py`: лестница внимания, отклонение в днях, признак жизни, «успеваем?»,
   свежесть данных. Один вход, один выход.
3. Справочники из указов в `seed.py`.
4. Снятый объём удалён (таблица выше).
5. Новый ADR «Лестница внимания вместо светофора», отменяющий ADR-0005.

**Готово, когда:** `alembic upgrade head` даёт схему ТЗ v2.0; `make check` и `make test`
зелёные; в `services/metrics.py` есть тест «Пульт равен сумме разделов».

### Этап 2. Пульт и ввод — блок 1

Порядок внутри — обратный нынешнему: экран, показ заказчику, потом API.

1. **Экран Пульта на вымышленных данных**: лестница внимания, решение в одно касание,
   «с прошлого визита», «кто держит». Три устройства, две темы, снимки.
2. Заказчик смотрит на iPhone и говорит, что не так. Правки до утверждения.
3. API под утверждённый экран. Ни одного эндпоинта, у которого нет места на экране.
4. Проекты, Программы, Задачи, Календарь — тем же порядком.
5. Захват и разбор строки; шаблоны вех по типу проекта.
6. Утренняя сводка и два пуша.

**Готово, когда:** выполнены критерии блока 1 из [PLAN.md](../PLAN.md) на настоящих
проектах, внесённых заказчиком.

### Этапы 3 и 4 — блоки 2 и 3 без изменений

Состав и критерии — [PLAN.md](../PLAN.md). Единственное дополнение: порт `SetaGateway`
проектируется в блоке 3 **только как приём событий** (принято, начато, сдано, продлено) —
это прямая просьба заказчика «заложить фундамент синхронизации», и она не требует ни
подключения, ни изменения расчётов.

## Визуал: что значит 10x на экране

Не «красивее». Три измеримых утверждения.

### Пульт на iPhone: пять строк, ноль прокрутки, одно касание

Строка лестницы внимания несёт ровно четыре вещи и ничего больше:

```
● горит   ПФ-155 §5.1  Каримов        −3 дн   [ поторопить ]
● решение Спутниковая миссия, веха    ждёт 6 дн [ утвердить ]
```

сигнал словом и цветом → что это → кто держит → на сколько отклонились → что нажать.
Норматив: руководитель понимает картину за 30 секунд без прокрутки и принимает решение
одним касанием (цель нажатия ≥ 44 px, ТЗ 6).

**Проверяется снимком и сценарием Playwright**, а не мнением: высота пяти строк
укладывается в 844 px за вычетом шапки и нижней панели.

### Монитор: три панели, а не одна широкая

Сейчас на 2 560 px — одна карточка и 85 % пустоты (аудит В8). Должно быть: слева лестница
внимания, по центру раскрытый объект, справа календарь горячих дней. Режим «Совещание» —
один вопрос на весь экран, без служебных элементов.

### «Космос» — четыре приёма и ни одного больше

По ТЗ 6 и [ADR-0021](../adr/ADR-0021-cosmic-visual-layer.md):

1. орбитальные дуги в шапке раздела — на ноутбуке и мониторе;
2. мягкие частицы там же, с остановкой по `prefers-reduced-motion`;
3. **одна вспышка изменившегося числа** — это и есть «живое время» из ADR-0034;
4. плавные переходы между разделами, 180 мс.

Под данными — ничего и никогда. На телефоне — только пункт 3. Трёхмерная сцена — по списку
поверхностей ADR-0021 §3а, отдельным куском сборки, с проверкой манифеста в CI.

## Чего этот план **не** предлагает

Названо, чтобы к этому не возвращались:

- **Не переписывать заново то, что работает.** Список «оставить как есть» — половина
  ценности репозитория.
- **Не заводить микросервисы, очередь, Redis, воркер.** Пользователей двое; всё
  перечисленное снято решением заказчика и CLAUDE.md.
- **Не делать генерацию клиента из OpenAPI прямо сейчас.** При пяти запросах генератор
  дороже задачи; порог — примерно двадцать эндпоинтов, то есть середина этапа 2.
- **Не добавлять третью тему, пятый сигнальный цвет, вторую библиотеку компонентов.**
- **Не трогать `domain/ijro.py`.** Он написан по настоящим данным и по ним же проверен.
