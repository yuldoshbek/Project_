## 1. Задача в одном абзаце

Агентство «Ўзбеккосмос» ведёт десятки параллельных проектов, мини-проектов и срочных
поручений. Сейчас это живёт в мессенджерах, файлах и в голове помощника заместителя
директора. ORBITA даёт единую точку правды и **одну актуальную картину**: проекты и
задачи, входящие обращения и поручения вышестоящих органов, встречи с результатами,
календарь, дашборд со «светофором», динамика по направлениям, отчётность. Ключевая, не
заменяемая коробочным продуктом часть — сборка разнородного в один экран и связка с
ассистентом SETA.

Формула, которой проверяется любой экран: **что происходит сейчас → что сделано → что
требует внимания → где проблема → что дальше.**

## 2. Кто пользуется системой

**Пользователей двое** ([ADR-0011](adr/ADR-0011-two-user-scope.md)), и с 10.09.2026 они
оба — **живые ежедневные пользователи**, а не «вносящий» и «зритель». 16.09 это
подтверждено ещё раз: исполнители в систему не входят, у поручений Ижро ответственный —
строка из чужой таблицы, а не учётная запись ([ADR-0023](adr/ADR-0023-ijro-register.md)).

| Роль | Что делает | Признак того, что система работает |
|---|---|---|
| Помощник (`assistant`) | Вносит все данные, ведёт весь периметр руководителя, готовит доклад | Внесение проекта — минуты, обращения — секунды, а не «потом заполню» |
| Руководитель (`leader`) | **Открывает систему сам, ежедневно, с телефона.** Читает сводки, задаёт вопросы, принимает решения по статусу «На контроле». Разбор — вместе с помощником за ноутбуком | За 30 секунд на телефоне называет, что в красной зоне и что ждёт его решения |

**Сотрудники агентства — не пользователи.** Кураторы проектов, исполнители задач и
участники встреч живут в справочнике `people`: помощник назначает их, чтобы знать, с
кого спрашивать, но в систему они не входят. Смешать их с `users` — значит завести сорок
учётных записей, которыми никто не воспользуется, и получить ложную картину
многопользовательской системы.

**Точек входа теперь две, пользователей по-прежнему двое.** Кроме веб-входа, интерфейс
открывается как Mini App из бота SETA — там живёт аналитика встреч, переехавшая к нам
([SETA-ORBITA](integration/SETA-ORBITA.md) §5). Доступ к Mini App — белый список по
`users.external_seta_id`, и в нём ровно две записи. Поле `roles`, которое SETA
возвращает из `POST /integration/initdata/verify`, **игнорируется целиком**: у неё шесть
ролей и 34 права, у нас два пользователя и граница по периметру
([ADR-0013](adr/ADR-0013-telegram-bot.md) в редакции 16.09). Принять чужую матрицу прав
значит завести второго хозяина у доступа.

Из этого следуют три свойства, определяющие всё остальное:

1. **Презентационный слой — это и есть продукт.** Не понял за полминуты — задача не
   выполнена, сколько бы функций ни работало. Показывать нужно не только состояние, но и
   движение: вопрос руководителя — «где мы проседаем», а не «что сейчас красное»
   ([ADR-0014](adr/ADR-0014-progress-history.md)).
2. **Стоимость ввода решает, выживет ли система.** Все данные вносит один человек между
   делом. Пять минут на проект — и через месяц данные устареют. Каждая новая сущность
   обязана отвечать на вопрос, откуда берётся её свежесть. Первая способность ИИ-слоя —
   «сокращать ввод» — бьёт ровно сюда ([ADR-0022](adr/ADR-0022-ai-layer-boundaries.md)).
3. **Между руководителем и данными больше нет человека.** Раньше помощник успевал
   поправить перед показом. Теперь не успевает — поэтому честная пометка о свежести и
   полноте важнее самой цифры (ADR-0016, ADR-0017, ADR-0020, ADR-0023).

## 3. Доменная модель

```
Направление (справочник)      Организация-партнёр ──► псевдонимы (ADR-0023)
        │                              │
        └──────────┐        ┌──────────┘
                   ▼        ▼
Person ─куратор─► Проект        (Person — сотрудник агентства, не пользователь)
                   │  kind: project | mini
                   │  share_externally: bool  (ADR-0024, бывш. classification)
                   │  impediment: «что мешает» + дата (ADR-0016)
                   ├──► Веха (milestone)
                   ├──► Задача ──► чек-лист, теги, исполнитель (Person)
                   │       │       recurrence_rule (RRULE), source_meeting_id
                   │       │       is_control: status/completed_at/due_at за SETA
                   │       └──► Уведомление ──► веб | почта | бот SETA
                   ├──► Комментарий
                   ├──► Документ ──► Версия документа
                   ├──► Встреча ──► участники, Результат ──► задачи (ADR-0018)
                   └──► Входящее обращение (ADR-0017)
                            kind: correspondence — письмо, запрос, звонок
                            kind: assignment     — «Ижро», поручение вышестоящего
                                                   органа: ответственный строкой,
                                                   привоз пакетом (ADR-0023)

Цепочка связей: Обращение → Проект → Задача → Встреча → Решение → Результат

SETA ──► встречи, занятость (busy), ход поручений, due_at   (ADR-0015, ADR-0020)
ORBITA ──► числа для утренней сводки, приём нажатий кнопок  (ADR-0020)
Google ◄── вехи и сроки задач, календарь «ORBITA», в одну сторону (ADR-0012)
Внешняя модель ◄── контекст ИИ-слоя, только с share_externally (ADR-0022)
Сквозное: audit_log, notifications, ai_requests, снимки состояния, справочники, отчёты
```

Сущностей, которых **нет** и не должно появиться: трудозатраты, бюджетные проводки,
согласование маршрутов документов, ЭЦП (ТЗ 2.5), «поручение» отдельно от задачи
(поручение — задача с `is_control`), участники проекта, наблюдатели задач, уровни
эскалации, **реестр рисков** (ADR-0016), **заявка на встречу** (живёт в SETA, ADR-0018,
ADR-0020), **письмо отдельно от обращения** (одна сущность, ADR-0017), **отдельный
реестр Ижро** (вид обращения, ADR-0023), **собственный Telegram-бот** (канал один —
SETA, ADR-0013 в редакции 16.09).

**Мини-проект — не отдельная сущность**, а `kind = mini`: та же таблица, другие правила
валидации (вехи необязательны) и другая форма создания. **«Ижро» — не отдельная
сущность** по той же причине: `inbound_requests.kind = assignment` плюс поле
ответственного. Различия в одно поле не стоят второй таблицы, второго списка и второй
аналитики.

**Время руководителя нам не принадлежит.** Встречи и анонимную занятость мы забираем из
API SETA и не создаём мимо её правил; ручное заведение встречи остаётся аварийным путём
и честно подписано «эта встреча календарь руководителя не занимает»
([ADR-0020](adr/ADR-0020-calendar-comes-from-seta.md)).

## 5. Сквозные правила реализации

1. **Граница проходит по периметру системы**, а не между пользователями: внутри видно
   всё. Наружу ведут **пять точек** — Google-календарь, SETA, Telegram через SETA,
   экспорт и внешняя модель, — и в каждой действует предпочтение выдачи
   `share_externally` (ADR-0024). Запись с `share_externally = false` не уходит ни
   названием, ни счётчиком. Проверка стоит внутри функции выдачи, а не у вызывающего.
   Это не гриф секретности и не режим доступа: служба безопасности из объёма убрана
   (решение заказчика 16.09), а вопрос «что можно показывать наружу» остался — точек
   выхода стало больше, а не меньше.
2. **Поиск в открытой сети ограничен белым списком полей** (ADR-0022): наружу уходят
   только название организации и реквизиты источника поручения. Названия, коды и
   описания проектов, темы обращений, ФИО из `people` не уходят в поиск никогда. Белый
   список полей, а не чёрный список слов: содержание, пересказанное другими словами,
   чёрный список не ловит.
3. **Происхождение данных видно на самих данных.** Найденное в сети сохраняется с
   `source = web_unverified`, показывается отдельным блоком «из сети, не проверено» и в
   поля карточки автоматически не пишется — перенос делает человек, и автором значения в
   `audit_log` становится он. Любой порождённый моделью текст несёт пометку рядом с
   текстом, а не сноской внизу экрана (ADR-0022). Смешать внесённое, привезённое и
   найденное в одном поле — значит через месяц не знать, что из этого кто-то проверял.
4. **Владение данными разделено по полям, а не по записям** (ADR-0015, договор с SETA).
   Сторона принимает только те поля, которыми не владеет; чужое поле игнорируется молча.
   За SETA — `tasks.status`, `completed_at`, `due_at` и всё время встречи; за нами —
   `planned_due_at`, смысл, привязки и все показатели. Двух хозяев у одного поля не бывает.
5. **Свежесть показывается всегда.** Строка «что мешает», счётчики обращений, дата
   привоза таблицы Ижро, момент последнего успешного опроса SETA — у каждого либо дата
   обновления, либо пометка об устаревании. Счётчик обращений подписывается «внесено за
   период», а не «поступило»: цифра без честной подписи порождает неверный вывод по
   верным данным. При недоступности SETA показываются последние полученные данные с
   пометкой, а не пустой экран: пустой календарь читается как «день свободен».
6. Все агрегаты главного экрана — один SQL-запрос на экран, не N запросов на карточку.
7. Время: хранение UTC (`timestamptz`), отображение `Asia/Tashkent`, просрочка — по
   календарным дням. События в Google создаются с явным поясом, не «плавающим».
8. Локализация: три локали `ru`, `uz-Cyrl`, `uz-Latn`. Ни одной строки в коде
   компонента — только ключи. Коды SETA (`uz`, `uz_cyrl`, `ru`, `en`) переводятся
   таблицей соответствия в шлюзе обмена; четвёртый словарь не заводится — английский
   интерфейс обслуживал бы пользователя, которого у нас нет.
9. Идемпотентность всех фоновых заданий (ADR-0008), включая обмен с SETA и привоз Ижро.
10. Аудит пишется сервисным слоем в одной транзакции с изменением (ADR-0010). Он же
    отвечает на вопрос «кто и что занёс» в аналитике обращений. Решение, нажатое кнопкой
    в чужом боте, ложится в `audit_log` от имени руководителя — инвариант не отменяется
    тем, что кнопка была в чужом интерфейсе.
11. API версионируется префиксом `/api/v1`; ломающее изменение — новый префикс.
12. **Одни и те же цифры во всех местах**: главный экран, «Доклад», утренняя сводка SETA
    и ответ Mini App считаются одними сервисами. Модель цифры не считает — она их только
    называет. Два источника расчёта разойдутся, и доверия не будет ни к одному.
13. **Телефон проектируется первым** (ADR-0019). Что помещается на телефоне,
    разложится на ноутбуке; обратное неверно.
14. **Цвет живёт только в `tokens.css`**, в двух наборах значений под одними именами
    (ADR-0021). Тёмная тема основная, светлая — переопределением. Контраст текста не
    ниже 4.5:1 и знака, несущего смысл, не ниже 3:1 в обеих темах — это пункт приёмки, а
    не пожелание.
15. Ни одного ключа в репозитории: он публичный (**Q30**). Секрет Google OAuth,
    сервисный токен SETA, ключ провайдера модели, токены обновления — только окружение и
    GitHub Secrets.

## 6. Границы MVP

**Входит:** проекты и мини-проекты, вехи, задачи с чек-листами и тегами, справочник
сотрудников, три представления базы задач, входящие обращения с аналитикой, **реестр
Ижро с еженедельным привозом**, встречи с результатом и вычисляемым качеством, единый
календарь из данных SETA, обмен с SETA по поручениям, встречам и занятости, числа для
утренней сводки и приём нажатий кнопок, дашборд со светофором и Гантт, риски как
сигналы, главный экран и режим «Доклад», мобильный вид, **тёмная тема и космический
визуальный слой**, **ИИ-слой из пяти способностей**, Mini App из бота SETA, справочники,
глобальный поиск, напоминания, отчёты в Word и Excel, журнал изменений, вложения с
версиями.

**Не входит:** чтение встреч из Google и любой вход направления «Google → ORBITA»
(ADR-0020), собственный Telegram-бот (ADR-0013 в редакции 16.09), заявки на встречу и их
согласование (живут в SETA), распознавание текста с фотографий писем (Q21 — вопрос без
адресата после снятия темы безопасности), интеграция с почтовым ящиком, выгрузка из СЭД,
ЭЦП, бухгалтерский учёт, публичный портал, мобильное приложение (только адаптивная
вёрстка), учёт трудозатрат, синхронизация с Outlook, разграничение доступа между
пользователями, реестр рисков, живое обновление постоянным соединением, трёхмерная
графика и анимированный фон под данными (ADR-0021), локальная модель в контуре
(ADR-0022).

Отдельной строкой, потому что этого нет ни в одном тикете: **выкладка**. Контейнеризация
самого приложения, продовый контур, домен и HTTPS планом не заведены, а по договору обе
системы переезжают на один сервер — там же второе столкновение портов (**Q29**).

## 7. Термины (единообразно в коде и в интерфейсе)

| Русский | В коде | Примечание |
|---|---|---|
| Проект / мини-проект | `Project`, `kind` | одна сущность, `project` либо `mini` |
| Веха | `Milestone` | не «этап», в UI — «веха» |
| Задача, поручение | `Task` | поручение = задача с `is_control`; `status`, `completed_at`, `due_at` — за SETA |
| Плановый срок | `planned_due_at` | наш срок по проекту; действующий `due_at` ведёт SETA |
| Сотрудник агентства | `Person` | справочник `people`; в систему не входит |
| Куратор проекта | `curator_person_id` | сотрудник, отвечающий за проект |
| Исполнитель задачи | `assignee_person_id` | сотрудник, которому поручено |
| Помощник | `assistant` | пользователь системы, вносит данные |
| Руководитель | `leader` | пользователь системы, смотрит и решает |
| Направление | `Direction` | справочник ТЗ 7; на главном экране — фильтр, не блок |
| Просрочка | `is_overdue` | вычисляемое, ADR-0004 |
| Светофор | `health` | зелёный, жёлтый, красный, серый — ADR-0005 |
| Что мешает | `impediment`, `impediment_updated_at` | единственное ручное поле по рискам, ADR-0016 |
| Молчание | `is_silent` | нет движения дольше порога; главный сигнал, ADR-0016 |
| Входящее обращение | `InboundRequest` | письмо, просьба, запрос — одна сущность, канал полем, ADR-0017 |
| **Ижро** | `InboundRequest.kind = assignment` | поручение вышестоящего органа; привозится таблицей еженедельно, ответственный — `responsible_text`, ADR-0023 |
| **Привоз** | `import_batch` | пакет строк одной недельной выгрузки Ижро; предпросмотр до записи обязателен, ADR-0023 |

| Качество встречи | `meeting_quality` | результативная, формальная, провисшая — вычисляется у нас; ручная оценка руководителя остаётся в SETA и с нашей не смешивается |
| **Занятость** | `busy` | анонимный интервал из `GET /integration/busy`: `start`, `end`, `kind`. Без названия и участников, в интерфейсе серым, подписью «личное время», ADR-0020 |
| Доклад | `briefing` | режим большого экрана, не отдельный расчёт |
| Сводка | `digest` | утреннее сообщение; отправляет бот SETA, числа считаем мы |
| **Mini App** | — | наш интерфейс, открытый из бота SETA; доступ — белый список по `users.external_seta_id`, `roles` из ответа SETA игнорируется |
