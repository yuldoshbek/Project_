Результат разбора [ТЗ v1.0](../tz/TZ-ORBITA-v1.0.md). Этот файл — рабочий контекст для
разработчика и для агента: доменная модель, найденные неоднозначности и то, как они
разрешены. Решения живут в [docs/adr](adr), нерешённое — в [OPEN-QUESTIONS](OPEN-QUESTIONS.md).

## 1. Задача в одном абзаце

Агентство «Ўзбеккосмос» ведёт десятки параллельных проектов, мини-проектов и срочных
поручений. Сейчас это живёт в мессенджерах, файлах и в голове помощника заместителя
директора. ORBITA даёт единую точку правды и **одну актуальную картину**: проекты и
задачи, входящие обращения, встречи с результатами, календарь, дашборд со «светофором»,
динамика по направлениям, отчётность. Ключевая, не заменяемая коробочным продуктом
часть — сборка разнородного в один экран и связка с ассистентом SETA.

Формула, которой проверяется любой экран: **что происходит сейчас → что сделано → что
требует внимания → где проблема → что дальше.**

## 2. Кто пользуется системой

**Пользователей двое** ([ADR-0011](adr/ADR-0011-two-user-scope.md)). Но с 10.09.2026 они
оба — **живые ежедневные пользователи**, а не «вносящий» и «зритель».

| Роль | Что делает | Признак того, что система работает |
|---|---|---|
| Помощник (`assistant`) | Вносит все данные, ведёт весь периметр руководителя, готовит доклад | Внесение проекта — минуты, обращения — секунды, а не «потом заполню» |
| Руководитель (`leader`) | **Открывает систему сам, ежедневно, с телефона.** Читает сводки, задаёт вопросы, принимает решения по статусу «На контроле». Разбор — вместе с помощником за ноутбуком | За 30 секунд на телефоне называет, что в красной зоне и что ждёт его решения |

**Сотрудники агентства — не пользователи.** Кураторы проектов, исполнители задач и
участники встреч живут в справочнике `people`: помощник назначает их, чтобы знать, с
кого спрашивать, но в систему они не входят. Смешать их с `users` — значит завести сорок
учётных записей, которыми никто не воспользуется, и получить ложную картину
многопользовательской системы.

Из этого следуют три свойства, определяющие всё остальное:

1. **Презентационный слой — это и есть продукт.** Не понял за полминуты — задача не
   выполнена, сколько бы функций ни работало. Показывать нужно не только состояние, но и
   движение: вопрос руководителя — «где мы проседаем», а не «что сейчас красное»
   ([ADR-0014](adr/ADR-0014-progress-history.md)).
2. **Стоимость ввода решает, выживет ли система.** Все данные вносит один человек между
   делом. Пять минут на проект — и через месяц данные устареют. Каждая новая сущность
   обязана отвечать на вопрос, откуда берётся её свежесть.
3. **Между руководителем и данными больше нет человека.** Раньше помощник успевал
   поправить перед показом. Теперь не успевает — поэтому честная пометка о свежести и
   полноте важнее самой цифры (ADR-0016, ADR-0017).

## 3. Доменная модель

```
Направление (справочник)      Организация-партнёр
        │                              │
        └──────────┐        ┌──────────┘
                   ▼        ▼
Person ─куратор─► Проект        (Person — сотрудник агентства, не пользователь)
                   │  kind: project | mini
                   │  classification: internal | restricted
                   │  impediment: «что мешает» + дата (ADR-0016)
                   ├──► Веха (milestone)
                   ├──► Задача ──► чек-лист, теги, исполнитель (Person)
                   │       │       recurrence_rule (RRULE), source_meeting_id
                   │       └──► Уведомление ──► веб | почта | Telegram
                   ├──► Комментарий
                   ├──► Документ ──► Версия документа
                   ├──► Встреча ──► участники, Результат ──► задачи (ADR-0018)
                   └──► Входящее обращение ──► организация, тема, срок (ADR-0017)

Цепочка связей: Обращение → Проект → Задача → Встреча → Решение → Результат

Google-календарь ◄──► вехи, сроки, встречи             (ADR-0012)
SETA ◄──► ход поручений, заявки и согласование встреч   (ADR-0015)
Сквозное: audit_log, notifications, снимки состояния, справочники, отчёты
```

Сущностей, которых **нет** и не должно появиться: трудозатраты, бюджетные проводки,
согласование маршрутов документов, ЭЦП (ТЗ 2.5), «поручение» отдельно от задачи
(поручение — задача с `is_control`), участники проекта, наблюдатели задач, уровни
эскалации, **реестр рисков** (ADR-0016), **заявка на встречу** (живёт в SETA, ADR-0018),
**письмо отдельно от обращения** (одна сущность, ADR-0017).

**Мини-проект — не отдельная сущность**, а `kind = mini`: та же таблица, другие правила
валидации (вехи необязательны) и другая форма создания.

## 5. Сквозные правила реализации

1. **Граница проходит по периметру системы**, а не между пользователями: внутри видно
   всё, наружу (Google, SETA, Telegram, экспорт, ИИ) не уходят проекты `restricted` —
   ни названием, ни счётчиком. Проверка стоит внутри функции выдачи, а не у вызывающего.
   Точек выхода теперь пять, и каждая обязана быть покрыта тестом.
2. **Владение данными разделено по полям, а не по записям** (ADR-0015). Сторона
   принимает только те поля, которыми не владеет; чужое поле игнорируется молча.
   Двух хозяев у одного поля не бывает.
3. **Свежесть показывается всегда.** Строка «что мешает», счётчики обращений, ход
   исполнения поручений — у каждого либо дата обновления, либо пометка об устаревании.
   Счётчик обращений подписывается «внесено за период», а не «поступило»: цифра без
   честной подписи порождает неверный вывод по верным данным.
4. Все агрегаты главного экрана — один SQL-запрос на экран, не N запросов на карточку.
5. Время: хранение UTC (`timestamptz`), отображение `Asia/Tashkent`, просрочка — по
   календарным дням. События в Google создаются с явным поясом, не «плавающим».
6. Локализация: три локали `ru`, `uz-Cyrl`, `uz-Latn`. Ни одной строки в коде
   компонента — только ключи. Тексты бота локализуются так же, как интерфейс.
7. Идемпотентность всех фоновых заданий (ADR-0008), включая обмен с SETA.
8. Аудит пишется сервисным слоем в одной транзакции с изменением (ADR-0010). Он же
   отвечает на вопрос «кто и что занёс» в аналитике обращений — отдельного механизма
   для этого не нужно.
9. API версионируется префиксом `/api/v1`; ломающее изменение — новый префикс.
10. **Одни и те же цифры во всех местах**: главный экран, «Доклад», сводка в Telegram и
    ответ SETA считаются одними сервисами. Два источника расчёта разойдутся, и доверия
    не будет ни к одному.
11. **Телефон проектируется первым** (ADR-0019). Что помещается на телефоне,
    разложится на ноутбуке; обратное неверно.
12. Ни одного ключа в репозитории: он публичный. Токен бота, секрет Google OAuth,
    учётные данные SETA, токены обновления — только окружение и GitHub Secrets.

## 6. Границы MVP

**Входит:** проекты и мини-проекты, вехи, задачи с чек-листами и тегами, справочник
сотрудников, три представления базы задач, входящие обращения с аналитикой, встречи с
результатом и вычисляемым качеством, единый календарь с двусторонней синхронизацией
Google, обмен с SETA по поручениям и встречам, дашборд со светофором и Гантт, риски как
сигналы, главный экран и режим «Доклад», мобильный вид, справочники, глобальный поиск,
напоминания, отчёты в Word и Excel, журнал изменений, вложения с версиями.

**Не входит:** обращение ИИ-слоя к внешней модели (до ответа СБ, Q22), распознавание
текста с фотографий писем (Q21), интеграция с почтовым ящиком, ЭЦП и СЭД, бухгалтерский
учёт, публичный портал, мобильное приложение (только адаптивная вёрстка), учёт
трудозатрат, синхронизация с Outlook, разграничение доступа между пользователями,
реестр рисков, заявки на встречу (живут в SETA), живое обновление постоянным соединением.

## 7. Термины (единообразно в коде и в интерфейсе)

| Русский | В коде | Примечание |
|---|---|---|
| Проект / мини-проект | `Project`, `kind` | одна сущность, `project` либо `mini` |
| Веха | `Milestone` | не «этап», в UI — «веха» |
| Задача, поручение | `Task` | поручение = задача с `is_control`; ход исполнения — за SETA |
| Сотрудник агентства | `Person` | справочник `people`; в систему не входит |
| Куратор проекта | `curator_person_id` | сотрудник, отвечающий за проект |
| Исполнитель задачи | `assignee_person_id` | сотрудник, которому поручено |
| Помощник | `assistant` | пользователь системы, вносит данные |
| Руководитель | `leader` | пользователь системы, смотрит и решает |
| Направление | `Direction` | справочник ТЗ 7; на главном экране — фильтр, не блок |
| Просрочка | `is_overdue` | вычисляемое, ADR-0004 |
| Светофор | `health` | зелёный, жёлтый, красный, серый — ADR-0005 |
| **Что мешает** | `impediment`, `impediment_updated_at` | единственное ручное поле по рискам, ADR-0016 |
| **Молчание** | `is_silent` | нет движения дольше порога; главный сигнал, ADR-0016 |
| **Входящее обращение** | `InboundRequest` | письмо, просьба, запрос — одна сущность, канал полем, ADR-0017 |
| **Результат встречи** | `MeetingOutcome` | что решили и что делаем, ADR-0018 |
| **Качество встречи** | `meeting_quality` | результативная, формальная, провисшая — вычисляется, ADR-0018 |
| Доклад | `briefing` | режим большого экрана, не отдельный расчёт |
| Сводка | `digest` | утреннее сообщение в Telegram |
| Ограниченный доступ | `classification = restricted` | не покидает систему ни одной из пяти точек выхода |
