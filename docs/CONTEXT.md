# CONTEXT — что мы строим и почему именно так

Результат разбора [ТЗ v1.0](../tz/TZ-ORBITA-v1.0.md). Этот файл — рабочий контекст для
разработчика и для агента: доменная модель, найденные в ТЗ неоднозначности и то, как они
разрешены. Решения живут в [docs/adr](adr), нерешённое — в [OPEN-QUESTIONS](OPEN-QUESTIONS.md).

## 1. Задача в одном абзаце

Агентство «Ўзбеккосмос» ведёт десятки параллельных проектов, мини-проектов и срочных
поручений. Сейчас это живёт в мессенджерах, файлах и в голове помощника заместителя
директора. ORBITA даёт единую точку правды: карточки проектов и задач, календарь, дашборд
со «светофором» по срокам, уведомления и эскалацию, отчётность. Ключевая, не заменяемая
коробочным продуктом часть — агрегированный вид помощника («весь периметр руководителя»)
и связка с Telegram-ассистентом SETA.

## 2. Кто пользователи и что для каждого «успех»

| Роль | Что делает ежедневно | Признак того, что система работает |
|---|---|---|
| Руководитель (зам. директора) | Смотрит дашборд, утверждает, делегирует | За 30 секунд видит, сколько проектов в красной зоне (U3) |
| Помощник / координатор | Ведёт весь периметр руководителя, ставит задачи от его имени, гасит просрочки | Утром открывает один экран и видит всё, что горит, без обзвона кураторов (U2) |
| Куратор проекта | Ведёт свои проекты, назначает исполнителей, отчитывается | Создание проекта с вехами и протоколом — пара минут (U1); отчёт за месяц — одно нажатие (U5) |
| Исполнитель | Обновляет статусы своих задач | Видит только своё, получает срочную задачу и понимает срок (U4, U7) |
| Наблюдатель | Смотрит проекты, куда приглашён | Не видит ничего лишнего |
| Администратор | Пользователи, роли, справочники, аудит | Меняет справочники без разработчика (ТЗ 6.8) |

Роль **помощника — центральная**. Если её агрегированный вид сделан формально («список
задач с фильтром»), проект не решает исходную проблему (ТЗ 3.3, 4).

## 3. Доменная модель

```
Направление (справочник)      Организация-партнёр
        │                              │
        └──────────┐        ┌──────────┘
                   ▼        ▼
User ──куратор──► Проект ◄── project_members (curator | executor | watcher)
                   │  kind: project | mini
                   │  classification: internal | restricted
                   ├──► Веха (milestone)
                   ├──► Задача ──► чек-лист, теги, наблюдатели
                   │       │       recurrence_rule (RRULE)
                   │       └──► Эскалация ──► Уведомление
                   ├──► Комментарий  ─┐
                   ├──► Документ ──► Версия документа
                   └──► Событие календаря (встреча)

Сквозное: audit_log, notifications, справочники, отчёты
```

Сущности, которых **нет** и не должно появиться в MVP: трудозатраты, бюджетные проводки,
согласование маршрутов документов, ЭЦП (ТЗ 2.5), сущность «поручение» отдельно от задачи
(поручение — это задача с автором-руководителем и признаком контроля).

**Мини-проект — не отдельная сущность**, а `kind = mini`: та же таблица, другие правила
валидации (вехи необязательны) и другая форма создания. Разделять таблицы — значит
дублировать задачи, комментарии, файлы и права.

## 4. Что в ТЗ оказалось неоднозначным и как разрешено

| Место ТЗ | Что не сходится | Решение |
|---|---|---|
| 7, статусы задачи | «Просрочена» стоит в одном ряду с рабочими статусами | Вычисляемый признак — [ADR-0004](adr/ADR-0004-overdue-is-computed.md) |
| 6.4, «светофор» | Названы три цвета, не заданы пороги | Правило + настраиваемые пороги — [ADR-0005](adr/ADR-0005-traffic-light.md) |
| 6.9, поиск на трёх раскладках | Не сказано, что «Oʻzbekiston» и «Ўзбекистон» должны находить друг друга — но без этого требование бессмысленно | Нормализация и транслитерация — [ADR-0006](adr/ADR-0006-multiscript-search.md) |
| 5 против 10.1 | Роль «Администратор системы» = IT-сопровождение, но при этом разграничение доступа на уровне проекта | Администратор управляет пользователями, но не видит содержимое чужих проектов — [ADR-0003](adr/ADR-0003-project-level-rbac.md) |
| 6.3 | «.ics» и «двусторонняя синхронизация» в одном пункте | В MVP только выгрузка; синхронизация — этап 4 |
| 6.5 | «Эскалация вышестоящему» — вышестоящий не определён | Цепочка куратор → помощник → руководитель — [ADR-0008](adr/ADR-0008-notifications-escalation.md), Q4 |
| 6.7 | «Экспорт в Word» в госоргане — это бланки, а не выгрузка таблицы | Нужны образцы, Q3 |
| 10.2 | «несколько десятков пользователей» — неизмеримо | 60 одновременных сессий, p95 API ≤ 400 мс — предложено в ТЗ |
| 15, риск 1 | Классификация данных выяснится позже | Режим `restricted` заложен сразу — [ADR-0007](adr/ADR-0007-restricted-data.md) |
| 6.2, повторяющиеся задачи | Неясно, экземпляры реальные или виртуальные | Реальные: иначе нельзя назначить исполнителя и обсудить конкретный экземпляр |

## 5. Сквозные правила реализации

1. Видимость данных — только через `visible_projects(actor)`.
2. Все агрегаты дашборда — один SQL-запрос на экран, не N запросов на карточку.
   Профиль дашборда с 200 проектами и 3000 задач входит в критерии приёмки ORB-029.
3. Время: хранение UTC (`timestamptz`), отображение `Asia/Tashkent`, «просрочено»
   считается по календарным, а не рабочим дням (рабочий календарь в ТЗ не заявлен).
4. Локализация: три локали `ru`, `uz-Cyrl`, `uz-Latn` с первого экрана. Ни одной строки
   в коде компонента — только ключи. Добавление `en` (ТЗ 10.3) не должно требовать правок кода.
5. Идемпотентность всех фоновых заданий (ADR-0008).
6. Аудит пишется сервисным слоем в одной транзакции с изменением (ADR-0010).
7. API версионируется префиксом `/api/v1`; ломающее изменение — новый префикс.

## 6. Границы MVP

**Входит (этапы 1–3 ТЗ 13):** проекты и мини-проекты, вехи, задачи с чек-листами и тегами,
роли и права на уровне проекта, три представления базы задач, календарь и .ics, дашборд со
светофором и Гантт, справочники, глобальный поиск, уведомления и эскалация, отчёты в Word
и Excel, аудит, вложения с версиями.

**Не входит:** ИИ-слой (ТЗ 11.3), двусторонняя синхронизация календарей, ЭЦП и СЭД,
бухгалтерский учёт, публичный портал, мобильное приложение (только адаптивная вёрстка),
учёт трудозатрат.

## 7. Термины (единообразно в коде и в интерфейсе)

| Русский | В коде | Примечание |
|---|---|---|
| Проект / мини-проект | `Project`, `kind=project|mini` | одна сущность |
| Веха | `Milestone` | не «этап», в UI — «веха» |
| Задача, поручение | `Task` | поручение = задача с `author` = руководитель |
| Куратор | `curator` | роль в `project_members`, не глобальная |
| Исполнитель | `assignee` | у задачи; `executor` — в `project_members` |
| Наблюдатель | `watcher` | |
| Направление | `Direction` | справочник, ТЗ 7 |
| Просрочка | `is_overdue` | вычисляемое, ADR-0004 |
| Светофор | `health` (`green|yellow|red|grey`) | ADR-0005 |
| Эскалация | `Escalation` | уровни 1–3 |
